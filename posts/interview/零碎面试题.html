零碎面试题

1. 如果让你优化携程一个核心列表页（如酒店列表）的加载速度和渲染性能，你会从哪些方面入手？

面试官题干

如果让你优化携程一个核心列表页，比如酒店列表的加载速度和渲染性能，你会从哪些方面入手？

面试回答

所以整体来说，我会先通过性能工具定位瓶颈。然后从 网络和资源层，接口和数据层，渲染层，用户体验层这四个层面进行入手优化，而不是只关注某一个点。

首先是网络和资源层。

比如对 JS、CSS、图片等静态资源进行压缩和拆分，使用 CDN，图片根据展示尺寸进行压缩和懒加载，同时通过 HTTP 缓存减少重复请求。

第二是接口和数据层的优化。

比如减少不必要的接口请求，对酒店列表这种数据量比较大的接口，可以进行分页或者增量加载，同时对一些不会频繁变化的数据进行缓存。

第三是渲染层渲染性能优化。

如果酒店列表有几百甚至上千条数据，我会考虑使用虚拟列表，只渲染当前视口附近的数据，避免一次性创建大量 DOM。

在 React 中，我还会通过 React.memo、useMemo、useCallback 等手段减少不必要的组件重新渲染，但我不会滥用，而是结合 React DevTools 或 Performance 面板定位真正的性能瓶颈。

最后是用户体验层。

这一层面主要是给用户感知与反馈并优化用户体验。首屏可以优先加载核心内容，使用 Skeleton 骨架屏，图片懒加载，并且在数据加载过程中给用户明确反馈。

面试官追问：你怎么定位到底是哪一部分慢？

可以回答：

我一般会先使用 Chrome DevTools 的 Network 和 Performance 面板。

Network 主要看接口耗时、资源大小、请求数量以及是否存在阻塞。

Performance 主要看具体是 JavaScript 执行时间长、Layout/Reflow 比较多，还是 Paint、Composite 比较耗时。

React 项目还可以结合 React DevTools Profiler 查看具体是哪些组件频繁重新渲染。

这样可以先定位瓶颈，再针对性优化，而不是凭经验优化。

2. 在 React 项目中，你是如何管理组件状态的？

面试回答

我一般会根据状态的作用范围来决定使用什么方式。

对于组件内部使用的状态，比如表单输入、弹窗开关、Tab 状态，我会优先使用 useState 或 useReducer。

如果是多个组件之间需要共享，但是状态本身比较简单，比如主题色、语言等，我会考虑使用 Context API。

如果是跨页面、跨模块共享的复杂业务状态，比如用户信息、权限、购物车、复杂的全局业务状态，我会考虑使用 Redux、Zustand 这类状态管理方案。

我的原则是：

状态影响范围越小，越倾向于组件内部管理；共享范围越大、业务逻辑越复杂，就越需要专门的状态管理方案。

追问：为什么不用 Context API 解决所有问题？

可以回答：

Context 更适合解决“数据需要跨层级 传递”的问题，但它本身并不是一个完整的状态管理方案。

如果整个应用的大量业务状态都放进 Context，随着项目变大，状态之间的依赖关系会越来越复杂，而且 Context Provider 中的 value 发生变化时，消费这个 Context 的组件可能会产生重新渲染。

所以简单的全局状态可以用 Context，但复杂业务状态我更倾向于使用 Redux、Zustand 这类方案，通过更细粒度的状态订阅降低不必要的渲染，同时也方便管理状态更新逻辑。

追问：你提到用 Context API 管理主题色。如果主题色需要在几十个深层组件中使用，而且可能频繁更新，你还坚持只用 Context 吗？

面试回答

如果主题色只是偶尔切换，比如用户手动切换一次深色模式，我觉得 Context 完全可以。

但是如果这个主题色更新非常频繁，我就不会简单地把整个主题对象放到 Context 中。

因为 Context 的更新可能导致大量消费这个 Context 的组件重新渲染。

我会考虑两种方式：

第一种是拆分 Context，把频繁变化和不频繁变化的数据拆开。

第二种是使用更细粒度的状态管理方案，比如 Zustand、Redux，或者使用专门的 Context Selector 思路，让组件只订阅自己真正需要的数据。

所以核心问题不是“Context 能不能用”，而是：

状态更新频率 + 影响范围 + 消费组件数量共同决定是否适合使用 Context。

3. 如何实现一个支持无限滚动加载的列表组件？

面试回答

我一般会把无限滚动拆成触发加载、请求管理、数据合并和用户体验几个部分。

首先可以使用 IntersectionObserver 监听列表底部的一个 sentinel 元素。

当这个元素进入可视区域时，就触发下一页数据请求。

然后需要维护几个状态：

list
loading
hasMore
page

请求成功后，把新的数据追加到原来的列表中。

同时要避免重复请求，所以在 loading === true 的时候不再触发请求。

如果后端返回了 hasMore 或者 total，还可以判断是否已经加载完毕。

简单实现思路

const observer = new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting && !loading && hasMore) {
    loadMore();
  }
});

我更倾向于使用 IntersectionObserver，而不是监听 scroll 后不断计算位置，因为后者容易产生大量事件回调。

需要考虑哪些用户体验问题？

我会考虑：

  • 首次加载 Skeleton
  • 加载更多时显示 Loading
  • 没有更多数据显示“没有更多了”
  • 请求失败提供重试
  • 防止重复请求
  • 防止快速滚动造成请求竞态
  • 列表数据量特别大时使用虚拟列表
  • 图片使用懒加载

如果数据存在排序要求，还需要考虑分页数据重复或者顺序错乱的问题。

4. 如何处理前端应用中的跨域问题？

面试回答

跨域本质上是浏览器的同源策略导致的。

常见解决方案主要有：

第一，后端配置 CORS。

这是生产环境比较常见的方式，由服务器通过响应头允许指定的 Origin 访问。

第二，开发环境使用代理。

比如 Vite 可以配置：

server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true
    }
  }
}

这样浏览器实际上请求的是当前前端服务，由开发服务器再转发到后端。

第三，生产环境通过 Nginx 做反向代理。

比如：

浏览器
  ↓
Nginx
  ↓
/api → 后端服务

这样从浏览器角度看，前后端属于同源。

追问：生产环境除了 CORS，还需要注意哪些安全问题？

可以回答：

CORS 只是解决跨域访问控制，并不等于完整的安全方案。

我还会关注 XSS、CSRF、SQL 注入、点击劫持、敏感信息泄露等问题。

前端层面比如避免直接使用 innerHTML 插入不可信内容，对用户输入进行校验。

Cookie 如果用于身份认证，可以合理设置 HttpOnly、Secure、SameSite 等属性。

同时生产环境还应该使用 HTTPS，并通过 CSP 等安全策略进一步降低 XSS 风险。

5. 请描述一次你解决过的复杂 CSS 布局问题或浏览器兼容性问题。

这个问题你不要硬编一个特别复杂的 CSS Bug。

你可以结合你实际项目中的后台系统，说一个比较真实的布局问题。

面试回答

我之前在做 React 后台管理系统的时候，遇到过一个比较典型的布局问题。

当时页面采用的是比较复杂的左右布局 + 中间内容区域，中间区域需要自适应剩余空间，同时内部还有列表和滚动区域。

一开始直接使用 width: 100% 和一些固定高度，结果在不同分辨率下会出现内容区域溢出或者滚动条不符合预期的问题。

后来我重新梳理了整个布局结构，把页面拆成：

页面
├── Header
└── Content
    ├── Sidebar
    └── Main

外层使用 Flex 布局，让 Main 自动占据剩余空间。

同时对于需要滚动的 Flex 子元素，设置：

min-width: 0;
min-height: 0;
overflow: auto;

解决 Flex 子元素因为默认 min-width: auto 导致内容撑开的问题。

这个问题让我比较深地理解了 Flex 布局中尺寸计算和滚动容器之间的关系，后来遇到类似后台页面布局时，我会优先从布局层级和尺寸计算入手排查。

面试官可能追问

min-width: 0 为什么有用？

回答：

Flex 子元素默认的 min-width 是 auto，它可能根据内容的最小尺寸撑开容器。

设置 min-width: 0 后，相当于允许这个 Flex 子元素缩小到容器允许的尺寸，超出的内容再通过 overflow 处理。

这个回答很加分。

6. 你如何理解前端工程化？

面试回答

我理解前端工程化就是：

通过工具、规范和自动化流程，把前端开发从依赖个人经验，变成一套可持续、可维护、可协作的工程体系。

它不仅仅是 Webpack 或 Vite。

我一般会从几个方面理解：

  1. 项目规范：ESLint、Prettier、TypeScript
  2. 依赖管理：锁定版本、依赖去重、安全扫描
  3. 构建打包：Vite、Webpack
  4. 代码质量：Lint、Type Check、Test
  5. Git 协作：分支管理、Code Review
  6. CI/CD：自动构建、测试和部署
  7. 性能优化：代码分割、Tree Shaking、资源压缩、缓存等

追问：你项目中怎么优化打包？

面试回答

我主要会从几个方面考虑。

首先是代码分割，比如路由级别使用懒加载：

const User = lazy(() => import('./User'));

这样用户访问首页的时候不需要一次性加载所有页面代码。

其次是 Tree Shaking，尽量使用支持 ESM 的依赖，并避免无必要的全量引入。

然后是资源压缩，比如 JS、CSS 压缩，图片压缩。

另外还会关注第三方依赖，如果发现某个依赖体积比较大，我会考虑是否可以替换成更轻量的方案。

最后会通过构建产物分析工具查看 Bundle，到底是哪些依赖占用了大量体积。

7. 移动端 H5 如何保证不同尺寸和分辨率设备体验？

面试回答

移动端 H5 我一般会从布局、尺寸适配、图片、交互和兼容性几个方面考虑。

首先布局尽量使用响应式方案，比如 Flex、Grid、百分比、vw/vh 等，避免大量固定像素。

对于字体和间距等尺寸，可以根据设计方案选择 rem 或 vw 进行适配。

图片要根据设备尺寸进行适配，避免低分辨率设备加载过大的图片。

另外还要考虑：

  • viewport 配置
  • iOS 安全区域
  • 刘海屏
  • 横竖屏
  • 软键盘弹出
  • 点击区域大小
  • 不同浏览器兼容性

比如底部固定导航，就需要考虑：

padding-bottom: env(safe-area-inset-bottom);

避免内容被 iPhone 的 Home Indicator 遮挡。

所以我的思路不是针对某一个设备单独写 CSS，而是尽量建立响应式布局 + 统一适配方案。

8. 如何看待 TypeScript 的价值？

面试回答

我认为 TypeScript 最大的价值是：

把很多运行时才能发现的问题提前到开发阶段发现。

尤其是在中大型项目中，组件之间、前后端接口之间的数据结构比较复杂，如果全部依赖 JavaScript，很容易因为参数类型或者字段错误产生问题。

TS 可以通过接口和类型定义明确数据结构，比如：

interface User {
  id: number;
  name: string;
}

这样在开发阶段 IDE 就能提供类型提示和错误检查。

另外 TS 对重构也比较友好，比如修改一个接口字段时，可以通过类型检查快速找到受到影响的代码。

追问：TS 有什么缺点？

回答：

第一是学习成本，需要理解泛型、联合类型、类型推导等概念。

第二是会增加一定的开发成本，需要维护类型定义。

第三是 TypeScript 类型主要存在于编译阶段，运行时还是 JavaScript，所以不能完全替代运行时的数据校验。

因此我认为 TS 的价值在中大型项目里比较明显，但也要避免为了类型而类型，类型设计应该服务于业务。

9. 请谈谈你对前端测试的理解。

面试回答

我理解前端测试主要是为了保证代码修改之后，原来的功能不会被意外破坏。

我一般会把测试分成几个层次：

第一层：单元测试

针对一个函数或者比较独立的组件进行测试。

比如：

输入数据 → 函数 → 输出结果

第二层：组件测试

比如测试一个 React 组件：

  • 是否正确渲染
  • 点击按钮后状态是否改变
  • 输入框输入内容后是否正确
  • 接口返回数据后是否展示正确

第三层：E2E 测试

模拟真实用户操作。

比如：

打开页面
→ 登录
→ 搜索酒店
→ 点击某个酒店
→ 查看详情

对于 React 项目，我比较常见的组合会是：

Vitest/Jest + React Testing Library

组件测试的时候，我更关注用户行为和最终结果，而不是测试组件内部具体调用了哪个函数。

例如不要过度测试：

useState 被调用了几次

而应该测试：

点击按钮之后页面是否显示正确结果

这样测试对实现细节依赖更小，后续重构组件也不容易导致大量测试失效。

10. 为什么选择前端开发？平时怎么跟进前端技术？

这个问题属于必问的自我认知题。

不要回答：

“因为我喜欢写代码。”

太空泛。

面试回答

我选择前端主要有两个原因。

第一，我比较喜欢能够直接看到开发结果的工作。

前端开发的特点是从需求、交互到最终页面都能够比较直观地看到结果，这个反馈过程让我比较有成就感。

第二，我觉得前端本身是一个需要持续学习的方向。

从最开始的 HTML、CSS、JavaScript，到 React、Vue、TypeScript，再到现在 AI 应用和前端工程化，前端技术变化比较快，我比较喜欢这种持续学习和解决问题的过程。

我平时主要通过几个方式跟进技术：

一是看官方文档，比如 React、Vue、TypeScript 等官方文档；

二是通过 GitHub、技术社区关注实际项目和开源方案；

三是通过技术文章和视频了解别人解决问题的思路；

但我比较重视的一点是：

不会单纯为了追新技术而学习，而是遇到实际问题的时候，再去深入研究对应的技术。

比如之前项目中遇到 SSE 多标签页连接复用的问题，我就进一步研究了浏览器连接限制以及 BroadcastChannel，最后设计了多标签页之间复用连接的方案。

「面试回答套路」

这 10 道题其实可以归纳成一个固定模板。

面试官问：

“你怎么优化 XXX？”

你可以：

① 先说总体思路

我一般会从 A、B、C、D 几个方面考虑。

② 具体展开 2～3 个重点

首先是……

其次是……

最后是……

③ 讲项目经历

我之前在 XX 项目中也遇到过类似问题，当时……

④ 最后总结原则

所以我的思路是先定位问题，再针对瓶颈进行优化，而不是直接套用某一种技术。

比如第一题，你不要背成几十个性能优化知识点。

你只需要记住：

网络 → 数据 → 渲染 → 体验 → 工具定位

然后现场展开。
