## 一、HTML / CSS 基础（成都犇犇整组）

### Q1：CSS 盒模型 ✍️

盒模型描述元素占位 = content + padding + border + margin 四层盒子。两种计算方式由 `box-sizing` 决定：**content-box**（默认）width 只含内容区，加 padding/border 后实际尺寸会"变大"；**border-box** 的 width 包含 content+padding+border，设置多少就是多少。实际项目里全局 `* { box-sizing: border-box }` 更符合直觉，算布局不容易错。调试时在 DevTools 的 Computed 面板能直接看到每层尺寸。

### Q2：CSS 实现垂直居中 ✍️

按场景选：
1. **flex（首选）**：父元素 `display:flex; justify-content:center; align-items:center`，一行搞定，适合绝大多数场景；
2. **grid**：`place-items: center`，更简洁，浏览器支持已足够好；
3. **绝对定位 + transform**：子元素 `position:absolute; top:50%; left:50%; transform:translate(-50%,-50%)`，优点是不需要知道子元素宽高；
4. **绝对定位 + margin:auto**：子元素四边设 0 + `margin:auto`，适合有固定宽高的弹窗；
5. 文本单行垂直居中用 `line-height` 等于高度，图片对齐可用 `vertical-align`。
追问延伸：flex 布局里 `margin:auto` 也能吸收剩余空间实现居中；grid 的 `place-content` 与 `place-items` 的区别（前者管轨道整体、后者管单元格内部）。

### Q3：CSS 优先级 ✍️

从高到低：**`!important` > 内联 style > ID 选择器 > 类/属性/伪类选择器 > 元素/伪元素选择器**（通配符 `*` 不计权重）。复合选择器按 (ID 数, 类数, 元素数) 逐级比较，先比 ID 再比类；同权重时**后写的覆盖先写的**（层叠规则）。`!important` 会破坏正常层叠，只建议覆盖第三方库样式时用。继承来的样式（如 color）优先级低于任何直接命中规则。

### Q4：行内元素、块级元素、行内块元素的区别 ✍️

- **块级**（div/p/ul/h1）：独占一行，可设宽高和四个方向 margin/padding，默认宽度撑满父容器；
- **行内**（span/a/strong）：不换行、**设置 width/height 无效**，上下 margin 无效、上下 padding 只显示不占布局空间，宽高由内容决定；
- **行内块**（img/input/button）：像行内一样并排排列，但像块级一样可设宽高。
三者通过 `display` 互相转换。经典坑：行内块元素之间因 HTML 换行符产生**空白间隙**，解法是父元素 `font-size:0` 或标签写在一行/用 flex 布局替代。

### Q5：什么是语义化标签 ✍️

用有含义的标签组织页面结构：`header/nav/main/article/section/aside/footer` 等，替代一堆无意义 div。价值三点：①**可读性与可维护性**，结构一目了然；② **SEO**，搜索引擎能识别页面结构权重；③**无障碍**，屏幕阅读器依赖语义导航。原则是"先看内容含义再选标签"，而不是全部 div + class。可以补一句：语义化配合 CSS 选择器和组件化，是维护大型页面样式不失控的基础。

## 二、JavaScript 核心

### Q1：var、let、const 的区别（成都犇犇）✍️

三个维度：
1. **作用域**：var 是函数作用域；let/const 是块级作用域（{} 内有效）；
2. **提升行为**：var 声明提升且初始化为 undefined，声明前访问不报错；let/const 也有提升但处于**暂时性死区（TDZ）**——声明前访问直接 ReferenceError，这个设计就是用来暴露错误使用的；
3. **重复声明与赋值**：var 可重复声明；let/const 同作用域不可重复声明；const 声明时必须初始化，且**绑定不可重新赋值**——但对象类型的内容仍可修改（`const arr = []; arr.push(1)` 合法），冻结内容要 `Object.freeze`。
实践默认：全用 const，需要重新赋值才用 let，var 不再使用。

### Q2：箭头函数与普通函数的区别？什么时候"只能"用箭头函数？（成都犇犇 / 心野引行）✍️

**区别四点：**
1. **this**：普通函数 this 在调用时确定（谁调用指向谁）；箭头函数**定义时继承外层词法 this**，call/apply/bind 都改不了；
2. 没有 `arguments`（可用剩余参数 `...args` 替代）；
3. **不能作为构造函数**（没有 prototype、没有 [[Construct]] 内部槽，new 会报错）；
4. 不能用作 generator（不能写 yield）。

**"只能用箭头函数"的场景**其实是：回调中必须沿用外层 this 时——最典型的是**类/对象方法内部的异步回调**（setTimeout、请求回调里还要用 this.xxx），箭头函数是最直接方案；React 的函数组件里不存在 this 问题，但事件外的回调同样受益。反向更要记牢——**不能用箭头函数**：构造函数、对象字面量方法（this 不会指向对象）、需要动态 this 的场景（DOM 事件处理器想拿元素）。

**bind 的 this 题要点（心野引行）**：`fn.bind(a)` 返回新函数不立即执行；bind 后 this 永久绑定为 a，**再次 bind 无效，call/apply 也改不动**（"一 bind 定终身"）；唯一例外是 `new`——new 调用时 this 指向新实例。连续 `fn.bind(a).bind(b)`，this 以第一次 bind 为准。

### Q3：apply、call、bind 的区别（MetaApp AI 面）✍️

三者都是显式指定函数的 this：**call** 逐个传参、立即执行；**apply** 用数组传参、立即执行；**bind** 不执行，返回一个永久绑定 this 的新函数（可预设部分参数——柯里化）。手写思路能加分：call 的核心是 `context.fn = this; context.fn(...args); delete context.fn`，注意处理 null（指向全局对象）和返回值。使用场景：类数组借数组方法（`Array.prototype.slice.call(arguments)`）、继承（子类构造里 `Parent.call(this)`）、事件回调固定 this。

### Q4：new 创建实例的时候做了什么？能用箭头函数吗？（MetaApp AI 面）✍️

**四步：**
1. 创建一个空对象；
2. 把空对象的 `__proto__` 指向构造函数的 `prototype`；
3. this 绑定到新对象上执行构造函数（属性方法挂到 this）；
4. 如果构造函数 return 了一个**对象**就返回它，否则返回新对象。

**箭头函数不能 new**——它没有 prototype 属性、没有 [[Construct]] 内部方法，`new` 直接抛 TypeError。手写 `myNew(fn, ...args)` 就是把上面四步翻译成代码，`Object.create(fn.prototype)` 完成原型链接。

### Q5：什么是 Promise？（成都犇犇）✍️

Promise 是异步编程的解决方案，本质是一个**承载未来结果的对象**。三个状态：pending → fulfilled / rejected，**一旦落定不可逆**。价值：①用链式调用 `.then().catch()` 替代回调地狱；②错误会沿链冒泡，一处 catch 兜底；③`.finally` 无论成败执行（关 loading）；④配合 async/await 用同步写法写异步。回调进入**微任务队列**，比宏任务（setTimeout）先执行。`then` 返回新 Promise 所以能链式，return 值会传给下一个 then，throw 则进入 rejected。

**delay 函数手写（心野引行追问）：**

```js
const delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// 使用：delay(1000).then(() => console.log('1秒后'));
// 配合 async/await: await delay(1000);
```

### Q6：Promise.all、allSettled、race 的区别（MetaApp 一面）✍️

- **all**：全部成功才 resolve（结果数组按传入顺序），**一个失败整体立即 reject**——适合"多个请求都要成功才渲染页面"；
- **allSettled**：等全部落定，返回每项的 `{status, value/reason}`，**永不 reject**——适合批量任务要异常隔离（我的慢 SQL 多文件批量分析就是靠它保证单文件失败不影响其他文件）；
- **race**：第一个落定的决定结果，无论成败——典型用途是**超时控制**（race 一个 setTimeout 的 reject）；
- 补充 **any**：第一个成功的 resolve，全失败才 reject。

### Q7：async/await 用得多吗？在什么地方用？（心野引行）✍️

async/await 是 Promise 的语法糖（Generator + 自动执行器），本质是把 then 链写成同步形态。典型使用场景：**多个接口有依赖的串联调用**（先拿服务器组 id 再建监听器）、需要中间判断的流程（拿结果决定走哪个分支）、重试逻辑。要点：①await 只能用在 async 函数内（顶层 await 限 module），等的是 thenable；②**错误必须 try/catch**，否则 unhandledrejection；③注意循环语义——`for...of + await` 是串行，`map + Promise.all` 才是并行，高频踩坑点。

### Q8：事件冒泡与事件委托；A 嵌 B、B 嵌 C，给 A 添加监听器，点击 C 触发顺序？（成都犇犇 / MetaApp AI 面）✍️

事件流三个阶段：**捕获（document → 目标）→ 目标阶段 → 冒泡（目标 → document）**，默认监听器挂在冒泡阶段。嵌套题：只给 A 加了监听器，点击 C 时事件从 C 一路冒泡到 A，**A 的监听器触发一次**，此时 `event.target` 是 C（实际点击的元素）、`event.currentTarget` 是 A（绑定监听的元素）。若 A/B/C 都加默认监听器，触发顺序是 C → B → A（由内向外）。

**事件委托**就是利用冒泡：把子元素的事件统一绑在父元素上，通过 `e.target` 判断来源。好处：①动态添加的子元素自动生效；②N 个列表项只需 1 个监听器，省内存。这就是"给 A 加监听器管理所有子孙点击"的标准姿势，也是 React 合成事件系统的基础。

### Q9：addEventListener 的参数有哪些？（MetaApp AI 面）✍️

`addEventListener(type, listener, options)`，第三个参数可以是布尔（useCapture，true 为捕获阶段触发）或对象：
- `capture`：捕获阶段触发；
- `once`：触发一次后自动移除（引导弹窗类场景）；
- `passive`：承诺不在回调里 preventDefault，**滚动性能优化利器**（浏览器不用等回调就能滚动）；
- `signal`：传 AbortController 的 signal，调用 `controller.abort()` 一键移除（管理大量监听器/组件卸载清理）。
细节：同类型 + 同函数 + 同配置重复注册只会生效一次；`removeEventListener` 必须传同一个函数引用，所以匿名函数移除不掉。

### Q10：深拷贝和浅拷贝（成都犇犇）✍️

- **浅拷贝**：复制第一层，嵌套对象仍共享引用——`Object.assign`、展开运算符 `...`、数组 `slice`；
- **深拷贝**：所有层级都复制成独立副本。
- 实现方式与缺陷：`JSON.parse(JSON.stringify())` 简单但**丢函数/undefined/Symbol、Date 变字符串、循环引用直接报错**；`structuredClone()`（原生 API）解决循环引用和多数类型但仍不支持函数；面试手写递归版本要点：递归 + 类型分派（数组/对象/Date/RegExp）+ **WeakMap 记录已拷贝对象解循环引用**。
- 应用：Redux 不可变更新用浅拷贝够（展开一层），真正需要隔离修改时才深拷贝。

### Q11：哪些会导致内存泄漏？循环引用会造成内存泄漏吗？垃圾回收方法？（MetaApp AI 面）✍️

**垃圾回收两种主流算法：**
1. **标记-清除**（现代引擎主流）：从根（全局对象、当前调用栈）出发做**可达性分析**，不可达的对象回收；
2. **引用计数**（老 IE 时代）：引用数为 0 才回收。

**循环引用会造成泄漏吗？——关键考点**：在引用计数下**会**（互相引用永不归零，IE 内存泄漏经典）；但现代标记-清除做的是可达性分析，**纯粹的循环引用不可达就会被回收，不是泄漏主因**。真正的泄漏清单：①意外的全局变量；②**未清理的 setInterval/setTimeout 和事件监听器**（回调持有 DOM 或大对象）；③**闭包长期持有大对象**；④脱离文档的 detached DOM 节点被 JS 引用；⑤console.log 持有对象（某些场景）。排查：DevTools 的 Memory 面板打堆快照对比、Performance Monitor 看 JS Heap Size 曲线。可以结合自己项目：SSE 连接、定时器统一在 useEffect cleanup 里清理，就是防泄漏实践。

### Q12：ES6 新特性（商汤）✍️

分组答：**语法层**——let/const、箭头函数、解构赋值、模板字符串、默认参数、剩余/扩展运算符；**面向对象**——class（原型语法糖）；**异步**——Promise、Generator；**模块化**——ESM（import/export 静态分析，Tree Shaking 的基础）；**数据结构与元编程**——Map/Set、Symbol（唯一键）、Iterator 协议、Proxy/Reflect（Vue3 响应式的基石）；再补两个 ES2020+ 高频：**可选链 `?.`** 和**空值合并 `??`**。答题策略：报菜名 + 挑一两个往深讲（Proxy 讲到 Vue3 响应式是最好串联）。

### Q13：打印结果题——var 循环 + setTimeout，怎么打印 0,1,2,3？（商汤）✍️

```js
for (var i = 0; i < 4; i++) {
  setTimeout(() => console.log(i)); // 输出 4 4 4 4
}
```

**原因**：var 是函数作用域，整个循环共享一个 i；setTimeout 回调是宏任务，主线程（循环）执行完才跑，此时 i 已是 4。
**三种修复：**
1. **把 var 改成 let**（最优）：let 块级作用域，**每次迭代创建一个新的 i 绑定**，回调闭包捕获各自的 i；
2. **IIFE 闭包**：`for (var i...) { ((j) => setTimeout(() => console.log(j)))(i) }`——用立即执行函数把 i 按值捕获进参数 j；
3. **setTimeout 第三个参数**：`setTimeout((j) => console.log(j), 0, i)`，额外参数会传给回调。
这题同时考 var/let、闭包、事件循环三个知识点，答完主动讲清"为什么"比只给修复方式加分。

### Q14：数组扁平化怎么做？（商汤）✍️

```js
// 法一：原生 API
arr.flat(Infinity);

// 法二：递归 + reduce（手写常考）
const flatten = (arr) =>
  arr.reduce((acc, cur) =>
    acc.concat(Array.isArray(cur) ? flatten(cur) : cur), []);

// 法三：迭代（栈，避免深递归爆栈）
const stack = [...arr]; const res = [];
while (stack.length) {
  const next = stack.pop();
  Array.isArray(next) ? stack.push(...next) : res.push(next);
}
```

延伸：带 depth 参数的版本（flat 支持指定层数）、对象扁平化（key 变路径）看面试官追问方向。

## 三、Vue 框架

### Q1：Vue2 和 Vue3 的区别（园测 / 盛趣 / 犇犇 / 合肥智慧）📌

四个维度：
1. **响应式系统**：Vue2 用 `Object.defineProperty`，监听不到**新增/删除属性**（要 $set/$delete）和**数组下标修改**，且初始化要递归遍历所有层级；Vue3 换 **Proxy**，全都能监听，而且是惰性深层代理（访问到才递归），性能和开发体验都更好；
2. **API 风格**：Options API（data/methods 分散写）→ **Composition API**（setup 里按功能组织逻辑），核心收益是**逻辑复用**——把一坨相关逻辑抽成 composable 函数，替代 Vue2 的 mixin（mixin 有命名冲突、来源不明的老问题）；
3. **TS 支持**：Vue3 用 TS 重写，this 类型推断、defineProps 泛型都好很多；
4. **性能**：编译期优化——静态节点提升（hoistStatic）、PatchFlag 标记动态部分（diff 只比对动态节点）、按需引入让包更小；生态上 Element UI → Element Plus、Vuex → Pinia。
追问"Vue2 能开发吗、有壁垒吗"：能上手（API 心智模型一致），主要踩坑点在响应式差异（Vue2 的数组/新增属性问题）和 mixin 复用方式。

### Q2：Vue2/Vue3 生命周期及区别？接口调用放哪个生命周期？（园测 / 合肥智慧）✍️

**Vue2**：beforeCreate → created → beforeMount → **mounted** → beforeUpdate → updated → beforeDestroy → destroyed。
**Vue3**：setup（在 beforeCreate 之前执行）→ onBeforeMount → onMounted → onBeforeUpdate → onUpdated → onBeforeUnmount → onUnmounted。对应关系：destroyed 系列改名 unmount 系列。

**接口调用放哪**：一般放 **onMounted**——此时 DOM 已挂载，请求回来直接操作 DOM（初始化 ECharts、滚动定位）也安全。纯取数据其实在 setup 顶层（相当于 created 时机）发也行，甚至更早拿到数据；但**团队统一放 onMounted 最省心**，不用纠结数据回来时 DOM 在不在。注意点：SSR 场景没有 mounted，取数要放 created/setup；Vue3 里 setup 是同步的，异步逻辑用 async setup 要配 Suspense，一般不这么写，直接在 onMounted 里 async。

### Q3：组件通信方式有哪些（园测 / 盛趣 / 犇犇 / 心野 / 合肥智慧）📌

按层级分：
1. **父子**：props 向下、emit 向上；`v-model` 是这两者的语法糖；
2. **跨层级**：provide / inject（主题、表单上下文往下透传）；
3. **兄弟**：状态提升到共同父组件，或直接进状态管理；
4. **全局共享**：Pinia；
5. **辅助手段**：`$refs` 直接调子组件方法、`$attrs` 透传未声明属性、作用域插槽（子组件把数据反向传给父组件模板）、`expose` 控制子组件暴露内容（Vue3）。
Vue2 还特有的：`$children`、`$listeners`、EventBus；Vue3 的 EventBus 要自己装 mitt，**不推荐**（来源不明难维护）。跨页面：路由 query/params、页面返回用 onShow 重拉数据或 eventChannel。

### Q4：v-if 和 v-show 的区别？uniapp 中的注意点（盛趣 / 敦煌 / 犇犇）📌

- **v-if 是真条件渲染**：条件为假节点不创建，切换 = 销毁重建，有切换开销但惰性好（初始为假就零渲染）；
- **v-show 一定渲染节点**，只切 `display: none`，切换成本低但有初始渲染开销。
- **选择**：频繁切换用 v-show；条件很少变、或初始大概率不显示的用 v-if。
- 两个细节：①v-if 和 v-for 不要写同一元素（Vue3 中 v-if 优先级更高，拿不到循环变量）；②**uniapp/小程序端**：v-show 编译成 `hidden` 属性，**套在自定义组件上可能不生效**，此时改用 v-if 或外包一层 view。

### Q5：v-for 为什么要用 key？为什么不建议用 index？（敦煌 / 犇犇）📌

key 是节点的**身份标识**，diff 时靠它判断"哪个节点是原来的哪个"，从而**复用而不是重建**。用 index 当 key 的问题：列表一旦**插入、删除、排序**，index 整体错位，框架会复用错误的节点——表现为输入框内容串行、勾选状态错乱、动画异常。所以要用**唯一且稳定的业务 id**；用随机数也不行——每次渲染都变，等于完全放弃复用。React 里同理（我的 React 项目同样遵守）。

### Q6：watch 和 computed 的区别（成都犇犇）✍️

- **computed**：**派生值**——从已有响应式数据算出新数据，**有缓存**（依赖不变不重算）、必须有返回值、不能写异步；适合"fullName 由 first+last 算出"、"过滤后的列表"；
- **watch**：**侦听变化执行副作用**——数据变了要发请求、操作 DOM、写本地存储时用；支持 deep（深层监听）、immediate（立即执行一次）、flush 时机；
- 一句话：**要"值"用 computed，要"做事"用 watch**。高频追问：watchEffect 是"自动收集依赖的 watch"，回调里用了什么就自动侦听什么，适合依赖多个数据的副作用。

### Q7：ref 和 reactive 的区别（云栖处）📌

- ref：把值包成带 `.value` 的响应式对象，**任意类型**都能装，基本类型只能用它；模板里自动解包不用写 .value；
- reactive：只接对象/数组，不用 .value 直接访问；两个坑——**解构会丢响应式**（要配 toRefs），**整个替换对象会断响应式**（要用 Object.assign 或改字段）。
实践惯例：**统一用 ref 省心**，需要拆解传参时配 toRefs。底层：ref 底层也是通过一个带 getter/setter 的 RefImpl 实现，对象类型的 ref 内部还是调 reactive。

### Q8：setup 的执行时机？里面能用 this 吗？（云栖处）📌

setup 是组合式 API 的入口，**在 beforeCreate 之前执行**，每个组件实例只跑一次。此时**组件实例还没创建，this 是 undefined**——后面才有的 data、methods 都不存在。要 props 从第一个参数拿，emit/slots/attrs 从第二个参数 context 拿。实在需要组件实例可以 `getCurrentInstance()`，但不推荐（脱离组合式的设计意图）。

### Q9：Vue 模板编译成 JS 的过程（心野引行）✍️

三步：
1. **parse 解析**：template 字符串 → **AST**（抽象语法树，描述标签/属性/指令的树结构）；
2. **transform 转换**：遍历 AST 做处理——指令转抽象节点、事件绑定收集，**Vue3 在这里做编译优化：静态提升**（静态节点提取到 render 外只创建一次）和 **PatchFlag**（给动态节点打标记，diff 时只比对标记的部分）；
3. **generate 生成**：AST → 渲染函数代码字符串。
运行时执行 render 函数生成 vnode，再 patch 到真实 DOM。这也是 Vue3 性能优于 Vue2 的根源——**把能在编译期做的优化都提前做掉**（React 没有编译期优化这一层，靠运行时 Fiber 调度，这正好接上"React vs Vue"对比题）。

### Q10：v-model 的实现方式？原生手写怎么实现？（心野引行）✍️

本质是**语法糖**：`<Child v-model="x" />` 等价于 `:modelValue="x"` + `@update:modelValue="v => x = v"`。
**手写组件侧**：

```vue
<!-- 父组件 -->
<Child :modelValue="x" @update:modelValue="val => x = val" />

<!-- 子组件 -->
<script setup>
const props = defineProps(['modelValue'])
const emit = defineEmits(['update:modelValue'])
const onInput = (e) => emit('update:modelValue', e.target.value)
</script>
```

Vue 3.4+ 提供 `defineModel()` 宏一步到位（内部同样是 props + emit）。原生 input 的 v-model 则是 `:value` + `@input`（Vue2 是 value/input，checkbox 是 checked/change）。修饰符：`.lazy`（change 才同步）、`.number`（转数字）、`.trim`；支持多个 v-model（`v-model:title`）。

### Q11：Pinia 的使用场景？怎么创建？页面刷新后数据还在吗？（飞致云 / 心野）📌

**定位**：Vue 官方状态管理库，本质是**全局响应式仓库**——跨组件、跨页面共享的数据统一管理，一处修改全局自动更新。
**适合放**：多个组件共用、生命周期长、需要同步读写、带异步或派生逻辑的数据——用户/token/权限、全局主题、多 Tab 共享列表、WebSocket 推送的数据。**不适合**：单组件临态、弹窗开关。
**创建（组合式）**：

```ts
export const useUserStore = defineStore('user', () => {
  const token = ref('')
  const permissions = ref<string[]>([])
  const setPerms = (list: string[]) => (permissions.value = list)
  return { token, permissions, setPerms }
})
```

组件内 `const store = useUserStore()`，解构要 `storeToRefs` 保持响应式。选 Pinia 而不是 Vuex：无 mutation、TS 支持好、天然模块化。

**刷新后还在吗？**——不在。Pinia 状态在内存里，刷新整个 JS 环境重建、状态重置。解决：**别把 Pinia 当持久化存储**——token 存 localStorage，刷新后路由守卫发现"有 token 但没权限"，重新拉用户信息接口，存回 Pinia、重建动态路由再放行，用户无感知。另一个方案是持久化插件（pinia-plugin-persistedstate）把权限也存本地，省一次请求但**权限可能过期**（管理员改了权限前端还是旧的），要配版本号/过期兜底。**最佳实践：只持久化凭证（token），权限每次刷新用凭证重新换。**（这正是我在流量调度平台 RBAC 里的做法）

### Q12：Vue3 中如何避免不必要的渲染？（云栖处）📌

六个手段：①**computed 缓存**派生数据，避免模板里重复计算；②大对象和**图表实例用 shallowRef / markRaw**（ECharts 实例没必要做成深层响应式，响应式遍历开销大）；③**组件拆分**让 props 变化范围最小（状态下沉，谁用谁持有）；④列表用**稳定 key** 帮助 diff 精确复用；⑤数据不变的大列表用 **v-memo**；⑥超长列表**虚拟滚动**。本质都是让"数据变化 → 触发更新的组件范围"尽可能小。

### Q13：KeepAlive 的实现思路（飞致云）⚠️📌

原题绑定他人项目（长任务导入页），按通用场景答：
**作用**：缓存组件实例——切走时不销毁、切回时不重建，保留状态和 DOM。原理是在外层包一个抽象组件，内部维护 `key → vnode 缓存`，切换时不是 unmount 而是搬进缓存容器（deactivate），切回再搬回来（activate），所以组件状态、滚动位置都在。
**使用**：路由 meta 标 keepAlive → router-view 外套 `<keep-alive :include="[...]">`；`max` 限制缓存数量（LRU 淘汰）。配套生命周期 **onActivated / onDeactivated** 代替 mounted/unmounted 做恢复/暂停（比如暂停轮询、恢复时拉一次最新状态）。
**两个坑**：①include 匹配的是**组件 name**，setup 语法糖要用 `defineOptions({ name: 'Xxx' })` 显式声明，否则**静默不生效**；②KeepAlive 只是内存缓存，**刷新页面就没了**——要配合 localStorage 持久化关键状态才能恢复。
我自己的场景设想（如面试官追问"你项目哪里能用"）：智能体平台工作流编辑页，用户切到别的页面再回来，画布缩放、未保存修改都能保留。

### Q14：自定义指令 v-permission 实现按钮级权限（MetaApp 一面 / 引力琥珀 / 飞致云）📌

**实现**：注册全局自定义指令，在 `mounted` 钩子里拿 `binding.value`（按钮声明的权限码），去 Pinia 权限 store 里匹配——匹配不上就 `el.parentNode.removeChild(el)` **直接删节点**（不是 display 隐藏，隐藏能在控制台改回来）。逻辑判断处（如 if 分支里）复用同一个 `hasPermission()` 函数，保持一套判断逻辑。

```ts
app.directive('permission', {
  mounted(el: HTMLElement, binding) {
    const store = useUserStore()
    if (!store.permissions.includes(binding.value)) {
      el.parentNode?.removeChild(el)
    }
  }
})
// 使用：<el-button v-permission="'user:delete'">删除</el-button>
```

**权限数据存哪**：按钮上的权限码是**前端代码里的声明**（表示这个按钮需要什么权限）；用户**实际拥有**的权限码来自后端接口下发，存在 Pinia 内存，刷新重拉重算，不缓存结果。
**边界（必说）**：前端权限只是**体验层**——不显示、不误点；真正的安全兜底在后端接口级校验（否则直接调接口就绕过了）。

### Q15：Vue 中组件与实例是一一对应吗？多组件共用一个实例（单例）能提升性能吗？（MetaApp 一面）✍️

**不是一一对应**——组件是"定义"（一个对象/函数，可以复用），**实例是每次挂载时创建的运行时对象**：同一个组件定义渲染 10 次就有 10 个实例（各自独立的 state、生命周期）。`<item v-for="i in 10">` 里每个 item 都有自己的实例。

**"共用一个实例"要拆开说**：组件实例本身没法共用（挂载点上各自独立），能做单例的是**状态**——模块级单例：Pinia store 本质就是"整个应用一份"的模块级状态；Vue2 时代 mixin/模块作用域对象也能做。能不能带来性能提升：**省内存**是真的（一份状态、一份订阅），但要小心**更新范围反而变大**——共享状态一变，所有依赖它的组件都触发更新，相当于把精确的局部更新变成全局广播，未必更快。另外图表库实例（ECharts）、WebSocket 连接这类**非响应式重资源**很适合单例（一个应用一个连接、一个图表实例复用），这才是性能提升的正确打开方式——配合 markRaw 避免被响应式系统代理。

### Q16：有没有自己封装过组件？（成都犇犇）✍️

结合自己项目答（准备 1~2 个能展开的）：
1. **工作流参数渲染组件 Parameter**（农担平台）：输入是参数配置对象，内部按 type 分发到 Input/Slider/Select/模型选择器等子组件——配置驱动的通用表单组件，新增节点类型基本零开发；
2. **分步向导容器**（流量调度平台）：el-steps + 动态步骤组件切换，统一管理跨步骤 model、每步校验、上一步回填；
3. 通用层：基于 Ant Design/Element Plus 二次封装的 ProTable（配置化列 + 搜索 + 分页）、搜索框抽离组件。
封装思路：**props 定契约、slot 留扩展、emits 上抛事件、不满足的场景用 expose 暴露方法**；能配置化的尽量配置化，复杂交互留给 slot。

## 四、React 与 TypeScript

### Q1：Vue 和 React 相比，React 有哪些相对优势？（引力琥珀）📌

公平地答（承认 Vue 的强处再讲 React 特点，反而显得客观）：
1. **运行时调度更灵活**：Vue 在编译期就决定哪些部分可以跳过更新，快但方式固定；React 在**运行时决定更新的优先级和打断**（Fiber 并发调度）——做"内容持续进来"的界面更顺，比如 **AI 边生成边显示的流式输出**，长任务可中断、不让输入卡住，这正是我实习做 LLM 流式界面的直接体会；
2. **纯 JS 描述 UI（JSX）+ TS**：类型推断和重构体验更顺；
3. **生态和跨端选择多**：React Native、Next.js 等。
同时承认 Vue 上手快、模板约束统一、编译优化到位——所以选型看团队和场景，我两个都写（简历两个项目正好一 React 一 Vue）。

### Q2：对 React Hooks 的理解（引力琥珀）📌

Hooks 让函数组件拥有状态和副作用能力。**本质**：React 靠**调用顺序**（链表）记住每个 hook 的状态——所以不能写在 if/循环里，顺序一错状态就串。最重要的心智模型：**useEffect 不是生命周期，是"和外部系统同步"的工具**——依赖数组声明"这段逻辑和哪些值同步"，依赖没写对就会重复执行或拿到旧值。最易错的两个点：①异步回调里的**闭包陷阱**（setState 后 state 在旧闭包里还是旧值——用函数式更新或 ref 存最新值）；②effect 清理函数防泄漏（连接、定时器、监听器）。

### Q3：有没有用过自定义 hooks？（MetaApp 一面）✍️

用过，场景就是"把一段有状态的逻辑抽出来复用"：
1. **useSSE / useEventStream**：封装流式连接的建立、消息追加、关闭清理、重复连接去重——组件只管消费消息；
2. **useRequest（或用 ahooks 的）**：请求发起点、loading/error 状态、防重复提交、竞态取消（AbortController）统一收口；
3. **usePermission**：权限判断逻辑的 hook 版（与 v-permission 指令同源判断）。
自定义 hook 的价值：**逻辑复用但不共享状态**（每次调用独立实例），比 mixin/全局函数干净；返回 `[state, api]` 的设计让消费方按需取。

### Q4：接口成功返回 data、失败返回 errorCode+message，TS 怎么安全区分？（引力琥珀）📌

用**可辨识联合（Discriminated Union）**：给两种结果各定一个形状，用同一个判别字段区分——

```ts
type ApiResult<T> =
  | { type: 'ok'; data: T }
  | { type: 'err'; code: number; message: string }

const res = await api() as ApiResult<User>
if (res.type === 'ok') {
  res.data.name       // ✅ TS 知道这里是成功分支
} else {
  res.code            // ✅ 失败分支只能取 code/message
}
```

判别字段也可以直接用业务码（`code === 0` 走 instanceof/narrowing）。工程上更进一步：在 **Axios 封装层统一剥壳**——拦截器里判断后要么 resolve 纯 data、要么 reject 统一错误，业务页面拿到的直接是数据，连判断都省了（两层层设计：类型层可辨识 + 封装层归一）。

## 五、网络 / 浏览器 / 安全（飞致云整组 + 合肥智慧）

### Q1：HTTP 是有状态吗？状态存在哪里？（飞致云）📌

**HTTP 是无状态的**——每个请求独立自包含，服务端处理完就不记得你是谁。所以"状态"不在协议里，是**我们自己在外层造的**：客户端用 Cookie/token 存凭证，服务端用 Session（Redis）存会话或用 JWT 验签，每个请求把凭证带上、服务端才能续上上下文——**本质是用无状态协议模拟有状态会话**。无状态的好处：请求可以分给任意一台机器处理，水平扩展和容错容易；代价：信息重复传、鉴权每次重做。细节加分：keep-alive 省的是 TCP 握手，那是**连接状态**不是**用户状态**，别混淆。

### Q2：怎么理解 Cookie？它的请求头长什么样？（飞致云）📌

Cookie 是浏览器按**域名**存的一小块键值对，服务端用 `Set-Cookie` 响应头下发，**同域请求浏览器自动带上**——这就是它的价值：服务端"认人"。传统 Session 靠它传 sessionId。请求头形态：`Cookie: sessionId=abc123; theme=dark`（name=value，分号分隔），由浏览器自动生成，不用手写；属性（Path/HttpOnly/Secure/SameSite）只出现在 Set-Cookie 里。风险与防护三件套：**HttpOnly**（JS 读不到，防 XSS 窃取）、**Secure**（仅 HTTPS）、**SameSite**（防 CSRF）。对比 JWT 的 `Authorization: Bearer xxx`——那个才是我们在拦截器里手动加的，多端（小程序/APP 没有 Cookie）统一用头更方便。

### Q3：怎么理解 Session 会话？（飞致云）📌

Session 就是**服务端存的一份"你登录过"的记录**：登录成功 → 服务端生成随机 sessionId → 用户信息存在服务端（通常 Redis）→ Cookie 把 sessionId 发给浏览器 → 之后每次请求浏览器自动带 → 服务端查到就知道你是谁。**sessionId 只是一把钥匙，身份数据在服务端。**
**Session vs JWT**（必追问）：Session 有状态、能主动踢人（删 Redis 记录即失效），但集群要共享存储、多端不友好；JWT 无状态、好扩展、多端通用，但**签出去就收不回来**（只能等过期或上黑名单）。选型：内部后台要管在线状态选 Session；前后端分离 + 多端选 JWT；两全就 JWT 带 jti（唯一 id）+ Redis 黑名单。

### Q4：登录后，下次请求后端怎么知道是谁？（飞致云）📌

两种主流：**Session 方案**（Cookie 自动带 sessionId，服务端查表）和 **JWT 方案**（token 存前端，Axios 请求拦截器统一加 `Authorization: Bearer xxx`，后端用密钥**验签**，签名通过说明没被篡改，直接从 payload 读 userId）。两者共同点：前端统一注入、后端统一解析、过期返回 401 前端统一跳登录。细节：JWT 的 payload 只是 Base64 **编码不是加密**，能被任何人解开看，不能放敏感信息。

### Q5：JWT 鉴权流程 + 双 Token 无感刷新（飞致云 / 合肥智慧 / 安徽智慧）📌

**基础流程**：登录成功 → 后端签发 JWT（payload 放 userId + 过期时间，密钥签名）→ 前端存储（Pinia + localStorage）→ 每次请求拦截器带上 → 后端依赖注入解 token、验签验过期 → 通过则放行。
**双 Token 设计**（解决"过期时用户正在用"的问题）：
- **access token** 短有效期（15~30 分钟），调业务接口用；**refresh token** 长有效期（天级），只用来换新 access；
- access 过期 → 后端返回 401 → 前端拦截器**自动**用 refresh 换新 access → **把刚才失败的请求重放** → 用户全程无感；
- 两个工程细节（必讲，体现真做过）：①**并发 401 只刷一次**——多个请求同时 401 时用标志位/锁，第一个触发刷新，其余排队等新 token 再重放（防刷新风暴）；②刷新接口本身 401 直接登出（防死循环）；③可以再进一步：前端**提前判断** access 剩余时间不足 5 分钟就主动刷新，避免撞 401。
- 服务端强制失效（踢人）：refresh token 轮换（每次刷新发新的、旧的作废）+ Redis 黑名单。

### Q6：TCP 和 HTTP 之间的关系（飞致云）📌

**分层关系**：HTTP 是应用层，TCP 是传输层，**HTTP 跑在 TCP 上面**。TCP 负责传输：三次握手建连接、确认重传、保证有序、流量/拥塞控制；HTTP 只管语义：方法、状态码、报文格式。类比：HTTP 是信的内容，TCP 是送信的快递。
延伸链（面试官常顺着问）：keep-alive 是一个 TCP 连接复用多个 HTTP 请求 → HTTP/1.1 的队头阻塞 → HTTP/2 二进制分帧 + 多路复用缓解 → HTTP/3 换 QUIC（UDP）；HTTPS 是在 HTTP 和 TCP 之间加了层 TLS。

### Q7：WebSocket 和 HTTP 的最大区别？为什么选 WebSocket？（飞致云 / 云栖处 / 合肥智慧）📌

**通信模式不同**：HTTP 是请求-响应，客户端不问服务端没法答，短连接、每次一坨头；WebSocket **握手一次（借 HTTP Upgrade 升级）建立长连接，之后全双工**——双方随时主动发消息，帧头只有几字节。WebSocket 是**长连接**。
**选型逻辑**：当**服务端有实时事件要主动推**时，HTTP 只能轮询——短轮询要么延迟高要么浪费请求，长轮询占连接；WebSocket 事件一发生就推，毫秒级延迟且无无效请求。适用：设备监控、门禁事件、聊天、协同。
**结合自己**（重要——我有真实对比经验）：设备管理平台的服务器状态推送用的是 **SSE**——因为它是**单向**推送场景，SSE 基于 HTTP 更轻、自带断线重连和 Last-Event-ID 续传；**只有需要双向实时（前端也要高频上行）才用 WebSocket**。"单向推用 SSE、双向才 WebSocket"这个选型结论面试官很认可。（主文档 1.4-Q7 有完整对比）

### Q8：WebSocket 多个请求同时触发会出什么问题？（云栖处）📌

四类问题：
1. **重复建连**：多个组件各自 new WebSocket → 连接数翻倍、同一条消息收多次、状态混乱。解决：**单例连接管理器 + 订阅模式**——全局一个连接，组件 subscribe/unsubscribe，**引用计数归零才真正关连接**；
2. **高频推送打爆渲染**：一秒几十条、每条都 setState 页面卡死。解决：条数上限 + **短时间消息防抖合批成一次渲染** + 视口外不渲染；
3. **请求响应无法对应**：同时发多个请求，回复可能乱序。解决：**消息带唯一 id（或 seq），收到回复按 id 匹配回调**；
4. **断线重连风暴**：断线后多个定时器同时重连。解决：标志位保证只有一个重连流程 + 指数退避；发送时连接没就绪就先进**发送队列**，open 后再发。

### Q9：WebSocket 断连怎么办？重连后数据丢失怎么办？（云栖处）📌

**断连检测**：心跳——客户端定时发 ping，超时没收到 pong 判定断开（TCP 半打开状态靠应用层心跳才能发现）。
**重连**：指数退避（1s/2s/4s...）+ 随机抖动（防止服务端重启后所有客户端同时冲进来），标志位防并发重连。
**丢数据兜底**（关键）：
1. **重连成功先拉一次全量快照接口把状态补齐**——最朴素也最可靠；
2. 更严谨：**消息带序号**，重连时上报最后收到的序号，服务端从断点补发；
3. 架构原则：**以拉为主、推为辅**——推送只通知"有变化"，数据靠拉取对账，丢了也能自愈。

### Q10：你封装 WebSocket 的代码逻辑和流程？前端怎么监听消息变化？（合肥智慧）✍️

**封装设计（连接管理器）**：

```ts
class WsManager {
  private ws: WebSocket | null = null
  private subscribers = new Map<string, Set<Function>>()  // 按消息类型订阅
  private pendingMsgs: any[] = []                          // 未连接时的发送队列
  private reconnecting = false
  connect()      // 建连 + onopen 清空发送队列 + 启动心跳
  send(type, payload, msgId)  // 带唯一 id，连接未就绪进队列
  on(type, cb): () => void    // 订阅某类消息，返回取消订阅函数
  private handleReconnect()   // 指数退避 + 拉快照对账
  close()        // 引用计数归零才真正关闭
}
```

要点：**单例**（一个应用一条连接）、**按消息类型分发**（订阅者集合）、**心跳 + 重连 + 序号对账**、组件卸载调用返回的取消订阅函数。
**前端监听**：组件里 `ws.on('deviceStatus', cb)` 订阅，回调里更新 **Pinia/Redux 的 store**——因为 store 是响应式的，**视图自动更新**，不需要手动操作 DOM；Vue 里也可以 watch store 里的数据做二次反应。消息分类处理（状态类直接进 store、告警类走通知）+ 合批节流防止高频卡顿。

### Q11：跨 Tab / 多标签页数据怎么联动？（云栖处 ×2）📌

先分清两个层次：
**① 页面内多个 Tab 组件之间**：Tab 是兄弟组件，props 要绕父组件——直接用 **Pinia 模块级共享**：仪器列表、筛选条件放 store，每个 Tab 读写同一份响应式数据，一处改全部自动更新；请求统一放 action 避免重复发。
**② 浏览器多个标签页之间**（四种手段按序答）：
1. **BroadcastChannel（首选）**：原生广播频道，同源标签页订阅同一频道，API 简单、能直接传对象；
2. **localStorage + storage 事件**：兼容性极好、顺便持久化，但**写入的那个页面自己不触发**、只能传字符串；
3. **SharedWorker**：多页连同一个 Worker 中转，能集中管理状态，但写法复杂、移动端支持差；
4. **服务端中转**：各标签页连 WebSocket，一页改动上报、服务端广播——**能跨设备**，不只是跨标签页。
**结合自己**：我在设备管理平台做过**基于 BroadcastChannel 的 SSE 多标签页连接复用**——主标签页选举持有唯一 SSE 连接、消息广播给其他页，N 条长连接降为 1 条（主文档 4.3 有完整方案，这是我的强项题，遇到要主动展开）。

### Q12：XSS 了解吗？怎么规避？（合肥智慧）✍️

**XSS（跨站脚本）**：攻击者把恶意脚本注入页面，在其他用户的浏览器执行——分**存储型**（提交的内容存库后渲染给所有人，如评论区插脚本）、**反射型**（恶意脚本在 URL 参数里被回显）、**DOM 型**（前端代码把不可信数据写进 innerHTML）。
**规避**：
1. **输出转义**：HTML 实体转义 < > &；现代框架（Vue/React 插值表达式）**默认转义**，天然防大部分 XSS；
2. **管住 v-html / dangerouslySetInnerHTML**：这是框架里的口子——富文本内容必须先过 **DOMPurify 白名单消毒**再渲染；
3. **HttpOnly Cookie**：脚本读不到 token；
4. **CSP**（Content-Security-Policy）：限制脚本来源，禁 inline script；
5. 不把用户输入拼进 URL 的 javascript: 位置；URL 参数回显场景统一 encode。

### Q13：CSRF 了解吗？怎么规避？（合肥智慧）✍️

**CSRF（跨站请求伪造）**：利用浏览器**自动带 Cookie** 的特性——用户登录着 A 站，访问恶意 B 站，B 站偷偷向 A 站发请求（表单/图片地址），浏览器自动带上 A 的 Cookie，服务端误认为是用户本人操作。
**与 XSS 的区别**：XSS 是"在你的页面里执行脚本"，CSRF 是"借你的身份发请求"（不需要拿到密码，也不执行脚本）。
**规避**：
1. **SameSite Cookie**（Lax/Strict）：跨站请求不带 Cookie，现代浏览器默认 Lax，防掉大部分 CSRF；
2. **CSRF Token**：服务端下发一次性 token，写请求必须带上且服务端校验（B 站拿不到这个 token）；
3. **JWT 放 Authorization 头**（我的项目方案）：不走 Cookie 自动携带，跨站请求根本带不了凭证，天然免疫 CSRF——但代价是要防 XSS 偷 token，所以两头权衡；
4. 校验 Origin/Referer 来源；敏感操作二次验证（验证码/密码）。

## 六、工程化与部署

### Q1：Vite 和 Webpack 的区别（成都犇犇）✍️

**开发体验差异是核心**：Webpack dev 模式要**先全量打包**再起服务，项目越大启动越慢；Vite 开发环境**不打包**——利用浏览器原生 ESM，请求到哪个模块才**按需编译**哪个（esbuild 预构建依赖，Go 写的，快几个数量级），所以启动毫秒级、冷启动不随项目变大；HMR 也是模块级精确更新。
**生产构建**：Vite 用 **Rollup**（生态成熟、产物干净），Webpack 体系更老、插件生态最全。
**选择**：新项目默认 Vite；老项目或依赖特殊 Webpack 插件链（Module Federation 等）留 Webpack。共同点：都需要处理 alias、环境变量、代码分割、按需引入。
细节加分：Vite 的 `import.meta.env` 环境变量是**构建期静态替换**编译进产物的（我的 Docker 部署方案就利用了这点，见主文档 4.4-Q3）。

### Q2：Node 版本如何切换？一般用什么版本？（盛趣）✍️

**切换工具**：**nvm**（Linux/Mac）/ **nvm-windows**（Windows）——`nvm install 20`、`nvm use 20`、`nvm ls`；同类还有 volta（自动按项目切）、fnm（快，Rust 写的）。项目里用 **`.nvmrc` 文件**声明版本，进目录自动切；`package.json` 的 `engines` 字段约束团队版本，配 CI 检查。
**用什么版本**：跟 **LTS（偶数版）**——目前团队项目以 Node 20/22 LTS 为主；奇数版是非 LTS 不上生产。注意点：不同项目依赖对 Node 大版本敏感（如 node-sass 这类原生模块），版本锁不住是"我本地能跑"的经典来源。

### Q3：Git 常用命令 / 回退历史 / 多人冲突（犇犇×2 / 盛趣）✍️

**回退历史**：
- `git reset --soft <commit>`：回退提交、**改动留在暂存区**（重新 commit 即可，最常用）；
- `git reset --mixed`（默认）：回退提交，改动留在工作区；
- `git reset --hard`：彻底丢弃（危险，未提交改动会丢）；
- **`git revert <commit>`：生成一个"反向提交"**——历史是被追加而不是改写，**已 push 的公共分支必须用 revert**，reset 只用于本地/私有分支。

**多人冲突处理**：`git pull`（fetch+merge）→ 冲突文件里 Git 标记 `<<<<<<< HEAD / ======= / >>>>>>>` → 手动选择保留代码 → `git add <file>` → `git commit`（或 `git rebase` 流程：pull --rebase → 解决 → `git rebase --continue`）。
**常用命令集**：`status / log (--oneline --graph) / diff`、分支 `checkout -b / switch -c / merge / branch -d`、暂存 `add / restore / stash`、远端 `pull / push / fetch`、救急 `cherry-pick`（摘单个提交）、`stash`（临时存现场切分支）、`reflog`（找回误删提交）。

### Q4：Docker 的理解与使用场景（飞致云）📌

一句话：**把应用连同整套环境打包成标准箱子，搬到哪台机器都原样跑**，解决"本地能跑服务器报错"的环境不一致。三个概念分清：**Dockerfile 是说明书 → 镜像是按说明书做出来的模板 → 容器是镜像跑起来的实例**（一个镜像可起多个容器）。
**场景**：①统一团队开发环境；②保证本地/线上一致；③ docker-compose 一条命令起全套依赖（数据库、缓存）；④ CI 里临时起数据库跑测试；⑤处理用户上传这类不可信任务放容器隔离。
**结合自己**：我实习用 Docker + Nginx 部署前端 Demo 到公司内网——多阶段构建（node 构建阶段 + nginx 运行阶段），构建参数注入后端地址，镜像带版本号管理（详见主文档 4.4）。

### Q5：Docker 容器和虚拟机最大的区别（飞致云）📌

**要不要装一整套操作系统**：虚拟机虚拟的是**硬件**，每个 VM 装完整 OS、有自己的内核——几个 G、启动分钟级；Docker 容器**共享宿主机内核**，只用 **Namespace 做隔离、Cgroups 限制资源**，本质还是宿主机上的进程——几十兆、秒级启动。代价：共享内核导致**隔离性不如 VM**（容器逃逸风险），所以"轻量"和"隔离彻底"是取舍——安全要求极高的场景仍用 VM，常规交付用容器。

### Q6：对操作系统内核 Kernel 的理解（飞致云）📌

内核是操作系统最核心的部分，**硬件和应用之间的中间人、资源大管家**。管四件事：**CPU 调度与进程管理、内存分配与隔离、文件系统与磁盘、设备驱动**（网络和权限也归它）。核心概念是**用户态/内核态**：应用跑在用户态权限受限，不能直接碰硬件；要读文件、发包必须通过**系统调用**请内核代办——这样单个程序出问题不会搞崩整个系统。
**加分串联**：这个模型直接解释了 Docker——容器的隔离（Namespace）和资源限制（Cgroups）就是内核能力，所以它共享宿主内核、不用自带系统，才那么轻。

### Q7：Nginx 的理解；反向代理是什么？和正向代理的区别（飞致云）📌

Nginx 是高性能 Web 服务器 + 反向代理。性能高是因为**事件驱动的异步非阻塞模型**（epoll），一个 worker 进程扛大量并发。两大用法：**托管静态资源**、**反向代理转发给后端**（顺带负载均衡、HTTPS 证书、限流）。
**反向代理 = 代理服务端**：用户以为直接访问了网站，实际是 Nginx 接了请求转给后面的应用，用户不知道背后有几台机器。好处：隐藏真实服务器、负载均衡、统一入口配证书、动静分离。
**正向代理 = 代理客户端**：客户端自己配代理，隐藏的是客户端——翻墙工具、公司统一出口、爬虫代理池。
**一句话**：正向代理替客户端办事，反向代理替服务端挡在前面。
**结合自己**：内网部署时 Nginx 做静态托管 + `/api` 反向代理；SPA 要配 `try_files $uri /index.html` 防 history 路由刷新 404。

### Q8：为什么部署到 Vercel / 怎么理解 Serverless？（飞致云）⚠️

⚠️ 原题绑定他人博客项目（我没有 Vercel 实践，按"理解 + 对比自己的实践"答）：
**Serverless**：只交代码不养服务器——代码上传平台，**有请求才唤醒函数执行、跑完就释放**，事件驱动、按调用计费、无状态、有**冷启动**（闲置后第一次请求慢几秒）、执行时长有上限。和常驻服务对比：常驻进程保留内存状态、天然支持 WebSocket 长连接、超时并发自己说了算，代价是要自己运维。**选型**：个人低频项目（博客、小工具）适合 Serverless；有长连接、实时推送（WebSocket/SSE）必须常驻服务。
**Vercel 类平台**：零运维、GitHub 推送自动部署、PR 预览环境，前端静态站点 + 轻后端函数很合适。坑：冷启动、连接池（函数多实例会打满数据库连接，要小池 + 探活）。
**落到自己**：我的实际部署实践是 Docker + Nginx 交付公司内网（安全可控、内网不出公网），Serverless 的优劣势是了解层面——这样答既诚实又展示了部署功底。

### Q9：GitHub Actions 的 CI/CD 怎么实现？build 怎么构建？（飞致云）✍️

**CI/CD**：push 代码 / 提 PR 自动跑流水线——拉代码 → 装依赖（配缓存加速）→ **类型检查** → 构建 → 测试 → 部署；任何一步失败红叉，坏代码进不了主干。配置就是仓库里的 `.github/workflows/*.yml`（触发器 on push/PR、jobs、steps、actions 市场）。
**关键细节（踩过坑的才知道）**：**Vite 用 esbuild 打包只删类型不做检查**——类型写错也能构建成功！所以要**显式跑 `vue-tsc --noEmit` / `tsc` 做全量类型检查**，这是前端 CI 最有性价比的一步。
**构建本质**：Vite/Rollup 从 index.html 入口递归分析依赖图 → 编译 TS/SCSS → 分包、压缩、内容 hash → 输出 dist。CD 侧：监听 main 分支自动构建上线，PR 生成预览环境。

## 七、后端与数据库

### Q1：FastAPI + SQLAlchemy/SQLModel 的设计思路（飞致云）📌

**分层架构**（我有 FastAPI + SQLModel 实践，按自己项目讲）：
- **routers 接口层**：只管接请求、回响应，薄；
- **schemas（Pydantic）**：入参出参的校验模型——脏数据进不来，敏感字段（密码）出不去；
- **models（SQLModel/SQLAlchemy）**：表结构定义；
- **crud/service 层**：真正的业务逻辑和数据库操作；
- **依赖注入**：数据库会话每请求一个、用完自动关；"获取当前用户"也做成依赖（token 验签后注入），需要鉴权的接口挂上即可，业务代码里零认证样板。
**SQLModel 的便利**：一个类同时是 ORM Model 和 Pydantic Model（FastAPI 作者写的），省掉"ORM 类和 Schema 类"两套重复定义。
**好处**：改数据库不动接口、改接口不动业务，各管一段。

### Q2：RESTful API 的背景和优势（云栖处）📌

**背景**：早期接口"一个动作一个 URL"（/getUser、/deleteOrder），混乱且不自解释。REST 把**一切当资源**：URL 用名词复数（/users/3），**用 HTTP 动词表达动作**（GET 查 / POST 建 / PUT 改 / DELETE 删），**用状态码表达结果**（200/201/400/401/404/422/500）。
**优势**：语义自解释、复用 HTTP 的缓存和幂等语义（GET 幂等可缓存）、前后端解耦、生态工具多（Swagger 自动文档）。
**对比 GraphQL**：GraphQL 按需取字段更灵活，但缓存复杂、学习成本高；REST 简单通用、缓存友好——内部系统 REST 够用。实操补充：公司内部接口常是"统一 code/message/data 响应体 + REST 风格混合"，统一约定比教条更重要。

### Q3：MySQL 掌握程度 / 常用类型 / 长文本用什么（盛趣 / 引力琥珀）📌

**程度口径**（诚实分层）：应用层够用——建表、多表连接、分组统计、按查询建联合索引、看执行计划（EXPLAIN）；分库分表、主从没做过，需要时查文档或问后端。
**类型选择**：
- 整数：TINYINT（状态/布尔）、INT（主键常见）、数据量大或雪花 ID 用 BIGINT；
- 小数：**金额一定 DECIMAL**（FLOAT/DOUBLE 有精度误差）；
- 字符串：CHAR 定长（固定编码）、VARCHAR 变长（最常用）；
- 时间：DATETIME 范围大不带时区转换；TIMESTAMP 只占 4 字节但**只能到 2038 年**、带时区转换，适合 created_at/updated_at；
- **长文本：TEXT（64K），更大用 MEDIUMTEXT/LONGTEXT**。细节：TEXT **不能有默认值、建索引要指定前缀长度、大字段导致行溢出拖慢主表查询**——所以文章正文这类内容**单独拆一张表**，列表查询不碰大字段。
**结合自己**：实习参与过查询优化——EXPLAIN 定位、JOIN 字段补索引、联合索引最左匹配（主文档 1.2-Q8/Q9 有完整答案，这是我的真实实践，主动引到这里）。

### Q4：数据库索引 / 慢查询（引力琥珀）📌

结合自己答最有说服力：大表按**设备和时间建联合索引**（查询模式是"某设备某时间段"），翻页不用大偏移量（深分页用 `WHERE id > last_id` 游标式）。索引原理（B+ 树、最左匹配、索引失效场景）和 EXPLAIN 全套见主文档 1.2-Q8/Q9——这题在两份 PDF 里出现多次，务必滚瓜烂熟。

### Q5：哈希和 MD5 的理解（飞致云）📌

**哈希**：给数据按"指纹"——任意长度内容压成**固定长度、不可逆**的摘要，用来验证"是不是同一个东西"。三大特性：单向、抗碰撞、雪崩效应（改一点结果大变）。
**MD5 的现状**：算得快，但**已被证明可构造碰撞**，安全场景不能用了——只能做文件判重、完整性校验。
**正确用法**：文件一致性用 **SHA-256**（上传前后各算一次对比，防篡改，分片上传每片可带校验）；**密码存储绝不能裸哈希**——要"**加盐 + Argon2/bcrypt 这类故意算得慢的算法**"，让暴力破解的成本高到不可行；彩虹表攻击靠加盐防御（每人不同盐，预计算表失效）。

## 八、AI 与 RAG（云栖处 / 飞致云 / 引力琥珀 / 敦煌 / 心野 / 犇犇）

### Q1：RAG 知识库的整体实现思路（飞致云）📌

**RAG = 检索增强生成**：大模型本身不知道私有知识，就先"查资料"再回答。核心链路：
**入库（离线）**：文档上传 → 解析提取文本 → 清洗 → **切片（chunk）** → 每片用 **Embedding 模型向量化** → 存入**向量数据库**（带原文和元数据）。
**查询（在线）**：用户提问 → 问题同样向量化 → 向量库**相似度检索 Top-K**（余弦相似度）→ （可选 **Rerank 重排**精筛）→ 把命中的分片拼进 Prompt 作为上下文 → LLM 生成答案（引用来源）。
**我参与的部分**（结合农担智能体平台）：知识库管理、**召回测试**（评测检索质量：输入测试问题集，统计命中率/召回率，展示 Top-K 命中详情帮用户调 chunk 大小、top_k、相似度阈值）、知识库检索节点接入工作流。

### Q2：知识切片的实现逻辑（云栖处）📌

**为什么切**：整篇文档塞不进上下文窗口，检索也需要小颗粒度才能命中得准。
**怎么切**：①解析出纯文本和结构（标题层级、表格）；②**按标题层级先切章节**（尊重语义边界），章节内再**按长度切**（如 300~500 token）；③**相邻块留 overlap 重叠**（10%~20%），避免答案恰好被切断在边界上；④图片单独生成描述摘要当一个块；⑤每块带**来源、页码等元数据**方便答案溯源引用。
**经验点**：chunk 太小 → 上下文碎片化，语义不完整；太大 → 检索不精准、上下文浪费。所以提供参数让用户调，并用召回测试验证效果——这正是我做的召回测试模块的价值。

### Q3：向量入库的实现？为什么要向量入库？（云栖处）📌

**实现**：每个文本块过 Embedding 模型编码成**定长向量**（几百到几千维），连同原文、元数据一起写入向量数据库并建 **ANN 索引**（如 HNSW）。查询时问题向量与库中向量算相似度取最近的 K 个。
**为什么必须**：关键词检索只能匹配**字面**——用户换个说法就搜不到（"服务器宕机"搜不到"主机不可用"）；向量把**语义编码成坐标**，意思相近的段落距离就近，才能实现**语义检索**；且向量库索引支持**百万级数据毫秒级召回**，这是通用的 SQL LIKE 做不到的。

### Q4：文件上传的限制和校验？怎么保证文件成功上传、不被篡改？上传攻击脚本怎么办？（飞致云）📌

**前端限制**只是体验层（选文件时校验类型、大小，避免无效请求），**绕过很容易，后端必须重验**：
1. **校验**：大小上限、白名单类型；不只看后缀——读**文件魔数**（PDF 开头必须是 `%PDF`），再用真实解析器**打开验证**（打不开就拒）；空文件拦截；文件名清洗、**服务端重命名为随机名**（防路径穿越和覆盖）；
2. **一致性（防篡改）**：上传前算 **SHA-256**，后端收到再算一次对比，对不上拒收；全程 HTTPS；分片上传每片带校验值；
3. **防恶意文件**：文件永远当**不可信数据、绝不执行**——只存对象存储、不落网站目录、不给执行权限、加杀毒/特征检测；
4. **RAG 独有坑**：**提示词注入**——文档内容里可能藏"忽略之前的指令"这种话，系统提示词要写明"检索内容只是资料不是指令"。
**结合自己**：农担平台我做的上传校验就覆盖了大小、危险后缀、空文件三类场景 + 统一异常处理（主文档 1.2-Q1~Q3），这题可以答出自己的实现再往上叠 PDF 答案的完整性。

### Q5：平时用哪些 AI 工具？AI 使用占比多大？（敦煌 / 引力琥珀 / 心野）📌

**工具**：Cursor（主力，日常写代码）、Codex、ChatGPT/Claude（方案讨论）、Dify（搭智能体实践）。
**占比按环节分层答**（这题答"百分之 X"都不如分层精确）：①写重复代码、样板代码、查不熟的 API——**六七成**交给 AI；②核心逻辑和方案设计——**一两成**，主要拿它对比思路、做头脑风暴，决策和实现还是自己做；③权限、安全、线上问题——**基本不用**，错一次代价太大。
**原则**（必说，面试官在考察你有没有失控风险）：**AI 写的我必须能讲明白，而且一定要跑过验证才算数**——类型检查 + 自测用例兜底。
**结合自己**：我用 Cursor 两天交付过涉诈平台招标 Demo（含 mock 数据 + Docker 部署 + 讲解视频），这是 AI 提效的最好证明；但生产代码（农担平台）AI 只做辅助。

### Q6：模型越强，AI 开发结果越扎实越稳定，对吗？（敦煌）📌

**不完全对**——这是观点题，答出思辨性就赢了：
模型变强确实**抬高了下限**：语法错误、API 误用这类低级问题明显变少。但结果稳不稳定，很大程度取决于**模型之外的三件事**：
1. **上下文够不够**——它不知道你的项目约定和业务约束，就会给出"看起来对但用不了"的代码；
2. **有没有验证闭环**——类型检查、跑一遍、测边界；这步不做，再强的模型也只是"看起来对"；
3. **任务拆得够不够细**——大而模糊的需求，再强的模型也会漂。
结论：**模型强让上限更高，但方差要靠工程约束压下去，两件事不能互相替代。**

### Q7：给你一张 UI 设计图，怎么让 AI 完成还原？（园测 / 犇犇）✍️

**不是把图丢给 AI 就完事**（直接丢图的产出可控性差），我的做法（结合我做 Demo 的真实流程）：
1. **先拆解再生成**：把设计稿拆成页面清单 + 每页的结构块（导航/侧栏/卡片/图表），标注布局方式（几栏、栅格）、配色和组件规格，写成结构化的 prompt；
2. **定技术约束**：先让 AI 按设计稿生成一次设计 token（颜色/间距/字号变量），后续页面引用同一套变量，保证风格一致；
3. **分页面/分组件生成**：小步走，每生成一块检查一次再继续，避免一个大 prompt 生成整页后返工成本高；
4. **组件库对齐**：明确指定用哪个组件库（Ant Design / Element Plus），减少自造样式的偏差；
5. **视觉走查收尾**：AI 生成的是"接近"，最后人工对照设计稿调间距/对齐/响应式。
一句话总结：**AI 负责"从结构到代码"的体力活，人负责拆解、约束和验收**——这也解释了为什么我能两天交付整个 Demo。

## 九、移动端与小程序（敦煌 / 合肥智慧 / 心野 / MetaApp 一面）

### Q1：小程序写一个页面，在哪里改配置？（敦煌）✍️

分三处（原生小程序）：**app.json**——全局配置（页面路径 pages、窗口样式 window、tabBar）；**project.config.json**——项目级（appid、编译设置）；**页面目录下同名 .json**——单页面配置（导航栏标题、启用下拉刷新、引入自定义组件）。
**uniapp** 里集中到两个文件：**pages.json**（全局 + 每页面的样式配置都在 pages 数组的 style 字段里，如标题、下拉刷新）、**manifest.json**（appid、各端打包配置和权限）；环境变量放 `.env` 系列。

### Q2：数据列表为什么在 onShow 更新而不是 onLoad？（敦煌 / 关联安徽智慧地图题）📌

**onLoad 只在页面首次创建时执行一次**——从详情页返回、切 tab 回来都不会再触发，列表就停留在旧数据。**onShow 每次页面显示都触发**——能拿到"刚提交完的订单、刚改过的状态"。
**细节**：onShow 首次进入也会执行（紧跟 onLoad 之后），所以两个地方都写请求会**重复发一次**——常用做法是统一放 onShow 里用标记跳过首次，或 onLoad 拉首次、onShow 里判断"有脏标记才重拉"。
**同类题**（安徽智慧）：腾讯地图初始化/定位请求放哪个生命周期——地图渲染要 DOM 在 onLoad/onReady（页面初次），**数据刷新**（重新定位、移动后刷新周边）走 onShow。

### Q3：Web 端和移动端开发有什么区别？（合肥智慧）✍️

六个维度：
1. **运行环境**：浏览器 vs 小程序/原生 WebView——小程序没有完整 DOM/BOM（无 window、document，localStorage 不可用，要用 wx.setStorage）；
2. **布局单位**：rem/vh/vw vs **rpx**（按屏幕宽度等比缩放）+ 安全区适配（iPhone 刘海/底部横条）；
3. **API 与能力**：移动端有原生能力（扫码、定位、推送）但要授权处理；部分 Web API 不可用（MetaApp 追问的 ECharts 就是典型——小程序没有 DOM，图表初始化要传 canvas 2d 上下文和像素比，否则模糊）；
4. **性能**：低端安卓机 CPU/内存弱——长列表要虚拟滚动、少用大面积阴影动画；
5. **调试**：浏览器 DevTools vs 真机调试 + vConsole；
6. **发布**：Web 随时部署，小程序要审核、分阶段发布。
**uniapp 的价值与代价**：一套代码多端，靠**条件编译**（#ifdef MP-WEIXIN）处理差异——代价是平台差异抹不平的部分还是要分端写。

### Q4：为什么 uniapp 和 Web 部分 API 不能适用？（合肥智慧）✍️

因为 **uniapp 小程序端跑在不完整的浏览器环境里**：小程序的逻辑层是独立 JS 引擎（无 DOM/BOM），渲染层是原生组件，所以：
1. **DOM 操作类 API**（document.querySelector）没有——框架把模板编译成原生渲染，不走真实 DOM；
2. **BOM 类**（window、navigator、localStorage）没有——换成 uni.xxx / wx.xxx（uni.setStorage、uni.getLocation）；
3. **浏览器特性**（history、cookie、fetch 按端差异）行为不同；
4. 三方库依赖 DOM 的（ECharts、富文本）需要专门的小程序版或传 canvas 上下文。
处理方式：**条件编译**（`#ifdef H5 / #ifdef MP-WEIXIN`）分端实现 + 优先用 uni 统一 API 层（框架已做好多端适配的接口）。

### Q5：Web / 平板 / 移动端多端响应式，有哪些性能优化方案？（MetaApp 一面）✍️

分两层：
**适配层**：①响应式布局打底（flex/grid + 媒体查询分档断点；关键组件换形态——侧边栏变抽屉、表格变卡片）；②相对单位（rem/rpx）+ 安全区；③大屏按设计稿整体 scale 等比缩放（数据大屏常用）；④图表容器用 ResizeObserver 触发 resize。
**性能层**（多端真正的差别在设备能力）：①**按端差异化加载**——低端机降级动画、减少图表数量、关阴影模糊；②图片按屏幕密度给不同尺寸（srcset/瀑布流占位）、WebP；③**路由/组件级懒加载**，首屏只装当前端需要的代码，甚至 PC 和 H5 拆两套页面按 UA 分流；④长列表虚拟滚动（移动端收益最大）；⑤高频数据合批渲染（我的 SSE 设备监控就是这个思路：消息合批 + 只保留最近一批）；⑥重计算下沉（Web Worker / 服务端预计算）。

### Q6：怎么知道用户拿的是什么设备？（MetaApp 一面）✍️

三类手段（组合使用）：
1. **UA 检测**：`navigator.userAgent` 匹配关键词（iPhone/Android/iPad/Mobile）判断端类型——粗粒度但够用；注意 iPad 新版 Safari 默认伪装成桌面 UA，要配合其他信号；
2. **特性检测**（比 UA 可靠）：`'ontouchstart' in window`、`matchMedia('(pointer: coarse)')`（触摸设备）、`window.innerWidth` 断点判断；
3. **服务端判断**：请求头 UA 在网关/Nginx 层分流到不同站点（m.xxx.com / www.xxx.com）。
实践：**布局用 CSS 媒体查询（跟随窗口变化），逻辑分支用特性检测，路由分流用 UA**——不依赖单一手段。

### Q7：如何实现基于设备类型的差异化渲染？（MetaApp 一面）✍️

四种模式按侵入度递进：
1. **同一套代码 + 响应式组件**：组件内部按断点渲染不同结构（表格↔卡片）——维护成本最低，首选；
2. **条件编译**（uniapp）：`#ifdef MP-WEIXIN / H5` 一套仓库按端出不同产物；
3. **动态组件映射**：`<component :is="mobileVersion ? MobileList : PCLList" />`，同一数据、两套展示组件，通过统一的组件 props 契约解耦；
4. **路由级拆分**：PC 和 H5 是两套页面（甚至两个站点），入口按设备分流——差异巨大时用，代价是双份维护。
设计 token（颜色/间距/字号变量）分端配置，保证"结构不同、风格一致"。

### Q8：接触过地图开发吗？地图上设计一个点怎么做？（园测）⚠️

⚠️ 我没有地图开发实践——诚实说"没实际做过，了解思路"：
**地图开发基础**：接高德/腾讯/百度地图 SDK（小程序端用官方 map 组件）——初始化地图（传容器、中心点、缩放级别）→ 业务数据转**覆盖物**渲染 → 监听交互事件。
**"设计一个点"的完整考虑**（这题在考设计思维）：
1. **数据结构**：点位 = 坐标（经纬度）+ 类型 + 状态 + 自定义属性；**坐标系要对齐**——国内地图用 GCJ-02（火星坐标），GPS 原始是 WGS-84，百度是 BD-09，**混用会偏移几百米**，入库前统一转换；
2. **渲染**：单个点用 Marker（自定义图标区分类型/状态），**海量点**（几千上万）要用聚合（点密集时聚合成簇显示数量，缩放再展开）或专门的散层（海量点图层）；
3. **交互**：点上的信息窗体（InfoWindow）、点击/悬浮事件、按类型筛选显隐；
4. **性能**：视口外不渲染、聚合、点数据分层（底图/热力/点位分层）。

## 十、业务场景设计题

### Q1：可配置看板怎么设计？（用户拖拽组件、改属性、绑指标）（引力琥珀）📌

**核心思想：配置驱动，三件事分离**——每个组件的配置分三段：**位置**（放哪：x/y/w/h）、**数据**（取什么：指标 id + 数据源 + 筛选条件）、**展示**（长什么样：图表类型 + 样式参数）。看板整体序列化成一份 JSON 配置存后端。
**四个设计点**：
1. **组件注册表**：一个组件清单（类型 → 异步组件映射），渲染时按配置里的 type 从清单取——**新增图表只要往清单登记，主流程零改动**（和我工作流节点模板 + type 分发是同一套思路，可主动关联）；
2. **拖拽**：拖动时只改内存里的位置配置、不发请求，**松手（dragend）才保存**，减少无效请求；
3. **数据层**：筛选条件生成**版本号**，条件一变版本号变，响应回来先比对版本号——过期响应直接丢弃（防竞态）；各组件按自己的指标配置独立取数；
4. **渲染**：grid 布局按位置配置摆放，ResizeObserver 让图表随容器 resize。
（原 PDF 答案核心吸收：配置三分离 + 组件清单 + 拖拽只改位置松手保存 + 筛选版本号。）

### Q2：表格筛选结果错乱怎么排查？（引力琥珀）📌

**先看请求，不看代码**：
1. **看参数**：筛选条件对不对、**页码有没有重置回第一页**（换了筛选还停留在第 5 页是高频 bug）、排序参数；
2. **看时序**：几个请求回来的顺序和发出去的是否一致——**最常见根因：快速切换筛选时，旧请求后返回把新结果覆盖了（竞态）**；
3. **二分定位**：参数和响应都对、只是显示不对 → 前端状态问题（多个状态源打架）；响应本身就错 → 参数或后端问题。
**修复**：统一封装列表请求方法——发新请求前 **AbortController 取消旧请求**、切筛选自动重置页码、（进阶）响应带请求版本号比对。（与我主文档 2.3-Q5 竞态题同源，可互相印证。）

### Q3：门禁消息条数限制 + 防抖刷新怎么设计？（引力琥珀）📌

（我自己的同类实践：设备管理平台 SSE 主机状态推送 + ECharts 展示，可替换"门禁"来答）三件事：
1. **消息分类**：推送按类型分开处理——状态类进 store、告警类走通知，不让一条消息触发整页刷新；
2. **条数限制**：内存里只保留**最近一批**消息（定长队列，超出淘汰旧的），配**虚拟滚动**，DOM 节点数量恒定，列表多长都不卡；
3. **合并刷新（防抖合批）**：几百毫秒窗口内的多条推送**合成一次 setState**——来一条刷一条必卡；配合**视口外不渲染**、切页面取消订阅清定时器。
量化收益说法：一秒几十条推送时，DOM 更新从每秒几十次降到 2~3 次。

### Q4：在线考试倒计时为什么放服务端？怎么判断时间到？（合肥智慧）⚠️

**为什么服务端**：客户端时间可被修改（改系统时间、改本地变量），**考试这种对抗性场景必须以服务端时间为唯一权威**；同时多端（换设备继续考）需要一致的时间基准。
**实现设计**：
1. 服务端存考试的**绝对截止时间**（deadline），倒计时 = deadline − 服务器当前时间——**算差值而不是累减**（setInterval 每秒减一会累积误差，还受暂停/后台影响）；
2. 开考/刷新时下发 deadline + 服务器时间，前端做**时钟校准**（记录服务器时间与本地时间的偏移量 offset，之后本地时间 + offset）；
3. **判断时间到**：前端倒计时到 0 只是 UI 提示（禁用答题、弹窗交卷），**真正的收卷判定在服务端**——提交时后端校验 `now > deadline` 直接拒绝或自动收卷；再加服务端定时任务兜底（到点自动交卷落库），防止用户一直不提交；
4. 页面隐藏（切屏）回来时**重新校准**一次时间。

### Q5：防作弊（防切屏）怎么设计？（合肥智慧）⚠️

分级设计：
1. **检测**：`visibilitychange`（document.hidden）+ window blur/focus 捕捉切屏、切应用；记录切屏次数 + 时长并**上报服务端**（证据留档）；
2. **策略**：首次警告弹窗、超 N 次强制交卷或标记违规；进入全屏 API（requestFullscreen）退出即算切屏；
3. **加固**：禁复制粘贴（copy/paste/contextmenu 拦截）、答案选项顺序打乱、敏感页面禁用开发者工具常用快捷键（防君子不防小人）、拍照/抓脸（有人脸能力时）；
4. **原则**：前端检测都是**体验和威慑层**，判违规的依据以服务端记录的行为日志为准。

### Q6：每做一题就调接口吗？断网了怎么办？（合肥智慧）⚠️

**设计权衡**：每题一请求——实时但请求量大、断网就丢答案；全部最后提交——请求少但中途崩溃全丢。**折中：自动保存 + 批量 + 本地兜底**：
1. **作答即存本地**（localStorage/IndexedDB，按题目 id 存答案 + 版本），页面崩溃/误退出可恢复；
2. **批量/节流上报**：答案变更后防抖 N 秒批量提交未同步的题目（携带题目 id + 答案 + 版本号，**幂等**——重复提交以最后版本为准）；
3. **断网处理**：监听 online/offline；断网期间照常答、全部进本地队列，恢复网络后按序重传；
4. **对账兜底**：交卷前拉一次服务端已保存的答案对比，缺的补传；最终交卷仍以服务端确认成功为准，失败则保留本地数据提示用户。

### Q7：电商订单状态流？锁单后的倒计时？多规格怎么做？（东翼智能）⚠️

**订单状态流**：待支付（锁单）→ 已支付/待发货 → 已发货/待收货 → 已完成；分支：取消（超时未支付自动取消、用户主动取消）、退款/售后。前端做法：状态机映射（状态 → 可用操作 + 颜色标签），状态变更靠轮询或推送刷新；**超时未支付自动取消由服务端定时任务/延迟队列兜底**，前端倒计时只是展示。
**锁单倒计时**：和考试倒计时同构——服务端下发**订单过期绝对时间**，前端 `剩余 = deadline − (本地时间 + 服务器校准偏移)`，**每秒重算差值**（不累减防误差）；倒计时归零禁用支付按钮并刷新状态（真实取消以服务端为准）；页面从后台切回（visibilitychange）要**重新拉取订单状态**校准——本地计时在后台可能被节流。
**多规格（SKU）**：规格组×规格值的组合构成 SKU 表（颜色×内存 → 每个 SKU 独立的价格/库存），**数据由后端维护**，前端负责**联动体验**——选中部分规格后，根据 SKU 可达组合**置灰不可选的规格值**（选中"金色"后"256G 无货"就禁用），全部选完定位到具体 SKU 查价格库存；没有单独 SKU 的（如耗材选择）才用简单下拉。核心数据结构：`skuList: [{ specs: {颜色:'金', 内存:'256G'}, price, stock }]`，前端从 skuList 反推每个规格维度的可选值集合。

### Q8：图片上传前端怎么传、后端怎么接收？（安徽智慧）✍️

**前端**：`<input type="file">`（或拖拽/粘贴）→ 校验类型大小 → 需要时**压缩**（canvas 重绘，按质量 0.7~0.8 输出）→ `FormData.append('file', blob)` → axios post（让浏览器自动设 multipart 头）；**本地预览**用 `URL.createObjectURL(file)`（记得 revoke）；进度条用 axios 的 `onUploadProgress`；大文件走**分片上传**（我做过：切片 + 分片状态管理 + 失败单片重传 + 后端合并，主文档 3.2-Q5）。
**后端**（FastAPI）：`file: UploadFile = File(...)` 接收 multipart → **重验**大小/类型（魔数）→ 文件名重命名（UUID）→ 存对象存储/磁盘 → 返回访问 URL。安全要点：不落可执行目录、限制大小（Nginx 层 client_max_body_size 配套）、返回的 URL 做权限控制（私有读走签名 URL）。

### Q9：用户数据脱敏和密码加密怎么做？（安徽智慧）✍️

**脱敏（展示侧）**：手机号 `138****5678`、身份证前 3 后 4、姓名脱姓——**优先在后端接口出参时脱敏**（前端脱敏只是显示层，接口原文一样泄漏），前端只做纯展示兜底；日志里的敏感字段同样要脱敏。
**密码（存储侧）**：**绝不存明文**，也不存裸 MD5——用**加盐 + 慢哈希（bcrypt / Argon2）**，每次注册随机盐、哈希耗时故意拉高让暴力破解不可行；登录时 `verify(密码, 哈希)` 比对。**传输侧**：全程 HTTPS，前端再做一层混合加密是第二道防线（防代理/日志明文），但不能替代 HTTPS。
**我的相关实践**：认证插件接入时做过敏感信息前端加密上送方案（主文档 4.2），上传校验做过文件安全（主文档 1.2）。

### Q10：首页白屏怎么优化？（安徽智慧）✍️

先定位再优化（Network + Performance 看是资源慢、接口慢还是 JS 报错）：
1. **资源层**：路由懒加载 + 代码分割（首屏只加载当前页）、第三方按需引入、Critical CSS 内联、静态资源 CDN + 强缓存（带 hash 长缓存）、图片懒加载/WebP；
2. **请求层**：首屏接口并行（Promise.all）、接口合并、**骨架屏**（感知性能）、数据缓存（React Query/SWR 二次进入秒开）；
3. **渲染层**：SSR/预渲染（SEO 首屏）、长列表虚拟滚动、避免同步长任务阻塞首绘；
4. **兜底**：JS 报错白屏 → **Error Boundary + 降级 UI**（我封装过全局 Error Boundary，主文档 1.4-Q6），加载超时提示重试。
答这题的框架感很重要：**测量 → 定位 → 分层优化 → 兜底**，和主文档 1.5-Q7 性能题同源。

### Q11：富文本编辑框怎么做的？（安徽智慧）✍️

**选型**：wangEditor（中文文档好上手）/ tiptap（基于 ProseMirror，可定制强）/ Quill——**不自研**，富文本的坑（光标、选区、协同）极深。
**接入要点**：①内容受控（v-model 绑 HTML 字符串）；②**工具栏定制**（按需保留按钮，禁危险源码编辑）；③图片上传对接自己的 OSS（编辑器默认转 base64 会让正文巨大）；④字数统计/长度校验。
**安全（关键，串联 XSS）**：富文本内容是 HTML，回显用 v-html——**必须先过 DOMPurify 白名单消毒**（剔 script/事件属性/javascript: 链接）再入库或渲染，否则存储型 XSS 直接进系统。

### Q12：CSS 和 JS 分别怎么实现抛物线运动？（MetaApp 一面）✍️

**CSS**（无 JS，巧思）：外层元素做**水平线性匀速**动画，内层子元素做**垂直先慢后快**动画（`cubic-bezier(0.25, 0.46, 0.45, 0.94)` 近似重力加速），两个方向叠加 = 抛物线：

```css
.outer { animation: moveX 1s linear forwards; }
.inner { animation: moveY 1s cubic-bezier(.3,.7,.7,1) forwards; }
@keyframes moveX { to { transform: translateX(300px); } }
@keyframes moveY { to { transform: translateY(200px); } }
```

**JS**：`requestAnimationFrame` 每帧按物理公式算位置（x = vx·t，y = ½·g·t²），设 `transform: translate()`：

```js
function fly(el, { x0, y0, vx, g, t0 = performance.now() }) {
  const step = (now) => {
    const t = (now - t0) / 1000
    el.style.transform = `translate(${x0 + vx * t}px, ${y0 + 0.5 * g * t * t}px)`
    if (/* 未落地 */) requestAnimationFrame(step)
  }
  requestAnimationFrame(step)
}
```

加分点：为什么用 rAF 而不是 setInterval（跟浏览器渲染帧对齐、后台自动暂停、不丢帧）；动画只用 transform（不触发重排，走合成层）；购物车飞入动画就是抛物线的典型业务场景。

### Q13：如何避免重复请求 / 重复页面刷新？（心野引行）⚠️

⚠️ 原题表述模糊，按两种理解都准备：
**① 避免重复请求**：a) **请求去重**——相同 key（url+参数）的请求在飞行中就直接复用同一个 Promise（in-flight map）；b) **竞态取消**——新请求发出前 AbortController 取消旧的；c) **数据缓存**——React Query/SWR 类工具，缓存期内直接返回旧数据后台静默刷新；d) 防抖节流搜索输入、按钮 loading 防重复提交；e) 列表切筛选重置页码（避免无效分页请求）。
**② 避免重复刷新/整页重载**：a) **路由缓存**——keep-alive 缓存组件（返回列表页不重新加载，配合 onActivated 局部刷新）；b) **局部更新**——提交成功后只更新受影响的数据（响应式自动改），不整页 reload；c) 返回上一页用"标记 + onShow 判断是否重拉"代替无脑刷新；d) 长列表保滚动位置（虚拟列表 + 缓存 scrollTop）。

### Q14：ECharts 系列（云栖处 ×2 / 合肥智慧 / 安徽智慧）📌

**按需注册**：ECharts 5 把核心、图表、组件、渲染器拆开——从 `echarts/core` 引入，在**一个统一文件**里 `echarts.use([...])` 注册实际用到的（柱状图/折线图/饼图 + Grid/Tooltip/Legend + Canvas 渲染器），全项目都从这个文件引，业务代码不出现整包 import——打包时没用到的部分被移除。类型上用 `ComposeOption` 收窄，**漏注册在编译期就能发现**而不是运行时图表空白。小程序端还要注意：没有 DOM，要传 **canvas 2d 上下文** + 宽高和**像素比 devicePixelRatio**（否则模糊），图片用 `canvas.createImage` 加载。
**双 Y 轴**：两个量纲差很多的数据（如数量和时长）——`yAxis` 配成**数组**（左轴数量、右轴时长），series 里用 **`yAxisIndex`** 指定各系列挂哪个轴。
**数据下钻**：图表一层层点进去——监听图表 **click 事件**拿到被点击项 → 请求下一层数据 → **setOption** 换成明细图；用**栈记录下钻路径** + 面包屑，点任意一级回退到那一层。
**初始化时机**：必须在 **mounted/onMounted**（需要 DOM 容器拿宽高）；容器尺寸变化用 ResizeObserver 调 `chart.resize()`；组件卸载要 **dispose**（防内存泄漏），实例用 markRaw/shallowRef 存（防被响应式系统代理导致性能问题）——这一串细节是我的设备监控项目实践过的。

## 十一、HR 与开放性问题

### Q1：有没有考研计划？大四怎么安排？（盛趣）✍️ ⚠️按自己实际调整

建议口径（求职导向）：**不考研，秋招直接就业**——实习经历让我确认了想做前端/AI 方向，早进工业界成长更快；大四课程已修完大头（按实际），可以保证每周 X 天、持续 X 个月的稳定实习时间。**禁忌**：含糊其辞（"可能考也可能不考"直接出局）；如确实有考研打算，也别说，先想清楚自己要什么。

### Q2：为什么选择来 XX 城市？（盛趣/园测）✍️

准备"城市意愿"的标准答案要素：个人发展（岗位密度、行业机会）+ 已有基础（实习/学校/人脉在附近）+ 生活成本与家庭因素。我的实际情况：**求职意向是成都/重庆**（简历上写了），被问其他城市时回答"可以接受，关键看岗位和成长空间，X 城市也能长期发展"——别把话说死，也别说"只考虑某地"。

### Q3：为什么学前端？怎么学的？（合肥智慧 / 犇犇）✍️

口径与主文档 0.3 保持一致：网络工程专业课（Web 实践、计算机网络）接触前端 → 喜欢即时反馈和离用户近 → 系统学习（MDN/文档 + 项目实战）→ 实习六个月从页面开发做到 AI 全栈。学习方式强调：**以项目驱动**——每学一块就落到项目里（实习三个项目分别覆盖 React/Vue/全栈），善用 AI 工具但要求自己能讲明白每一行。

### Q4：在上家负责哪些业务？为什么离职？（合肥智慧）✍️

**负责业务**：一句话概括三个项目 + 各自核心模块（用主文档 0.2 的三项目定位表）。
**离职原因**（实习场景标准答案）：**实习合同期结束/学校安排返校**（真实且无争议），补充感谢式收尾："六个月收获很大，想找一份能长期投入的正式岗位/更聚焦 AI 方向的机会。"**禁忌**：不说前司坏话、不提薪资矛盾。

### Q5：你对自己的技术十分制打几分？（敦煌）✍️

**不给单点分，给分维度分**（既谦虚又显成熟）："打 7 分——基础部分（JS/Vue/React/工程化）经过六个月实习打磨比较扎实，能独立负责模块；差的 3 分：一是底层原理（框架源码、V8）还停在会用层，二是复杂场景经验（高并发、大型架构）不足。所以现在每天还在补 XX。"数字别打太满（9/10 显得没自知）也别太低（6 以下自贬）。

### Q6：现在在找工作吗？情况怎么样？（园测）✍️

口径：**有在推进，也有其他流程在进行**——展示市场认可但表达对当前公司的兴趣："在看机会，目前有几家在流程中（不主动提 offer 细节），贵司的 XX 方向和我实习做的最匹配，是我重点想争取的。"既不慌张（没公司要）也不傲慢（手握 offer 爱来不来）。

### Q7：你学过哪些专业课程？（云栖处 / 盛趣）✍️

照简历答并能各带一句与前端/AI 的关联：计算机网络（HTTP/TCP——做接口联调调优的底层理解）、数据结构（算法基础）、网络协议分析（抓包定位问题的能力）、网络安全 B（XSS/CSRF/加密的理论基础）、软件定义网络、Web 实践（前端起点）。**技巧**：把课程往岗位能力上引，不是报菜名。

### Q8：你有什么想问的吗？（园测）✍️

准备 2~3 个（与主文档 7.1 一致）：①团队技术栈与 AI 方向投入；②实习生负责的模块和 mentor 机制；③协作流程（评审/迭代节奏）。避免：这轮直接问薪资加班（留给 HR 面）、问"我表现怎么样"。

3. **强项主动展开点**：BroadcastChannel/SSE（我的独有亮点）、分片上传与并发管理、RBAC 按钮级权限（三家都问，我做过两套）、AI 工具实战（两天 Demo）——在相关题目里主动往自己项目带。
