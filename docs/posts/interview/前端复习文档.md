### 1.1 贡献一：工作流配置 —— Schema 驱动的节点配置机制

**简历原文：** 基于 Schema 驱动思想重构工作流节点配置机制，将节点表单与参数配置抽象为统一 Schema，实现不同类型节点配置页面的动态渲染，提升组件复用性与节点扩展效率。

#### 1.1.0 先记住整体架构（所有回答的总纲）📌

> 这个工作流搭建页面，本质是一个 **ReactFlow 画布 + 前端硬编码节点模板 + 后端存 flow JSON 并执行** 的架构。前端负责节点长什么样、表单怎么渲染；后端不返回表单 Schema，只负责保存整张工作流 JSON，运行时根据 `node.type` 找到对应执行类，再把 `group_params` 里的 key/value 扁平化成运行参数。所以它是**前端驱动 UI，后端驱动执行，两边通过 `type` 这个约定标签解耦**。

**核心一句话（面试点题用）：**

> "我们实际不是后端下发完整 Schema，而是前端维护节点参数配置模型，通过参数的 `type` 做表单组件分发；简单约束配置化，复杂交互组件化。"

#### Q1：简历里说"基于 Schema 驱动思想重构工作流节点配置机制"，具体怎么做的？📌

**参考回答：**

我们当时并不是后端动态返回一套完整的表单 Schema，而是前端维护了一套节点模板（硬编码在 `workflow.ts` 里）。节点模板里定义节点类型、参数分组，以及每个参数的 `key`、`label`、`type`、默认值、`options`、范围等配置。

创建节点时，前端根据模板生成 ReactFlow Node，模板来源于网站初始化的返回的本地记录；而用户请求已经创建的工作流时，后端会返回nodes和edges数组，edges数组记录节点的位置以及节点间的联想关系，nodes这个对象数组中则是不同的节点的名称和类型，每个节点对象有group_params属性，面板拿到 `group_params` 后遍历参数组，把每个参数交给统一的 `Parameter` 组件，它根据参数的 `type` 将这些数据包括表单组件的范围限制等，分发到这个节点所含有的对应的表单组件——`textarea` 对应文本输入、`slide` 对应滑块、`postwise_model` 对应模型选择器。

所以这里的"配置驱动"核心是：**不是每种节点单独写一套配置页面，而是统一的数据结构 + 参数类型分发机制来复用表单组件**，不同表单组件所组成的才是一个节点。

**可能的追问铺垫：**"重构"意味着原来不是这样的——如果被问"重构前是什么样"，可答：早期每种节点（或每类表单）存在重复开发的配置代码，新增节点要复制改一份；重构后统一走模板 + 分发，新增简单节点基本只需要加模板配置。

#### Q2：你们的"Schema"具体是什么？和标准 JSON Schema 什么区别？📌

**参考回答：**

严格来说我们不是标准 JSON Schema，而是一种自定义的节点参数配置描述。比如一个参数长这样：

```json
{ "key": "temperature", "type": "slide", "scope": [0, 2], "step": 0.1, "value": 0.7 }
```

即每个参数有 `key`、`label`、`type`、`value`、`required`、`options`、`scope`、`step` 这些字段。比如 temperature 定义成 `slide` 类型并配置范围步长；前端的 `Parameter` 组件根据 `type` 找到对应组件，把这些配置传进去。

所以简历里说的 Schema，准确说是**节点参数的配置模型**，服务于"编辑"，而不是校验文档结构的标准 JSON Schema。它的字段是按 UI 渲染需要设计的（比如 `scope`、`step` 都是 UI 元信息）。

#### Q3：前端具体怎么根据配置动态渲染表单的？渲染链路是什么？📌

**参考回答：**

核心是在 `Parameter` 这一层做组件分发。完整链路是：

```
节点 data.group_params（参数分组数组）
  → FlowNode 组件遍历 group_params
  → ParameterGroup 渲染每个分组
  → Parameter 组件根据 param.type switch 分发
  → 具体表单组件（Input / Slider / Select / ModelItem / Textarea…）
```

`Parameter.tsx` 里就是一个 switch：`slide` 渲染滑块、`postwise_model` 渲染模型选择器、`textarea` 渲染文本域、`condition` 渲染条件配置组件等。后端给的是**数据 + 类型标签**，前端拿标签查自己硬编码的组件表，把数据渲染成表单。这样新增简单节点参数时主要改节点模板，不需要重写配置页面。

#### Q4：用户打开一个已有工作流时，前端发生了什么？📌

**参考回答：**

前端拿 URL 里的 `workflowId` 调后端接口，后端返回整张 flow JSON，包含 `nodes` 和 `edges`。每个 node 有 `id`、`type`、`position`，以及最核心的 `data.group_params`（参数分组数组，每组有 `name`，组下有 `params`）。

前端把 nodes 映射成 ReactFlow 节点，统一设成 `type: 'flowNode'`，把 `data` 原封不动塞进去。ReactFlow 渲染时会调我们注册的 `FlowNode` 组件，`FlowNode` 内部遍历 `group_params` 走到 `Parameter` 分发——所以**打开已有工作流和拖拽新建，最终汇入同一条渲染链路**，区别只是 `data` 来自后端还是前端模板。

#### Q5：拖拽新建节点是怎么实现的？📌

**参考回答：**

左侧 Sidebar 的 `getWorkflowNodeTemplate()` 名字像 API，其实不请求后端，直接返回 `workflow.ts` 里硬编码的模板数组，每个模板包含 `type`、`name`、`group_params`，和保存后的结构完全一致。

用户拖拽时，`onDragStart` 把模板 JSON 通过 `dataTransfer.setData('flownodedata', JSON.stringify(data))` 存进浏览器拖拽数据；拖到画布时，`Pane.tsx` 的 `onDrop` 里取出模板，用 `screenToFlowPosition` 把鼠标屏幕坐标转成画布坐标，`initNode` 补全默认值，生成新节点 `{ id: 新生成, type: 'flowNode', position, data: 模板节点 }`，再 `setNodes` 追加到画布。新节点出现后同样走 `FlowNode → ParameterGroup → Parameter` 渲染表单。

**可被追问的细节：**

- `screenToFlowPosition` 是 ReactFlow 提供的工具，解决"浏览器窗口坐标 → 画布坐标系（含缩放平移）"的换算；
- HTML5 拖放 API：`dragstart` 里 setData、`drop` 里要 `preventDefault` 阻止默认行为，否则 drop 不触发；
- React Drag events 和 HTML5 原生 DnD 的关系（React 只是合成事件包装）。

#### Q6：保存工作流时，前端提交什么数据？后端怎么用它？📌

**参考回答：**

保存时前端提交整张 ReactFlow 画布的序列化 JSON，外层是 `nodes` 和 `edges`。每个节点里：
- ReactFlow 自身的 `id`、`type: 'flowNode'`、`position` 用于还原画布；
- 业务数据在 `data` 里，包含业务 `type`（如 `llm`、`agent`）和 `group_params`（参数分组数组）。

后端全量存下来；运行时只取 `data.type` 找节点执行类，再把 `group_params` 扁平化：`BaseNodeData` 接收 `group_params`，在 `base.py` 里做一层 `for group in group_params: for param in group.params: self.node_params[param.key] = param.value`，节点类里直接 `self.node_params['model_id']`、`self.node_params.get('temperature', 0.3)` 取参，不关心 UI 怎么分组。

所以保存的数据**既让前端能还原表单，也让后端能拿到运行参数**，两边通过 `type` 和 `group_params` 解耦。前端配置模型负责"怎么配置"，后端运行参数负责"怎么执行"。

#### Q7：前端的 `type: "llm"` 和后端怎么对应起来？📌

**参考回答：**

后端维护一个节点类型到执行类的映射 `NODE_CLASS_MAP`，比如 `llm` 对应 `LLMNode`、`condition` 对应 `ConditionNode`、`agent` 对应 `AgentNode`。后端拿到节点后根据 `node.data.type` 找到 Node Class，实例化并执行。

所以前端的节点类型主要决定**怎么编辑和展示**，后端的节点类型主要决定**怎么执行**，两边靠同一个字符串约定对齐。

#### Q8：如果一个输入框要求只能输入 0 到 1，怎么处理？📌

**参考回答：**

这种简单约束直接放在参数配置里。比如 Slider 类型通过 `scope: [0, 2]` 定义范围、`step: 0.1` 定义步长，Slider 组件读取配置转成 `min`/`max`/`step`；普通 number 类型也可以通过 `min`、`max` 传给 Input。不过实际项目里不同组件约束程度不完全一样——有些是配置传入，有些特殊输入规则在具体组件内部处理。

#### Q9：两个选择框有联动（选模型 → 选版本），怎么处理？📌

**参考回答：**

这种不能简单当成两个独立 Schema 字段，我们会把复杂交互放到具体组件里。比如模型选择组件本身就是独立的 `ModelItem`，内部获取模型列表并根据当前选择更新状态；如果前一个字段变化需要重新请求接口，具体组件监听前一个字段变化、重新拉取后一个字段的 options 再更新表单数据。

原则是：**简单的字段类型和基础约束配置化，复杂的联动和异步逻辑放到具体组件里**。

#### Q10：为什么不把所有逻辑都放进 Schema？📌

**参考回答：**

Schema 适合描述静态信息——字段类型、默认值、范围、是否必填。但字段联动属于行为逻辑：一个字段变化后要调接口，再根据结果决定另一个字段怎么变。这种逻辑全塞进 Schema，配置本身会变得非常复杂，可维护性反而下降（比直接写组件还难维护——这是我们实际踩过的认识过程，一开始想尽量全部 Schema 化，后来主动收边界）。

所以最终是折中方案：**通用能力配置化，复杂业务逻辑组件化**。像开始/结束节点、LLM 节点、知识库检索节点、普通工具调用节点适合配置化；有复杂联动、异步加载、特殊业务规则的节点用自定义 React 组件。

#### Q11：新增一种节点，前端要改哪些地方？📌

**参考回答：**

分两种情况：
1. **使用已有参数类型的简单节点**：主要在节点模板里加定义（节点类型、参数分组、参数配置），已有的 `Parameter` 分发机制直接复用现有表单组件，扩展成本低；
2. **有新参数类型或复杂交互的节点**：需要新增 React 组件，并在 `Parameter` 里加 `type → 组件` 的映射。

所以简历说"提升平台扩展能力"，准确含义是**降低简单节点的扩展成本，同时保留复杂节点的定制能力**，不是说新增节点完全不用写代码。

#### Q12：这套方案的优点和缺点？如果继续优化怎么做？📌

**优点：**
1. **组件复用**：Input、Slider、Select 等基础表单通过 `type` 统一复用，不同节点不重复实现；
2. **节点扩展方便**：简单节点主要加配置；
3. **前后端解耦**：前端完全掌控表单 UI，后端只关心数据结构和执行，通过 `type` 约定对齐。

**缺点（诚实说，面试官喜欢）：**
前后端靠字符串约定，没有强类型校验，容易出现不一致。实际遇到过两类问题：
- 前端模板写了 `type: 'select'`，但 `Parameter.tsx` 没有对应渲染器，界面显示 `Unsupported parameter type`；
- 模板写了 `file_retriever`，但后端 `NODE_CLASS_MAP` 里只有 `knowledge_retriever`，运行时找不到执行类。

**优化方向：**
加一层**节点模板 Schema 校验**（CI 或运行时启动时校验前端模板里的 type 在两边都有定义），或用 JSON Schema / 单一数据源自动生成前后端类型定义（TypeScript 类型 + Python Pydantic model），保证 `type` 两边强一致。进一步还可以把字段类型、默认值、校验规则、依赖关系抽象得更统一，封装通用 FormRenderer：简单字段完全由配置生成，复杂联动允许注册自定义组件——即 `Schema → 通用 Renderer → 基础组件` + `Schema → 自定义组件` 两条路。

#### Q13：节点很多的时候，性能怎么优化？📌

**参考回答：**

ReactFlow 本身支持视口虚拟化（只渲染可视区域），但**表单渲染可能重**。可以：
1. **按需渲染**：折叠状态的 group 不渲染内部表单，展开时再渲染；
2. **memo 化**：对 `Parameter`、卡片类子组件做 `React.memo`，节点拖动/画布缩放时不重复执行表单渲染；
3. **拖拽轻量化**：拖拽过程中用轻量占位组件，drop 之后再渲染完整表单；
4. 配合状态拆分，避免画布坐标变化触发业务表单组件更新（见 Q14）。

#### Q14：工作流编辑器里有哪些状态？怎么管理？📌

**参考回答：**

工作流同时存在三类状态：
1. **后端保存的工作流配置**（持久化的 flow JSON）；
2. **前端业务状态**（当前选中节点、未保存的参数修改、节点展开/折叠等）；
3. **ReactFlow 自己管理的画布状态**（节点位置、边、视口缩放平移）。

我们的做法是把这三部分**拆分**，中间通过转换层把业务数据转换成 ReactFlow 的 `nodes`/`edges`，避免不同状态互相耦合——比如拖动节点只影响画布状态，不应该让配置表单跟着重渲染。

**追问预备（ReactFlow 受控模式）⚠️：** ReactFlow 支持受控（自己持有 nodes/edges，监听 `onNodesChange`/`onEdgesChange` 应用变更）与非受控两种用法；受控模式下要小心每次 render 生成新数组/新对象导致整画布重渲染，change 回调里应按 `type`（position/dimensions/selection）精准应用变更，而不是粗暴 `setNodes(重新map一遍)`。

#### Q15：工作流连线有什么校验？（追问预备）⚠️

参考思路：连线本质是向 `edges` 数组加一条 `{ source, target, sourceHandle, targetHandle }`。常见校验包括：不能自连、不能重复连、开始节点只有出边、结束节点只有入边、有的节点限制入边数量；执行层面工作流应为 **DAG（有向无环图）**，保存或执行前做环检测（DFS 拓扑排序）。若实际项目未做环检测，如实说"前端做了 XX 校验，环检测是后端执行时/或未严格做"，不要编造。

### 1.2 贡献二：后端与文件安全 —— FastAPI + SQLModel + 上传校验 + 查询优化

**简历原文：** 基于 FastAPI + SQLModel 参与后端模块开发与维护，完善文件上传校验，覆盖文件大小、危险后缀及空文件等场景；完成 REST API 调整、业务逻辑优化、数据库查询优化及前后端联调。

#### Q1：文件上传安全校验是怎么设计的？前端和后端分别承担什么职责？📌

**参考回答：**

文件上传主要用于 AI 应用和知识库相关功能。我在后端上传接口中增加了**文件大小、危险后缀、空文件**等校验，避免明显不符合要求的文件进入后续处理流程，并对异常情况做统一处理（返回明确错误码和错误信息）。

前端负责**用户侧基础校验和交互反馈**：用户选择文件时就检查大小、类型，不符合直接提示，避免发出无效请求。但前端校验只能作为第一层防护——前端逻辑是可以被绕过的（直接用 curl/Postman 调接口）。

**后端才是最终安全边界**：服务端必须对上传请求重新校验大小、后缀以及内容相关的业务规则。前端根据接口返回更新上传状态并展示提示。

核心表述：**前端负责体验和减少无效请求，后端负责最终安全校验，前端校验过不等于后端可以信任文件**。

#### Q2：危险后缀校验具体怎么做？只看后缀名够吗？⚠️

**参考回答思路（按常见实现口述，细节需核对）：**

我们主要用**后缀黑名单/白名单**方式：黑名单拦截 `.exe`、`.sh`、`.bat`、`.jsp` 等可执行/脚本类危险后缀，知识库场景用白名单只放行 `.pdf`、`.docx`、`.txt`、`.md` 等文档类型（白名单比黑名单更安全）。

只看后缀不够严格，面试官可能追问的加深点：
1. **大小写与双后缀**：`a.PDF.exe`、`a.exe.pdf`、URL 编码/空字节（`%00`）绕过——应取最后一个 `.` 之后的部分并 `toLowerCase`，或直接用白名单匹配；
2. **MIME 类型可伪造**：请求头 `Content-Type` 是客户端声明的，只能作参考；
3. **魔数（文件头）校验**：读文件前几个字节判断真实类型（如 PDF 是 `%PDF`、PNG 是 `89 50 4E 47`），Python 可用 `python-magic` 库；
4. **存储侧防护**：上传目录不给执行权限、文件名服务端重命名（UUID）、不使用用户原始文件名拼路径（防路径穿越 `../../`）。

#### Q3：为什么要校验空文件？多大算大？限制在哪里配？⚠️

**参考思路：** 空文件（0 字节）通常是用户误传或上传中断的产物，进入知识库解析流程会报错或产生脏数据，所以前置拦截。大小限制既要在后端接口校验（如 FastAPI 里读 `file.size` / `len(await file.read())`），也可以在反向代理层（Nginx `client_max_body_size`）限制——否则超大请求在到达应用前就 413 了，这个层次区别是加分点。

#### Q4：前端上传文件用什么方式？multipart/form-data 是什么？⚠️

**参考思路：** 用 `<input type="file">` + FormData，`formData.append('file', file)`，`axios.post(url, formData)` 时让浏览器自动设置 `Content-Type: multipart/form-data; boundary=...`（**手动设置 Content-Type 反而会丢 boundary 导致后端解析失败**，这是高频坑）。multipart 格式就是用 boundary 分隔符把多个字段/文件拼在一个请求体里。知识库多文件上传就是 append 多个 entry 或多次调用。

#### Q5：FastAPI 有什么特点？为什么项目用它？⚠️

**参考回答思路：**
1. **基于 ASGI 的异步框架**，`async def` 路由配合 `await` 处理 IO 密集任务（调用 LLM、读文件）吞吐好，很适合 AI 应用这种大量等待外部服务的场景；
2. **Pydantic 数据校验**：请求/响应模型声明式定义，自动校验和序列化，422 错误自动返回；
3. **依赖注入系统**（`Depends`）：如"当前登录用户"、"DB 会话"这类公共依赖统一注入，权限校验很适合做成依赖；
4. 自动生成 OpenAPI 文档（`/docs`），前后端联调直接看 Swagger。

#### Q6：SQLModel 是什么？和 SQLAlchemy、Pydantic 什么关系？⚠️

**参考回答思路：** SQLModel 是 tiangolo（FastAPI 作者）写的库，**一个类同时是 SQLAlchemy ORM Model 和 Pydantic Model**——继承 SQLModel 的类可以直接被 FastAPI 用作请求/响应模型，也能操作数据库，减少"ORM 模型"和"接口 Schema"两套类的重复定义。底层查询能力就是 SQLAlchemy（`session.exec(select(Model).where(...))`），校验能力来自 Pydantic。代价是复杂查询/迁移场景灵活性不如直接用 SQLAlchemy + Alembic 的成熟组合。

#### Q7：REST API 调整具体做过什么？RESTful 设计规范你怎么理解？⚠️

**参考思路：** 实际工作包括：字段增减后同步更新接口模型、统一响应结构（`code/message/data`）、修正不合理的状态码返回（如校验失败返回 400/422 而不是 500）、补齐参数校验。规范层面：**资源用名词复数、方法表达语义**（GET 查 / POST 建 / PUT 全量改 / PATCH 部分改 / DELETE 删）、**状态码语义化**（200/201/400/401/403/404/422/500）、无状态、版本化（`/api/v1/...`）。可以坦率说：公司内部接口不一定严格 RESTful，更多是"统一约定优先"。

#### Q8：数据库查询优化你是怎么做的？一条慢 SQL 怎么分析？📌

**参考回答：**

一般从**执行计划、索引、SQL 写法、数据量**四方面入手：

1. **先 `EXPLAIN` 看执行计划**：重点看每张表的访问类型（`type` 列，是否 ALL 全表扫描）、预估扫描行数、用了哪个索引（`key`），判断瓶颈在哪张表、哪个关联条件；
2. **检查索引**：多表关联看 JOIN 字段有没有索引；多条件筛选考虑联合索引并注意**最左匹配原则**；避免给区分度低的字段单独建索引，也避免堆一堆没收益的索引（写入代价）；
3. **检查 SQL 写法**：有没有 `SELECT *`、不必要子查询、复杂 `OR`；索引字段上做函数计算或**隐式类型转换**（字符串列传数字）会导致索引失效；确认是否可以"先过滤再 JOIN"减少中间结果集；
4. **结合数据量**：数据量特别大时即使 SQL 合理也可能有瓶颈，考虑分页（且避免深分页 `LIMIT 100000,20`——可用游游标方式 `WHERE id > last_id LIMIT 20`）、归档、缓存。

总结口径：**EXPLAIN 定位问题 → 查 JOIN/WHERE 的索引 → 优化写法和关联顺序 → 结合数据量考虑分页/缓存**。

**关联项目事实：** 农担平台里我参与的是应用记录、审计日志这类查询链路的优化（详见贡献三），慢 SQL 分析系统项目本身则是对外提供慢 SQL 分析能力的产品。

#### Q9：（八股追问）索引为什么快？什么情况下索引失效？⚠️

**要点式回答：** InnoDB 默认 B+ 树索引——叶子节点存数据（聚簇索引）或主键（二级索引），树高一般 2~4 层，把全表扫描降为 O(logN) 次页访问；范围查询和最左前缀利用节点有序性。失效场景：对索引列用函数/运算、隐式类型转换、前导 `%like`、`OR` 连接了非索引列、违反联合索引最左匹配、优化器判断回表成本过高（区分度低）选择全表扫描。追问 B+ 树 vs B 树：B+ 树非叶子节点不存数据、叶子链表串联利于范围查询。

#### Q10：（八股追问）事务的 ACID？项目里哪里用到事务？⚠️

**要点式回答：** 原子性（undo log）、一致性、隔离性（锁 + MVCC）、持久性（redo log）。隔离级别读未提交/读已提交/可重复提交（InnoDB 默认，可重复读 repeatable read）/串行化；并发问题脏读、不可重复读、幻读。项目场景：删除模型要同时清理关联配置（见贡献四模型缓存问题的后端侧），多表一致修改就该包在事务里；Python 侧 `session.begin()` / `commit` / 出错 `rollback`。

### 1.3 贡献三：权限治理 —— 用户组 / 资源归属 / 角色权限 / 会话记录关联

**简历原文：** 梳理用户组、资源归属、角色权限与会话记录之间的关联关系，优化应用记录及审计日志查询链路，修复跨角色授权场景下记录漏查、串查及权限校验异常，提升数据查询准确性与权限控制一致性。

#### Q1：先讲讲你对 RBAC 的理解，数据库上怎么设计？📌

**参考回答：**

RBAC 核心是**基于角色的访问控制**：不给用户直接配权限，而是 用户 → 角色 → 权限 三层关联。经典五表结构：
- `user`（用户）、`role`（角色）、`user_role`（用户-角色多对多）；
- `permission` / `resource`（菜单、按钮、接口、数据资源）、`role_permission`（角色-权限多对多）。

我们平台在这个基础上还有**用户组**和**资源归属**概念：用户组是一批用户的集合（可以整体授权），资源归属记录"这条应用/这条会话记录属于哪个用户/用户组"——数据权限过滤时要用它。

**三个权限层次要分清：**
- **菜单权限**：用户能不能看到这个功能（前端控制显示）；
- **接口权限**：用户能不能调这个接口（后端鉴权中间件/依赖校验）；
- **数据权限**：调通接口后能看到哪些数据（查询时按资源归属/用户组过滤 WHERE 条件）。

前端负责页面展示、路由控制和请求层面配合，但接口权限和数据权限必须由后端校验——**不能只靠前端隐藏菜单保证安全**，因为接口可以直接被调用。

#### Q2：用户组、资源归属、角色权限、会话记录之间的关联关系，你是怎么梳理的？⚠️

**参考回答思路：**

这是这条贡献的"业务功课"，面试前必须能把关系讲顺：

- **会话记录/应用记录**（Agent 对话历史、应用运行记录）是数据主体，每条记录有**资源归属**（创建人/所属用户组）；
- **用户**加入**用户组**，用户/用户组被授予**角色**，角色挂**菜单/接口/数据权限**；
- 查询一个人的可见记录 = 「自己创建的」 ∪ 「所属用户组共享的」 ∩ 「角色数据权限允许的」，多条链路取并集/交集时最容易出错——这正是漏查、串查的来源。

实际梳理动作：画 ER 关系图对齐前后端理解、核对每个查询接口的过滤条件是否同时满足三类约束、补齐测试用例（跨角色、跨用户组的边界场景）。

#### Q3：「跨角色授权场景下记录漏查、串查」具体是什么问题？怎么发现、怎么修复的？⚠️

这个问题是这条贡献的核心，一定要能讲出具体画面。

**参考回答框架（按排查故事讲）：**

1. **现象**：测试/客户反馈两类异常——
   - **漏查**：用户 A 明明应该能看到（比如所属用户组下其他人创建的）某些应用记录/审计日志，列表里却没有；
   - **串查**：用户 B 看到了不属于自己的记录（越权可见，比漏查更严重）；
   - 还有权限校验异常：有菜单权限的用户访问审计日志接口直接返回 403。
2. **排查**：从接口入手打印/复现最终执行的 SQL，对照权限模型逐条检查过滤条件。定位到的问题类型：
   - 查询只按"创建人 = 当前用户"过滤，**漏掉了用户组共享**的记录 → 漏查；
   - 多角色用户做权限过滤时，**JOIN 条件与过滤条件位置不当**（比如先 JOIN 出笛卡尔积再在结果上过滤，或 OR 优先级括号错误），导致无关联记录混入 → 串查；
   - 权限校验只查了角色-菜单关系，没查数据权限，行为不一致 → 有菜单权限却 403。
3. **修复**：
   - 重写查询链路：资源归属条件（本人 ∪ 用户组）与角色数据权限**在正确的 JOIN/WHERE 层次上组合**，多角色取并集时明确用 `EXISTS / IN` 子查询而不是多表 JOIN；
   - 行为对齐：**有菜单访问权限但没有对应数据权限的用户返回空结果，而不是抛 403 异常**，让菜单权限、接口权限、数据权限行为一致；
   - 补充跨角色、跨用户组的边界测试用例防止回归。

**面试官可能追问「漏查和串查的技术成因」，准备两句精准解释：**
- 漏查典型成因：过滤条件写了 `AND`（同时要求满足两种授权），实际授权语义是 `OR`（任一授权即可见）；
- 串查典型成因：权限表 JOIN 时没有把"该用户-该角色"的绑定条件写进 ON/WHERE，导致任意角色的权限记录都参与了匹配。

#### Q4：审计日志 403 那个案例展开讲讲？📌

**参考回答：**

实际遇到过一个权限链路问题：用户明明已经获得了菜单访问权限（菜单能看到审计日志入口），但访问审计日志接口时返回 403。我们梳理了用户组、资源归属、角色权限以及数据权限之间的关系，对权限校验链路做了调整，最终让**有菜单权限但没有对应数据权限的用户拿到空结果列表，而不是异常**——从用户视角，"能进页面但没数据"比"页面报错"更符合权限语义，也让菜单权限、接口权限、数据权限三层行为保持一致。

#### Q5：应用记录 / 审计日志的查询链路优化具体指什么？⚠️

**参考思路：** 三方面：① SQL 层面——权限过滤子查询化、补 JOIN 字段索引（user_id、group_id、resource_id 组合查询是高频条件）、大表按时间过滤走索引避免全表扫描；② 接口层面——分页参数规范化、避免一次拉全量、列表接口只查摘要不查大会话正文；③ 缓存/快照——用户-角色-用户组关系变动不频繁，权限集合可短缓存（要能答"缓存失效怎么办"：授权变更时主动失效）。

#### Q6：（八股追问）JWT / Session / Cookie 三种认证方式对比？⚠️

**要点式回答：**
- **Session + Cookie**：状态存服务端，浏览器带 Cookie（自动携带、同源约束），服务端按 session_id 取；扩容要共享 session 存储；
- **JWT**：状态存客户端，`header.payload.signature` 三段，服务端用签名验证不存状态，天然适合分布式/前后端分离；缺点是**签发后无法主动作废**（只能靠短有效期 + refresh token 或黑名单）、payload 只是 Base64 编码**不能放敏感信息**；
- **Token（opaque）+ localStorage**：我们平台类项目常用——登录换 token，前端存 localStorage，请求头 `Authorization: Bearer xxx` 注入（Axios 拦截器统一做）。
- 追问"JWT 怎么退出登录"：客户端删 token 只是表面，服务端要黑名单/版本号机制，或接受"退出只是前端行为、令牌自然过期"。

### 1.4 贡献四：前端异常治理 —— 模型缓存失效 + SSE 重复展示 + Error Boundary

**简历原文：** 修复模型缓存失效、流式响应重复展示问题，并通过全局 Error Boundary 封装实现前端运行时异常捕获与页面降级处理，增强系统稳定性。

#### Q1：模型缓存失效问题是怎么回事？怎么解决的？📌

**参考回答：**

问题本质是**本地缓存的模型配置和后端最新模型列表不一致**。当时用户选择模型后，会把模型 id 和名称存到 localStorage；但删除模型时只更新了后台配置，没有同步清理本地存储。于是再次进入工作台时：下拉列表里已经没有该模型，但对话功能仍从 localStorage 读到了旧模型 id，当前选中项还是被删的那个——用户一发起对话就出错或行为异常。

**解决方式：** 在工作台初始化加载模型配置时增加**校验逻辑**——先拉取后端最新模型列表，判断 localStorage 里的模型 id 是否还存在：存在则继续使用；不存在则清除本地缓存，默认选中模型列表第一个可用模型，同时更新 localStorage，保证本地状态和后台配置一致。降级的同时**弹窗提示**用户"该模型已被管理员删除，已切换为默认模型"。

**回答亮点（主动升华）：** 这类问题的通用模式是"**客户端缓存的服务端可变数据，必须考虑一致性校验**"——缓存读取时以服务端为准做兜底，而不是假设缓存永远有效。

#### Q2：（追问）如果两个标签页同时打开工作台，一边删模型一边用，localStorage 怎么同步？⚠️

**参考思路：** localStorage 跨标签页不触发响应式更新。方案：① 监听 `window` 的 `storage` 事件（其他标签页修改时当前页会收到，注意**当前修改页自己不触发**）；② 用 `BroadcastChannel` 广播"模型列表变更"事件，各页面收到后重新拉取/校验；③ 简单兜底：关键动作（发起对话）前再校验一次。可关联实习专项里的 BroadcastChannel 方案，体现知识串联。

#### Q3：流式响应重复展示是什么问题？怎么定位和解决的？📌

**参考回答：**

现象是对话消息被重复拼接展示。根因是 **SSE 长连接生命周期管理不完善**——页面切换（组件卸载重建）时没有正确关闭旧连接，旧连接和新连接同时接收服务端推送，两边都在往同一条消息上拼接，造成重复。

**解决三层：**
1. **生命周期管理**：用 `useRef` 持有 EventSource 实例，建立新连接前判断是否已有连接、有则先关闭；组件卸载（`useEffect` return）时主动 `close()`；
2. **消息去重**：对服务端返回的消息增加唯一标识，前端收到后判断该 ID 是否处理过，处理过直接丢弃，保证一次请求只展示一次流式结果；
3. （关联追问：断线重连场景见 Q4）

#### Q4：（追问）SSE 断线重连后收到已收过的消息，怎么办？📌

**参考回答：**

通过**消息唯一 ID 保证幂等**，避免同一条数据重复渲染：服务端给每条 SSE 消息分配唯一 ID，前端收到先查是否处理过，处理过丢弃，否则更新消息列表。

更进一步，**SSE 协议本身有 `id` 字段和 `Last-Event-ID` 机制**：客户端断线重连时，浏览器会自动把最后收到的事件 ID 通过 `Last-Event-ID` 请求头带给服务端，服务端从这个位置之后继续推送（要求服务端有消息存储和重放能力，比如根据会话记录查到 last id 的下一条开始重推）。

如果服务端没做持久化、不支持 `Last-Event-ID`，前端只能自救：内存 `Set` 记录已处理 ID（跨标签页则用 localStorage），但这只是权宜之计——要小心 **ID 集合无限增长导致内存泄漏**（可做上限 + 会话结束清理）。

**总结口径：最好后端配合用浏览器原生 `Last-Event-ID` 做断点续传保证幂等；否则服务端保证消息有唯一标识、客户端消费时去重，并注意去重集合的内存治理。**

#### Q5：（追问）为什么用 useRef 存 EventSource 而不是 state？⚠️

**参考回答：** EventSource 是**外部资源句柄**，不是渲染数据——它不需要参与渲染，改它也不应该触发组件重渲染；用 state 存会在每次 set 时触发不必要的 render，还可能因为严格模式/重渲染被意外重建。`useRef` 在组件整个生命周期里保持同一引用，`ref.current` 可变，恰好匹配"连接实例"这种用途。同类场景：定时器 id、DOM 引用、Axios 取消控制器。可以补一句 React 严格模式（StrictMode）下 effect 会执行两次（开发环境），所以 effect 里创建连接 + return 清理的写法正好能保证不泄漏。

#### Q6：全局 Error Boundary 是怎么封装的？原理是什么？⚠️

**参考回答思路：**

- **原理**：React 的类组件如果定义了 `static getDerivedStateFromError()`（渲染备用 UI）或 `componentDidCatch()`（记录错误信息），就成为错误边界——**捕获子组件树在渲染、生命周期和构造函数里抛出的 JS 异常**，展示降级 UI 而不是整页白屏。
- **封装方式**：写一个通用 `ErrorBoundary` 类组件，`state.hasError` + 备用 UI（"页面出错了，点击重试/刷新"，埋点上报错误）。在路由层使用——**每个路由页面（或关键业务区块）包一层**，这样单个页面崩溃只降级该页面，侧边栏菜单等全局框架还在，用户仍能导航到其他页面。
- **为什么是类组件**：React 官方至今没有提供函数组件版本的 Error Boundary hook（社区有 `react-error-boundary` 库封装了 `useErrorBoundary`），这是少数"必须用 class"的场景。
- **捕获范围之外**（高频追问）：Error Boundary **不捕获**事件处理器里的错误、异步代码（setTimeout/请求回调）错误、SSR 错误、以及自身内部的错误。所以"全局异常捕获"要分层：
  - Error Boundary → 渲染异常 + 降级 UI；
  - `window.addEventListener('error')` → 未捕获的同步/资源加载异常；
  - `window.addEventListener('unhandledrejection')` → 未处理的 Promise rejection；
  - Axios 响应拦截器 → 接口异常统一提示；
  - React 18 里还可配 `onUncaughtError` / `onCaughtError`（createRoot 的回调）。

#### Q7：（八股追问）SSE、WebSocket、轮询怎么选型？📌

**参考回答要点：**
- **轮询/长轮询**：实现最简单、兼容性最好，但无效请求多、实时性差，适合低频数据；
- **SSE**：基于 HTTP 的**单向**服务端推送，`EventSource` API 自带断线重连和 `Last-Event-ID` 续传，文本协议，天然过 HTTP 代理/网关；缺点是只能服务端→客户端、默认有浏览器同域连接数限制（HTTP/1.1 下 6 个）、IE 不支持（需 polyfill）；
- **WebSocket**：全双工、二进制支持、低延迟，但协议升级（ws://）、需要单独处理心跳重连、穿透代理更复杂。
- **选型结论**：LLM 流式输出、状态推送这类"只要服务端往下推"的场景，SSE 是最贴合的（我们 Agent 对话、设备监控都用它）；需要双向实时（协作编辑、游戏、语音）才上 WebSocket。
- 追问"LLM 为什么用 SSE"：token 逐个生成的体验需求 + 请求仍是 HTTP 语义（鉴权头、网关兼容）+ 断线续传协议内建。

### 1.5 贡献五：体验优化 —— 业务模块开发 + 响应式重构 + 渲染性能治理

**简历原文：** 负责用户管理、平台概览、召回测试、敏感词库等模块开发，基于 Tailwind CSS 重构响应式布局，解决知识库卡片频繁重绘、菜单样式异常及页面拉伸问题，提升多分辨率适配能力与交互体验。

#### Q1：这几个模块分别做了什么？（被问"还做过什么"时的展开）⚠️

**参考回答思路：**
- **用户管理**：用户/用户组/角色的 CRUD 列表 + 表单（对应权限治理的业务载体），含分页、搜索、状态切换、授权操作；
- **平台概览**：数据看板类页面——调统计接口渲染各类图表/指标卡（应用数、会话数、Token 消耗、知识库数量等）；
- **召回测试**：知识库检索效果评测功能（详见 Q2，这是最"AI 味"的模块，容易被单独追问）；
- **敏感词库**：敏感词的增删改查 + 批量导入，供对话/输入内容过滤使用。

#### Q2：召回测试是什么？怎么做的？⚠️（AI 高频考点）

**参考回答思路：**

召回测试是**评估知识库检索（RAG 召回）质量的工具**：用户输入一组测试问题（和期望命中的文档/分段），系统对每个问题走一遍真实检索链路（Embedding → 向量检索 → 可选重排），然后统计命中情况。

核心指标：
- **召回率（Recall）**= 命中的期望文档数 / 期望文档总数，衡量"该找到的有没有找到"；
- **命中率 / 命中率@K（Hit Rate@K）**= Top-K 结果里包含期望文档的测试占比；
- 还能展示每个问题的 Top-K 分段和相似度分数，帮助用户调参（chunk 大小、top_k、相似度阈值、是否开重排）。

前端工作：测试集管理、发起批量测试、进度与结果展示（每题命中/未命中、命中文档高亮）、指标汇总。**面试若被问"RAG 全链路"**：文档加载 → 切分（chunk）→ Embedding 向量化 → 存向量库 → 查询时问题同样向量化 → 相似度检索 top_k →（可选 rerank 重排）→ 拼上下文给 LLM 生成答案。

#### Q3：知识库卡片频繁重绘是什么问题？怎么定位、怎么解决的？📌

**参考回答：**

知识库页面有一个卡片列表。排查发现父组件的一些状态变化（比如**搜索关键词输入**、其他页面状态更新）会导致整个卡片列表频繁重新渲染。

**定位手段**：React DevTools 的 Profiler（高亮重复渲染的组件、看每次 render 耗时和原因）+ 分析哪些 props 每次都是新引用。

**解决：**
1. 对不需要随这些状态更新的卡片组件做 **`React.memo`**，只有自身相关 props 变化时才重渲染；
2. **组件拆分**：把搜索框从父组件抽离成独立子组件，让搜索关键词这个高频变化的状态下沉，不再触发父组件（进而整个列表）重渲染；
3. 传递给列表的回调/对象注意引用稳定（`useCallback`/`useMemo`），否则 memo 会失效。

**升华：** 这是 React "状态驱动 UI"模型的典型代价——状态放得越高，波及面越大；优化方向就是**状态下沉（放离使用处最近的组件）+ 渲染隔离（memo）**。

#### Q4：（八股追问）React.memo、useMemo、useCallback 的区别和原理？⚠️

**要点式回答：**
- **React.memo**：高阶组件，浅比较 props，没变就跳过整个子组件的重渲染；
- **useMemo**：缓存**计算结果**，依赖不变不重算，常用于昂贵计算或保持对象引用稳定；
- **useCallback**：缓存**函数引用**，依赖不变返回同一函数，服务于"传给 memo 子组件的回调"引用稳定（`useCallback(fn, deps)` ≈ `useMemo(() => fn, deps)`）。
- 共同陷阱：**浅比较**——props 里传新对象/新数组字面量、每次 render 重新创建的函数都会让 memo 失效；过度使用反而增加比较开销，先测再用（Profiler 定位）。

#### Q5：菜单样式异常和页面拉伸分别是什么问题？📌

**参考回答：**

**菜单样式异常**：菜单的激活/高亮状态和页面路由状态没有完全同步，部分页面切换后菜单高亮显示错误。我检查了路由匹配逻辑和组件状态来源，让菜单选中态**统一由当前路由计算得出**（单一数据源，而不是各自维护一份状态），并调整了相关 CSS，保证切换页面和展开子菜单时样式正确更新。

**页面拉伸（弹窗被内容撑开）**：部分弹窗在特定内容/动态数据加载后被内部组件撑开变形。通过 DevTools 检查 DOM 的实际计算宽高，定位到 **flex 子元素的内容约束问题**：flex 容器内子元素默认 `min-width: auto`，内容（长文本、表格）宽于容器时不会收缩而是撑破布局。解决是补 `min-width: 0`（配合 `overflow` 处理如 `truncate`）、内部滚动，以及调整响应式断点，避免内容把 Dialog 撑开。

**背后八股（必会被追问）：**
- `min-width: auto` 是 flex item 的默认值，导致内容不收缩——设 `min-width: 0` 或 `overflow: hidden` 才允许收缩，这是 flex 布局经典坑；
- 重排（reflow，几何变化）与重绘（repaint，外观变化）的区别，`width/height/top` 触发重排、`color/background` 只重绘；批量读写 DOM、`transform` 代替几何动画可减少重排。

#### Q6：为什么用 Tailwind？响应式怎么做的？Tailwind 原理和缺点？⚠️

**参考回答思路：**
- **为什么**：原子化 class 组合开发快、和组件化契合（样式跟着组件走，没有起名/样式冲突问题——天然 scoped）、JIT 引擎产物小、团队统一间距/配色约束（设计 token 化）；
- **响应式**：Tailwind 移动优先，`sm: md: lg: xl:` 前缀生成媒体查询断点，例如 `w-full md:w-1/2 lg:w-1/3` 实现三档卡片栅格；配合 `flex/grid` 完成多分辨率适配（简历里"多分辨率适配能力"对应的就是这类工作）；
- **原理**：扫描源码中出现的工具类，JIT 按需生成对应 CSS（PostCSS 插件），产物只包含用到的类；
- **缺点（答出来是加分）**：HTML 里 class 冗长、和组件库样式覆盖调试成本、动态拼接类名（`text-${color}`）无法被 JIT 静态分析收集会失效——需要用完整类名映射对象。

#### Q7：（追问）页面首屏慢 / 白屏久，你会怎么排查优化？📌（通用性能题，对应"体验优化"贡献）

**参考回答：** 先定位再优化：**Network 面板**看资源体积和加载瀑布（哪个 JS/图片最大最慢）、**Performance/Lighthouse** 看长任务和渲染瓶颈。然后分三层：
- **资源层**：路由懒加载（React.lazy + Suspense）、代码分割、第三方按需引入、图片压缩/WebP/懒加载；
- **请求层**：首屏请求合并并行（Promise.all）、接口缓存、骨架屏；
- **渲染层**：组件更新范围控制（memo/状态下沉）、虚拟列表（长列表）、防抖节流。
口径：**先测量定位瓶颈，再针对性优化，不盲目加配置**。

### 2.1 贡献一：权限体系 —— RBAC 动态路由与菜单权限联动

**简历原文：** 基于 Vue Router + Pinia 实现 RBAC 动态路由与菜单联动，处理 Token 鉴权、角色路由加载及退出登录后的路由状态清理。

#### Q1：结合项目讲讲你对 RBAC 的理解，前端动态路由和权限控制是怎么实现的？📌

**参考回答：**

RBAC 核心是**基于角色进行访问控制**：用户、角色、资源权限三者关联，用户通过角色获得菜单、接口、数据权限，而不是直接给每个用户配权限。

结合流量调度平台，前端主要做**动态路由和菜单权限控制**：
1. **登录**：用户登录后拿到 Token，请求用户信息接口，后端根据身份返回角色和权限标识；
2. **路由生成**：前端维护"完整路由表 + 每个路由的所需权限 meta"，拿到权限数据后**过滤出该用户有权限的路由**，用 `router.addRoute()` 动态注册；菜单由这份过滤后的路由表直接生成，**路由和菜单天然联动**（同一数据源）；
3. **路由守卫**：`router.beforeEach` 里判断——未登录跳登录页；已登录但未加载权限则先拉权限再放行；访问无权限路由跳 403/首页；
4. **退出清理**：退出登录时清 Token、清 Pinia 里的权限状态、**重置路由**（把动态加的路由移除，见 Q6）。

同时明确边界：前端权限控制是**体验层**的（不显示、拦导航），真正的接口权限和数据权限由后端校验，**不能只靠隐藏菜单保证安全**。

#### Q2：动态路由具体怎么加的？404 路由有什么坑？⚠️

**参考回答思路：**

- 两种常见模式：① **前端全量路由表 + 权限过滤**（路由都在前端，按 `meta.roles` 过滤后 addRoute）——我们项目路由可控、团队小，用这种简单直接；② **后端返回路由表**，前端按 component 字符串映射组件（`import.meta.glob` / `components map`）动态拼装——适合路由由服务端权限系统统一管理的场景。
- Vue Router 4 的 `addRoute` 只能逐条或按路由配置添加，注意 `addRoute` 返回移除函数。
- **404 坑（必被追问）**：`path: '/:pathMatch(.*)'` 的 404 路由如果**在静态路由里先注册**，刷新页面时动态路由还没加，访问任何动态路径都会先匹配到 404。解法：404 路由**放在动态路由全部 addRoute 之后再添加**（或 `addRoute` 后用 `return to.fullPath` 重进一次导航）。

#### Q3：路由守卫里"已登录但权限未加载"怎么处理？刷新页面权限还在吗？⚠️

**参考回答思路：** 权限数据放 Pinia；页面刷新后 Pinia 状态丢失（除非持久化插件），所以守卫里判断"有 Token 但 Pinia 里没有权限数据 → 先请求用户信息/权限 → addRoute → `next(to.fullPath)` 重新走一次导航"。注意避免死循环（加个 loading 标记）。也可以说我们用了 pinia 持久化（如配了插件）把权限/用户信息存 localStorage——按实际情况二选一，别两个都说。

#### Q4：Token 存哪里？localStorage 和 Cookie 怎么选？📌

**参考回答要点：**
- **localStorage**：容量大、不自动发送、API 简单，前后端分离 + `Authorization` 头注入的常用选择（我们项目就是 Token 存 localStorage，Axios 拦截器统一注入）；缺点是**任何 JS 都能读**，容易被 XSS 拿走；
- **Cookie（HttpOnly）**：服务端设置 HttpOnly 后 JS 不可读，天然防 XSS 窃取，且自动携带；但有 CSRF 风险（需 SameSite 配合）；
- 结论：**没有绝对安全，只有风险权衡**——HttpOnly Cookie 防 XSS 窃取但防不了 CSRF（要配 SameSite/CSRF token）；localStorage 防 CSRF 但怕 XSS。企业内部系统常用 localStorage + 严格转义防 XSS。

#### Q5：（追问）Token 过期怎么处理？了解无感刷新吗？⚠️

**参考回答思路：** 常见三种：① 过期返回 401 → 跳登录页（简单体验差）；② 双 Token（access 短有效期 + refresh 长有效期）：Axios 响应拦截器捕获 401，用 refresh 换新 access，**把失败期间的请求存队列，刷新成功后重放**——注意并发 401 只触发一次刷新（加锁）；③ refresh 也过期才真正跳登录。要点词：请求队列、重放、防循环（刷新接口本身 401 直接登出）。

#### Q6：退出登录后路由状态怎么清理？为什么必须清？⚠️

**参考回答思路：** Vue Router 的路由表注册后是**全局累积**的——`addRoute` 加的动态路由在退出后仍在内存里。如果只清 Token 不清路由：换个低权限账号登录，旧账号的高权限路由还在（菜单也许重新生成了，但**直接输 URL 仍能匹配到旧路由组件**），造成越权页面可见。清理方式：① 保存每个 `addRoute` 的返回值，退出时逐个调用移除；② 更常用的——把动态路由注册封装成函数，Router 实例的 `matcher` 重置 / 或新版本用 `removeRoute` 按名称移除；③ 同时清 Pinia 权限状态（`store.$reset()` 或逐字段清空）并 `router.push('/login')`。

#### Q7：菜单权限、接口权限、数据权限的区别？📌

**参考回答：** 菜单权限解决"**能不能看到这个功能**"（前端控制显示隐藏）；接口权限解决"**能不能调这个接口**"（后端对每个请求鉴权，前端配合 403 处理）；数据权限解决"**调通接口后能看到哪些数据**"（查询按归属/角色过滤）。前端主要参与第一层和第三层的展示配合，后两层必须后端兜底。这一题在农担平台权限治理部分还会深挖（漏查串查），注意两个项目的权限粒度差异：流量调度平台做的是**前端路由/菜单层**，农担平台做的是**后端数据权限链路**——面试要能分开讲清楚。

#### Q8：（八股追问）Pinia 和 Vuex 的区别？Pinia 怎么用的？⚠️

**参考回答要点：**
- Pinia：Vue3 官方推荐，**去掉 mutation**（state 可直接改或 `$patch`）、天然 TS 支持、模块化（每个 store 独立 defineStore，不用嵌套模块）、支持组合式写法、devtools 集成、可插件持久化；
- Vuex：mutation/action 分离、单 store 树 + modules 嵌套，TS 支持弱；
- 项目用法：`useUserStore`（token、用户信息、权限列表、动态路由标记）、`useAppStore`（菜单折叠等 UI 状态）之类，组件里 `storeToRefs` 解构保持响应式（直接解构会丢响应式——追问点）。

### 2.2 贡献二：配置编排 —— ELB 监听器五步配置向导

**简历原文：** 负责天翼云 ELB 监听器五步配置向导开发，拆分多步骤表单组件，管理跨步骤状态、参数校验与流程流转，支持服务器组新建及复用。

> ⚠️ 本条原始记录未覆盖，以下按简历描述 + 多步表单通用最佳实践整理，**面试前务必对照实际代码确认每步的配置项名称与状态管理细节**。

#### Q1：五步向导的整体设计？为什么要拆组件？⚠️

**参考回答思路：**

- 业务：创建 ELB 监听器要依次配置（按天翼云 ELB 概念）**监听协议/端口 → 后端服务器组 → 转发策略/访问控制 → 健康检查 → 确认提交**这类多步信息（具体五步名称按实际项目说）；
- 设计：**每步一个独立子组件**，父组件（向导容器）用 `el-steps` 展示进度 + `<component :is>` 或 v-if 切换当前步骤；
- 为什么拆：单步表单独立维护（校验规则、字段、联动都收敛在自己组件里）、可读性和可维护性、避免一个巨型表单组件；
- 数据流：**跨步骤共享的表单数据提升到父级**（或 Pinia），由父组件统一持有整个向导的 model；子组件通过 `v-model` / props + emit 读写自己那部分字段。

#### Q2：跨步骤状态怎么管理？放组件里还是 Pinia？⚠️

**参考回答思路：** 默认**状态提升到向导父组件**（一个聚合的 form model 对象，每步组件只操作自己的分片）——向导是一次性流程，结束即释放，没必要进全局 store。**例外**：如果要求"中途关掉浏览器、下次继续配"（草稿）或者步骤间数据量超大、多处复用，才考虑 Pinia + 持久化。能说出"状态放最低必要层级"这个原则即可。

#### Q3：每一步的校验怎么做？"下一步"和"最终提交"分别校验什么？⚠️

**参考回答思路：**
- **每步独立校验**：每步组件内自己持有 `el-form` 的 rules，点"下一步"时 `formRef.validate()`，通过才 `currentStep++`——保证用户填一步对一步，错误即时反馈；
- Element Plus 的 `validate` 返回 Promise，`await` 拿结果；也可以用 `validateField` 只校验部分字段；
- **最终提交前再整体校验一遍**（把所有步骤的 form 引用收集起来逐个 validate，或父级统一 rules）——防止"改了第 1 步、第 3 步已经过不去"的数据被直接提交；
- 条件性必填：rules 支持函数/计算属性动态生成（见贡献四表单治理）。

#### Q4：用户点"上一步"再回来，数据还在吗？"下一步"之后还能改前一步吗？⚠️

**参考回答思路：** 因为数据提升在父组件持有、步骤组件只是切换显示（**v-show 保留 DOM / v-if 销毁重建但数据在父级**），所以回退数据天然还在——这是"状态提升"设计的直接收益。如果 v-if + 数据在子组件内部就会丢，所以数据必须在父级。"下一步之后修改前一步"要注意级联：前一步改了协议（如 HTTP→HTTPS），后一步健康检查的默认端口/可选值要跟着重算——监听关键字段 watch 清理下游字段。

#### Q5："服务器组新建及复用"怎么实现的？⚠️

**参考回答思路：** 向导里选后端服务器组时提供两种路径：① **复用已有**——下拉拉取服务器组列表（展示名称/协议/后端主机数），选中回填其配置；② **新建**——内嵌一个创建服务器组的子表单/子对话框（选 VPC、添加主机、端口），提交成功后把新组 id 塞回向导并选中。注意点：新建成功后要**刷新下拉数据源**；复用模式展示只读信息、新建模式展示可编辑表单（同一区域的两种形态切换）。

#### Q6：向导做到一半用户直接关页面/跳走怎么办？（追问预备）⚠️

参考思路：未保存数据会丢。可选方案：① `beforeRouteLeave` / `onBeforeRouteLeave` 守卫提示"配置未保存确认离开"；② `beforeunload` 提示（浏览器级）；③ 草稿持久化（Pinia + localStorage，进入向导时检测草稿询问恢复）。答出"提示 + 可选草稿"层次即可，别硬说做了没做的。

#### Q7：（八股追问）v-model 的原理？在组件上怎么用？⚠️

**参考回答要点：** 表单元素上 `v-model` 是 `:value` + `@input` 的语法糖（Vue3 改为 `modelValue` + `update:modelValue`）；组件上使用需子组件 `props: ['modelValue']` + `emit('update:modelValue', val)`，Vue 3.4+ 可用 `defineModel()` 宏简化；支持**多个 v-model**（`v-model:title`）和修饰符（`.lazy` change 才同步、`.number` 转数字、`.trim` 去空格）。向导里"每步表单绑定父级 model 的分片"就是组件 v-model 的典型用法。

### 2.3 贡献三：接口协同 —— 依赖梳理 + 参数转换 + 多接口串联

**简历原文：** 梳理主机、服务器组与监听器之间的依赖关系，封装接口参数转换与数据适配逻辑，串联多接口调用流程，处理不同配置模式下的参数差异。

> ⚠️ 本条原始记录未覆盖，按简历描述 + 接口联调通用实践整理，请结合实际接口字段核对。

#### Q1：主机、服务器组、监听器之间的依赖关系是什么？⚠️

**参考回答思路（按天翼云 ELB 概念）：**
- **主机（后端服务器）**是最底层资源（IP + 端口）；
- **服务器组（后端服务器组）**把若干主机组织成组，定义组级协议/端口/健康检查；
- **监听器**挂在 ELB 实例上，按协议+端口监听流量，**转发给某个服务器组**。
- 依赖链：**主机 → 服务器组 → 监听器**，创建顺序必须自下而上（没有服务器组就建不了监听器；服务器组里没主机就是个空转的组）；展示/编辑时反向：从监听器能下钻到组、从组下钻到主机列表。
- 前端为此做的：级联选择（选监听器 → 过滤可用组；选组 → 过滤可用主机）、按依赖排序的加载时序（先拉组和主机，再拉监听器，避免监听器引用了还没加载的资源显示成 id）。

#### Q2：参数转换与数据适配逻辑怎么封装的？⚠️

**参考回答思路：**
- **为什么需要**：天翼云 API 的参数结构（嵌套、命名）和前端表单 model 不是一一对应——比如前端向导 model 是按步骤扁平组织的，而创建监听器接口要的是嵌套结构（监听器配置 + 内嵌服务器组配置 + 健康检查配置）；
- **怎么封装**：在 API 层和页面之间加**适配层（adapter/转换函数）**——`toRequest(formModel)`（表单 → 接口入参：字段映射、命名转换、默认值填充、嵌套组装）和 `toFormModel(response)`（接口 → 表单：编辑回显时用），集中放 `utils/adapter.ts` 这类文件，**页面不直接拼接口参数**；
- 好处：接口字段变更只改编译层一处；表单结构和接口结构解耦，两边都能独立演进。

#### Q3：多接口串联的调用流程怎么组织？某一步失败怎么办？⚠️

**参考回答思路：** 串联场景如"新建监听器（含新建服务器组）"：① 必要时先创建服务器组拿 group_id → ② 用 group_id 创建监听器 → ③ 成功后刷新列表。组织方式：`async/await` 顺序调用（语义清晰、错误处理集中 try/catch）；无依赖的调用（如同时拉主机列表和组列表）用 `Promise.all` 并行。失败处理分两类：**前置步骤失败直接中止并提示**（还没产生副作用）；**创建监听器成功但后续步骤失败**提示部分成功状态。追加点：后端如果提供了"一步创建"的组合接口，优先用组合接口，前端串联只是没有组合接口时的折衷（多请求、非原子性）。

#### Q4：不同配置模式下的参数差异怎么处理？（四层/七层监听差异）⚠️

**参考回答思路：** ELB 监听器分 **TCP/UDP（四层）**和 **HTTP/HTTPS（七层）**模式，配置项差异大：七层才有转发策略、证书、HTTP 字段；健康检查方式也不同（TCP 探测 vs HTTP 路径探测）。前端处理：向导某步的**表单项按当前协议条件渲染**（v-if），**校验规则和提交参数也按模式动态组装**（适配层根据协议字段走不同分支映射）——即"同一表单骨架 + 模式差异显式分支"，避免把四层七层混在一套字段里靠 if 打补丁。

#### Q5：（追问）快速切换筛选条件时，旧请求后返回覆盖新结果（竞态）怎么处理？⚠️

**参考回答思路：** 经典竞态问题。方案：① **请求标记/序号**：发请求前记 `const id = ++latestId`，回调里 `if (id !== latestId) return` 丢弃过期响应；② **AbortController**：发新请求前 `controller.abort()` 取消旧的（Axios 支持 signal）；③ Vue 生态可用 watch 的 `onCleanup`。能主动讲出"列表页切换筛选要防竞态"是加分项。

#### Q6：（八股追问）Promise.all、allSettled、race、any 的区别？⚠️

**要点式回答：** `all` 全成功才 resolve、一个 reject 整体 reject（适合"都要成功才渲染"）；`allSettled` 等全部落定，返回每个的状态（**批量任务异常隔离**的基础，慢 SQL 批量分析也用到）；`race` 第一个落定者定胜负（超时控制）；`any` 第一个成功者 resolve、全失败才 reject。配合"async/await 的错误要 try/catch 或 .catch，否则 unhandledrejection"一起答。

### 2.4 贡献四：表单治理 —— 条件校验 + 提交控制 + 异常反馈

**简历原文：** 针对访问控制、VPC、健康检查等配置实现条件校验、提交控制及异常反馈，增强复杂配置流程的稳定性与可维护性。

> ⚠️ 本条原始记录未覆盖，按简历描述 + Element Plus 表单实践整理。

#### Q1：条件校验怎么实现？举个实际例子 ⚠️

**参考回答思路：**
- Element Plus 的 rules 支持**动态化**：把 rules 写成 `computed`，根据当前表单值返回不同规则；或在 rule 里用**自定义 validator**（`(rule, value, callback) => {...}`），validator 内部读取同级其他字段做联动判断；
- 实例（结合项目业务）：
  - **访问控制**：开启"访问控制"开关后，白名单/黑名单列表**从选填变必填**，且 IP 列表要逐项校验 IPv4 格式（正则或 `validator`）；
  - **健康检查**：检查方式选 HTTP 时，**检查路径变必填**且要校验以 `/` 开头；选 TCP 时路径字段隐藏并不参与提交；
  - **VPC/端口**：源端口 1~65535 范围校验，且某些协议下端口互斥；
- 联动字段变化时要**手动触发对方重校验**（`validateField`）或用 `watch`——否则"先填好、后改条件"会留下过期校验状态。

#### Q2：提交控制怎么做？怎么防重复提交？⚠️

**参考回答思路：** ① **loading 锁**：提交按钮 `:loading="submitting"`（loading 态按钮自动不可点）；② 提交函数入口 `if (submitting) return` 双保险；③ finally 里复位 loading（失败也要复位）；④ 大表单提交前 `await formRef.validate()` 通过才发请求；⑤ 二次确认（`ElMessageBox.confirm`）用于危险或不可逆操作。追加点：只靠按钮 disabled 不够——回车/快捷键仍可能触发 submit，函数级锁才可靠。

#### Q3：异常反馈怎么设计的？（表单错误 vs 接口错误分层）⚠️

**参考回答思路：** 分三层：
1. **字段级**：rules 校验失败，表单项下方红字 inline 提示 + 输入框红框（Element Plus Form 自带）；提交时可 `scrollIntoView` 滚动到第一个错误字段（长表单体验关键点）；
2. **页面级**：接口返回的业务错误（4xx/业务码非 0）用 `ElMessage`/`ElNotification` 全局提示，错误信息**转成用户能懂的话**而不是直接抛 code；
3. **流程级**：多步向导里失败要明确"卡在第几步、哪个配置项冲突"（比如端口被占用），并保留用户已填数据不丢失。
可维护性：错误提示文案统一收口（错误码 → 文案映射），避免散落各组件。

#### Q4：（八股追问）Element Plus 表单校验的原理？async-validator 了解吗？⚠️

**参考回答思路：** Element Plus 的 Form 组件校验底层用 **async-validator** 库：rules 声明式描述字段约束（required/type/pattern/min-max/validator/trigger），Form 收集所有 FormItem 的上下文（prop 定位字段），`validate()` 时逐字段异步执行规则返回 Promise。触发时机 trigger：`blur`/`change` 各自绑定。自定义 validator 处理复杂/联动规则。知道"声明式规则 + 异步校验器"这个模型即可。

## 三、项目三：电信 IT 慢 SQL 分析系统

**项目时间：** 2025-10 ~ 2025-11　**角色：** 前端开发
**技术栈：** React + TypeScript + Redux + Ant Design + React Router + Axios
**项目描述：** 面向电信 IT 运维场景的慢 SQL 分析平台，提供慢 SQL 查询、分析及报告导出能力，帮助运维和开发人员快速定位数据库性能瓶颈。

### 项目 30 秒介绍

> 这是给电信运维用的慢 SQL 分析工具：上传含慢 SQL 的文件，系统分析后给出性能诊断和优化报告。项目到我接手时页面和 Mock 数据已经有一部分，我负责四块：真实接口联调（清理 MockJS、做字段适配）、多文件批量分析的并发管理和失败重试、按文件维度的结果聚合与报告下载、PDF 导出适配。这个项目技术上最有含量的是**前端并发任务管理**那部分。

### 3.1 贡献一：接口接入 —— Axios 联调 + Mock 清理 + 数据适配

**简历原文：** 基于 Axios 完成业务接口联调与数据适配，清理遗留 MockJS 逻辑，处理接口字段差异及响应结构不一致问题，打通页面与真实业务数据链路。

#### Q1：接口联调的完整流程说一下？"清理 MockJS 逻辑"具体清了什么？📌

**参考回答：**

联调流程：**对接口文档（或后端 Swagger）→ 封装 API 函数 → 处理响应结构差异 → 联调字段级问题 → 走通异常分支**。

这个项目特殊点是**存在遗留的 MockJS**：项目早期用 MockJS 拦截请求返回假数据（它劫持 XHR/fetch，按 URL 规则匹配返回 mock 响应）。我接手联调时的问题：**部分接口还挂在 mock 规则上，真实请求根本没发出去**；而且 mock 数据的字段结构和后端真实返回不一致。

清理工作：
1. 移除 mock 规则注册和 MockJS 依赖（或配置开关，只在无后端环境启用）；
2. 逐页面对照后端真实返回**适配字段差异**（mock 里 `name`，真实接口 `instanceName`；mock 数组直接返回，真实接口包在 `data.records` 里）；
3. 处理**响应结构不一致**：不同接口有的返回 `{code, message, data}`，有的直接返回数据体，统一在 Axios 响应拦截器里归一；
4. 异常分支验证：401/500/空数据/超时各走一遍，补齐 loading 和错误提示。

#### Q2：MockJS 的原理是什么？有什么副作用？（追问预备）⚠️

**参考回答思路：** MockJS 在**前端拦截 XHR**（重写 XMLHttpRequest 的 open/send 等方法），URL 命中规则时不发真实请求、按模板生成假响应回调。副作用（都是联调真实踩坑点）：① 拦截是全局的，规则没删干净时请求被"吞掉"，Network 面板**看不到请求**（因为根本没发）；② mock 响应没有真实 HTTP 状态码/头，一些依赖 headers 的逻辑（下载、鉴权）测不了；③ 和 Vite/TS 环境结合时类型全是 any。所以现代项目更倾向用 msw（Service Worker 层拦截）或独立 mock server / proxy。

#### Q3：字段差异和响应结构不一致，你是改前端还是推后端改？⚠️

**参考回答思路：** 判断标准：**接口契约是否已对外/是否多人依赖**。
- 后端已稳定、多人消费的接口 → 前端做适配层（转换函数统一处理），不动接口；
- 后端还在开发期、结构明显不合理（列表不返回 total、时间戳格式不统一、code 语义混乱）→ 推动后端在契约层统一（这类问题每个前端都要再写一遍适配，成本更高）；
- 折衷：先前端适配保联调节奏，同时提给后端排期统一。
体现的素质：**契约意识 + 沟通推动**，不是闷头全自己兜。

#### Q4：Axios 二次封装你是怎么做的？拦截器里处理什么？📌

**参考回答：**

封装目标：**统一请求入口、统一认证和异常处理，减少业务代码重复逻辑**。

1. **创建统一实例**：集中配置 `baseURL`（来自环境变量 `import.meta.env.VITE_API_BASE_URL`，配合 Docker 构建参数注入，见实习专项四）、超时时间、公共 headers；
2. **请求拦截器**：从本地取 Token 注入 `Authorization` 头；按需处理公共参数；
3. **响应拦截器**：
   - 成功：判断 HTTP 状态 + 后端业务码，直接**把业务 data 提取出来返回**，业务代码不用层层剥 `.data.data`；
   - 401：统一处理登录失效（清状态跳登录）；
   - 其他异常：统一错误提示（Message 弹错）、把错误转成统一结构 reject，调用方只需 catch 处理业务特例；
   - 网络超时/服务器错误（Axios error）也在这一层统一兜。

业务组件只关心"传什么参数、拿到数据怎么渲染"。

**追问预备：** Axios 拦截器执行顺序（请求拦截后注册先执行、响应拦截先注册先执行）；Axios 底层是 XMLHttpRequest（浏览器端），所以能被 MockJS 拦截；XHR vs fetch 的区别（fetch 原生、默认不拒绝 4xx/5xx、需要手动处理 JSON 和超时）。

#### Q5：联调时跨域怎么处理的？CORS 原理说一下 ⚠️

**参考回答思路：**
- 开发环境：Vite dev server `server.proxy` 把 `/api` 代理到后端（同源无跨域）；生产环境：Nginx `proxy_pass` 反向代理，或后端直接配 CORS 响应头；
- CORS 原理：浏览器同源策略限制脚本跨域读响应；跨域请求分**简单请求**（GET/POST/HEAD + 有限 headers）直接发送但响应要带 `Access-Control-Allow-Origin` 才可读；**非简单请求**（自定义头如 Authorization、PUT/DELETE、JSON Content-Type 触发预检的细节）先发 **OPTIONS 预检**，服务端放行后才发真实请求；
- 带 Cookie 时要 `withCredentials` + 服务端 `Allow-Credentials` 且 Origin 不能是 `*`；
- 常见报错场景：预检被 Nginx/网关拦截、允许的头没包含 `Authorization`。

### 3.2 贡献二：并发管理 —— 多文件批量分析 + 状态跟踪 + 异常隔离 + 失败重试

**简历原文：** 完成慢 SQL 多文件批量分析流程，支持文件批量提交、并发任务状态跟踪及独立结果下载；通过任务状态管理与异常隔离，支持单文件失败重试，避免单个任务异常影响其他文件处理。

#### Q1：整体讲一下多文件批量分析是怎么设计的？📌

**参考回答：**

业务场景：运维一次性上传多个 SQL 文件，平台逐个分析并产出报告。整体流程：

1. **批量提交**：用户多选文件上传，每个文件创建一个分析任务，后端返回任务标识（任务 id + 文件名映射）；
2. **并发控制**：前端不是把所有任务同时打出去，而是**维护并发池**（同时最多 N 个任务在"提交/分析中"状态），完成一个补位一个，避免瞬时打爆后端；
3. **状态跟踪**：每个任务维护独立状态机（上传中 → 排队 → 分析中 → 成功/失败），轮询或状态接口刷新；
4. **异常隔离 + 单文件重试**：单个文件失败只标记该文件为失败态、给出错误原因，**不影响其他文件继续跑**；用户可对失败文件单独点"重试"，只重传/重分析那一个；
5. **独立结果下载**：成功的文件各自有报告下载地址。

**回答点题句：** 这套东西本质是在前端实现了一个**轻量任务调度 + 状态机**：状态隔离保证互不干扰，并发池保证吞吐可控。

#### Q2：并发控制具体怎么实现的？为什么不一次全并发？⚠️

**参考回答思路：**
- **为什么不全并发**：浏览器对同域 HTTP/1.1 有 6 个连接的限制，多余请求排队；一次性全发后端瞬时压力大，容易超时/限流，失败率反而上升；上传场景还抢带宽。
- **实现（手写并发池思路）**：维护"执行中任务集合"，`while (pool.length < N && queue.length)` 取任务启动；每个任务 `finally` 里从 pool 移除并补位。伪代码：

```ts
async function runPool(tasks: Task[], limit = 3) {
  const executing = new Set<Promise<void>>();
  for (const task of tasks) {
    const p = Promise.resolve().then(() => task.run()).finally(() => executing.delete(p));
    executing.add(p);
    if (executing.size >= limit) await Promise.race(executing);
  }
  await Promise.allSettled([...executing]);
}
```

- 能提 `p-limit` 库（功能等价）也行，但手写思路必须会说。

#### Q3：异常隔离怎么实现？"单文件失败不影响其他文件"技术上靠什么？⚠️

**参考回答思路：** 关键两点：
1. **Promise.allSettled 而不是 all**——all 会"一坏全坏"（第一个 reject 整体 reject，其余结果丢弃）；allSettled 等全部落定并保留每个成功/失败结果；
2. **每个任务独立 try/catch + 独立状态存储**（以文件 id 为 key 存状态，互不共享中间变量），一个任务抛错只更新自己的状态为 failed，调度循环继续；
3. UI 层：失败行显示原因 + 重试按钮，成功行正常出下载入口——**状态按文件维度隔离展示**。
加一句升华：这其实是把"批处理容错"原则搬到前端——**隔离故障域、保留部分成功**。

#### Q4：单文件失败重试怎么做的？重试要注意什么？⚠️

**参考回答思路：** 重试 = 以该文件的参数重新走一遍提交流程，成功后把状态从 failed 改回 analyzing 继续跟踪。注意点：
- 重试也要**走并发池**（用户一次点 5 个重试，不能绕过限流）；
- 防重复点击（重试按钮 loading）；
- 如果后端任务有幂等要求，重试带上原任务 id 或客户端生成的去重键，避免重复创建分析任务；
- 追问"自动重试"：瞬时错误（网络抖动）可自动退避重试（指数退避 1s/2s/4s，设上限 3 次），业务性错误（文件格式非法）自动重试无意义必须人工处理——**区分错误类型再谈重试**是加分点。

#### Q5：大文件上传还做了分片，讲讲分片上传的方案？📌

**参考回答：**

当时场景是要上传较大的 SQL 文件做分析，普通单次上传的问题：**上传时间长、网络一抖整个文件重来、大请求容易超时**。

方案是**文件切片 + 分片上传 + 后端合并**：
1. 前端把文件按固定大小切片（`file.slice(start, end)`，Blob API，本身不占内存拷贝）；
2. 每个分片维护独立上传状态，逐个/受控并发上传（带分片索引和文件标识）；
3. 后端根据文件标识 + 分片信息合并成完整文件。

**主要难点是上传状态管理和数据一致性**：一个大文件对应多个分片，不能用一个状态表示整个文件——要区分**文件整体状态**和**分片状态**，按分片结果聚合更新整体进度；接口失败时要知道是**哪个分片失败**，只重传该分片而不是整个文件重来。

**体会句：** 大文件上传不只是"把文件拆开"，前端要设计好分片状态、进度聚合、失败定位和前后端分片信息对齐，才真正提升稳定性。

**追问预备（高频）：**
- **断点续传**：进页面先调"已上传分片列表"接口（或按文件 hash 查询），跳过已传分片；
- **秒传**：上传前算文件整体 hash（大文件算 MD5 慢，可用 Web Worker 或抽样 hash），后端存在同 hash 文件直接返回成功；
- **hash 计算放哪**：Web Worker 里算，避免阻塞主线程导致页面卡死（关联事件循环八股）。

#### Q6：（八股追问）浏览器事件循环：为什么 hash 计算要放 Web Worker？⚠️

**要点式回答：** JS 单线程，主线程被长任务占用时 UI 无法响应（渲染和 JS 执行互斥）；事件循环机制——调用栈清空后按序取**微任务**（Promise.then、queueMicrotask，每轮清空）再取一个**宏任务**（setTimeout、I/O、事件回调），`await` 后续代码是微任务。Web Worker 是独立线程，不能操作 DOM 但能算密集任务，通过 `postMessage` 传结果。追问 `setTimeout(fn, 0)` 不是立即执行（要等当前栈+微任务清空）。

### 3.3 贡献三：分析结果 —— 任务/结果映射 + 状态聚合 + 报告下载

**简历原文：** 根据文件维度维护分析任务与结果映射，聚合各文件的分析状态及下载地址，支持多份分析报告分别下载，提升批量运维场景下的分析效率与结果管理能力。

> ⚠️ 本条原始记录未覆盖，按简历描述 + Redux 项目实践整理。

#### Q1：任务与结果的映射数据结构怎么设计的？⚠️

**参考回答思路：** 以**文件标识（fileId/taskId）为 key** 维护映射，而不是用数组下标——接口刷新、重试、排序后 key 依然稳定。典型结构：

```ts
// Redux state
tasksById: {
  [taskId]: {
    fileId, fileName, status: 'uploading'|'queued'|'analyzing'|'success'|'failed',
    progress, errorMsg, reportUrl?, analyzedAt
  }
},
taskOrder: string[]  // 保持列表顺序，渲染时 map 取详情
```

好处：状态更新精确到单个任务（`state.tasksById[id].status = 'analyzing'`），符合 Redux 不可变更新粒度；顺序和内容分离，列表操作不碰任务详情。这个"normalize 数据"思想同样适合主机/服务器组这类有关联的资源（按 id 索引 + 关联存 id 数组）。

#### Q2：各文件状态怎么聚合展示的？"全部完成"怎么判断？⚠️

**参考回答思路：**
- 派生状态用 selector 计算：总进度 = 各任务进度加权（或按分片数占比）；**整体批次状态由所有任务状态推导**——全部 success → 批次完成；存在 failed → 批次"部分失败"（提示哪些文件可重试）；有 analyzing → 进行中；
- 派生数据不存 state（单一数据源原则），用 `useMemo`/reselect 按需计算，避免状态不同步；
- UI 上：汇总条（N 成功 / M 失败 / K 进行中）+ 每行独立状态和操作。

#### Q3：报告下载在前端有几种实现方式？你们用哪种？⚠️

**参考回答思路：**
1. **后端返回静态 URL**：`<a href={url} download>` 或 `window.open(url)`——最简单，我们项目报告是后端生成后给下载地址，走这种；
2. **Blob 响应下载**：接口直接返回文件流（`responseType: 'blob'`），前端 `URL.createObjectURL(blob)` 创建临时地址再触发 a 标签点击，记得 `revokeObjectURL` 释放；
3. 大文件流式下载用 StreamSaver 之类（提一句即可）。
- 注意点：`download` 属性**同源才生效**，跨域 a 标签 download 会被忽略（会变导航）；要自定义文件名时后端要配 `Content-Disposition`。

#### Q4：这个项目为什么用 Redux？Redux 的原理和流程？⚠️

**参考回答思路：**
- 为什么：项目接手时就定的 React + Redux（历史选型），且批量任务状态（跨页面共享：列表页发起、详情页看进度）适合集中 store；
- 原理/流程：**单向数据流**——`dispatch(action)` → middleware（thunk 处理异步）→ **reducer 纯函数** `(state, action) => newState` → 订阅者（`useSelector`）按引用比较决定重渲染；
- 核心规则：state 不可变（展开运算/spread 更新）、reducer 纯（同样输入同样输出，无副作用）、单一 store；
- **Redux Toolkit**（现代写法）：`createSlice` 自动生成 action 和 reducer、Immer 内置"可变写法"生成不可变更新、`configureStore` 默认配好 thunk 和 devtools——如果被问"为什么还手写 reducer"，答老项目存量代码，新模块用 RTK 或说明了解即可；
- 追问 `useSelector` 性能：按需选字段 + 引用相等比较，避免整个 state 选择导致多余渲染。

### 3.4 贡献四：报告导出 —— PDF 导出适配

**简历原文：** 参与 PDF 导出功能适配，处理导出场景下的数据渲染与页面样式问题，保证分析结果与导出报告的内容一致性。

> ⚠️ 本条原始记录未覆盖（简历用词是"参与"——说明不是主导，回答注意分寸），按前端 PDF 导出常见方案整理。

#### Q1：PDF 导出是什么方案？前端生成还是后端生成？⚠️

**参考回答思路：** 先讲清三种路线和选择逻辑：
1. **后端生成**（服务端用模板/wkhtmltopdf/Playwright 渲染 HTML 转 PDF）：样式还原度可控、不占客户端资源，适合正式报告；
2. **前端生成**：`html2canvas` 把 DOM 截图成 canvas → `jsPDF` 把图片按页塞进 PDF——纯前端可控，但**本质是截图**（文字变图片、不可选中、体积大）；
3. **浏览器打印**（`window.print()` + `@media print` 样式）：零依赖，但体验不可控。
- 我们项目是"参与适配"：在已有导出能力上处理**数据渲染和页面样式问题**（如实说参与部分，别揽成主导）。

#### Q2：导出场景下的"数据渲染与页面样式问题"具体指什么？⚠️

**参考回答思路：** 常见四类（挑实际遇到的说）：
1. **分页断裂**：内容高度不定，表格/图表在分页处被拦腰截断——需要按页高计算分页点，或给关键块设置 `page-break-inside: avoid`；
2. **图片/图表跨域**：html2canvas 画不了没配 CORS 的跨域图片（canvas 被污染），图表库（ECharts 等）导出时要用其自带 `getDataURL` 或服务端同源资源；
3. **样式丢失**：导出容器不在视口内/被 `overflow: hidden` 截断、rem/视口单位在离屏渲染时计算异常——常见做法是渲染一个**专门的导出用 DOM**（隐藏挂载、固定宽度如 794px≈A4@96dpi），而不是直接截页面；
4. **异步数据未就绪**：导出前要等图表动画结束、数据加载完（否则截到 loading 态）。

#### Q3：怎么保证导出报告与页面分析结果一致？⚠️

**参考回答思路：** ① 数据同源——导出视图和页面视图消费**同一份 store/接口数据**，不二次加工产生分叉；② 导出前重新拉取或校验数据版本，避免"页面是旧数据、导出是新数据"；③ 字段格式化（时间、耗时、字节数）统一用同一组 format 工具函数；④ 关键数值（SQL 条数、耗时统计）在导出视图和页面用同一个聚合逻辑（selector 复用）。

### 4.1 AI 智能体平台整体架构类问题

#### Q1：整体讲一下 AI Agent 平台的开发流程 / 架构？📌

**参考回答：**

我一般把它分成 **Agent 配置、工作流编排、任务执行、结果返回** 四部分：

1. **Agent 配置**：用户配置模型、System Prompt、模型参数，绑定知识库和工具（知识库检索、数据库查询、业务 API）；
2. **工作流编排**：复杂任务不让单个 Agent 从头做到尾，而是拆成多个节点——开始节点、LLM 节点、知识库检索节点、工具调用节点、条件判断节点、结束节点。前端用 ReactFlow 画布让用户拖节点、配参数、连线，整张工作流保存成结构化 JSON（详见项目一贡献一）；
3. **后端执行**：用户发问后，后端按节点关系依次执行——LLM 节点调大模型，模型判断需要调工具就执行工具、结果放回上下文继续推理（ReAct 循环的思路），直到产出最终答案；涉及 RAG 时先对问题 Embedding → 向量库相似度检索 → （可选重排）→ 拼上下文给大模型；
4. **结果返回与运行记录**：流式输出（SSE）实时推送生成过程；同时记录每个节点的执行状态、对话记录、Token 消耗、异常信息，方便排查。

**点题句：AI Agent 平台本质是把 LLM 的推理能力、工具调用、知识库和工作流编排结合起来——前端负责配置和可视化编排，后端负责执行和状态管理，最后通过流式接口把结果返回。**

#### Q2：你们的工作流是任务调度器吗？（考察对自己系统边界的认知）📌

**参考回答：**

诚实切割：我们这个工作流本身有执行机制，但我参与的部分**不是 Celery、Airflow 那种独立的任务调度系统**。我主要负责前端编排和节点配置；执行侧后端根据节点类型找执行类、按节点关系执行。从调度角度它更接近**工作流执行层对节点执行顺序的管理**，任务队列、重试、并发控制、定时调度这些完整调度能力我没有深入参与。

**但如果讲理解**，任务调度器负责**任务生命周期和资源调度**：什么时候执行、依赖关系（A 完成才触发 B）、并发数量、失败重试、状态管理（pending/running/success/failed），互不依赖的节点可并行执行。

**面试提示：** 这题考察"知道自己不知道什么"。边界诚实 + 概念清楚，比硬撑说自己实现过调度器好得多。

#### Q3：流式输出前端是怎么接的？和普通请求有什么区别？📌

**参考回答要点：** 前端用 `EventSource`（或 fetch + ReadableStream 处理 POST 场景——EventSource 原生只支持 GET，带鉴权头/POST 体时常用 fetch 流式解析，这是高频追问）连接 SSE 接口，`onmessage` 逐段收到增量 token 追加渲染。和普通请求的区别：连接保持、分多次下发数据、需要管理连接生命周期（组件卸载关闭、重复连接去重——见项目一贡献四）。渲染侧注意：高频 setState 要做节流/合并，否则每个 token 一次 render 会卡（可 60ms 聚合一次再 setState）。

### 4.2 四川统一浏览器认证插件接入（人脸识别 + 前端加密）

**简历原文：** 参与四川统一浏览器认证插件接入，完成人脸识别认证及前端加密方案开发，保障身份认证链路安全。

> ⚠️⚠️ **此条原始记录完全未覆盖**。以下问题与回答框架基于"浏览器认证插件 + 人脸识别 + 前端加密"的通用实现整理，**面试前务必按实际项目核对**：插件是谁提供的（公司/四川政务侧）、加密用的什么算法（国密 SM2/SM4 还是 RSA/AES）、人脸比对在前端还是服务端。宁可说得保守，不要被拆穿。

#### Q1：这个插件接入具体做了什么？⚠️

**参考回答框架（按"参与接入"的口径讲）：**

这是四川侧统一的身份认证浏览器插件（政务/运营商体系里常见的统一认证组件），我们平台的登录链路要接入它。我参与的部分是**前端集成**：按插件提供的 JS-SDK 文档初始化插件、调起认证流程、处理认证回调结果，并配合做了**人脸识别认证环节的前端交互**和**敏感数据的加密处理**，保证身份认证链路安全（不落明文、防篡改、防重放）。

#### Q2：前端加密方案：为什么要前端加密？加密的是什么？⚠️

**参考回答思路（按混合加密通用方案讲）：**

首先要明确一个观念：**前端加密不能替代 HTTPS**，它是传输安全之外的**第二道防线**（防代理抓包直接看到明文、防浏览器插件/日志泄漏敏感字段）。典型做法：

1. **混合加密**：客户端生成随机对称密钥（如 AES/国密 SM4），用它加密业务数据（身份证号、人脸特征等敏感字段）；对称密钥本身用服务端公钥（RSA/国密 SM2）加密后一起上送；服务端私钥解密拿到对称密钥再解数据——兼顾安全性和性能（RSA 加密大数据慢）；
2. **防重放**：请求带时间戳 + 随机数 nonce，服务端校验时间窗口和 nonce 是否重复；
3. **防篡改**：对参数做签名（按 key 排序拼接 + 盐 + 摘要算法）随请求上送，服务端验签；
4. 前端实现可用 Web Crypto API（原生、安全）或厂商 JS 加密库（如 sm-crypto 国密库）。

#### Q3：（追问）密码/敏感信息在前端哈希一下再传，就安全了吗？⚠️

**参考回答要点：** 不安全。前端哈希后"哈希值就是密码"——抓包者直接重放哈希值即可通过校验（撞库传递性）。前端处理的意义有限（防明文直接可见、防服务端日志明文落盘），**真正的安全靠 HTTPS + 服务端侧加盐哈希（bcrypt 等慢哈希）存储 + 一次性 token**。能主动讲出这个误区是明显加分项。

#### Q4：人脸识别认证的前端流程？⚠️

**参考回答思路：**
1. **调起摄像头**：`navigator.mediaDevices.getUserMedia({ video: {} })`，必须 HTTPS/localhost 才可用；权限被拒要有引导（提示去浏览器设置开启/降级其他认证方式）；
2. **采集**：video 流渲染到 `<video>`，到达采集时机时 `canvas.drawImage(video)` 抓帧转 blob 上传（活体检测通常要求做动作——眨眼/张嘴/转头，由插件或服务端下发指令并校验）；
3. **比对**：人脸特征比对在**服务端/认证平台侧**完成，前端只负责采集上传和展示结果，**前端不做比对判断**（结果不可信）；
4. **安全**：图像数据走加密通道上送、不本地留存、及时关闭摄像头流（`stream.getTracks().forEach(t => t.stop())`，否则摄像头指示灯常亮——体验细节加分）。

#### Q5：（追问）getUserMedia 除了摄像头还能做什么？兼容性注意什么？⚠️

**要点：** 麦克风/屏幕共享（`getDisplayMedia`）、音视频流可挂 MediaRecorder 录制；权限需要用户授权且页面安全上下文（HTTPS）；iOS Safari 有各自限制。往 AI 方向还能关联一句：浏览器端机器学习（如 face-api.js / WebGPU）可以做前端活体质量检测，但结论仍要服务端复核。

### 4.3 SSE 长连接 + BroadcastChannel 多标签页复用方案

**简历原文：** 针对设备管理平台 SSE 长连接受浏览器连接数限制的问题，设计并实现基于 BroadcastChannel 的多标签页连接复用方案，由主标签页统一维护连接并同步数据，降低资源消耗，提升页面稳定性。

#### Q1：这个方案的背景和实现思路？为什么用 BroadcastChannel 而不是每个标签页各自建连？📌

**参考回答：**

**背景：** 设备管理平台（服务器主机状态动态监控 + ECharts 展示）存在多标签页同时打开的情况。浏览器对**同域 HTTP/1.1 并发连接数有限制（默认 6 个）**，每个标签页各自建 SSE 长连接会：① 占满连接额度，连普通 API 请求都被阻塞；② 服务端连接数成倍增长。

**方案：多个标签页复用一条 SSE 连接。**
1. **主标签页选举**：多个标签页通过 BroadcastChannel 协商，选出一个 Leader；
2. **主标签页职责**：唯一持有并维护 SSE 连接，收到服务端推送后，通过 `BroadcastChannel.postMessage()` 把消息广播给同源的其他标签页；
3. **从标签页职责**：不连 SSE，只监听 BroadcastChannel 消息并更新自己的页面状态（刷新图表）；
4. **故障接管**：主标签页关闭或连接异常时，其余标签页通过心跳检测感知（一定时间没收到主页心跳），重新选举产生新 Leader 接管 SSE 连接。

**为什么用 BroadcastChannel：** 它就是为**同源多标签页消息广播**设计的浏览器 API，无需服务端任何改造；相比每页一条连接，N 条长连接降为 1 条，同时避免每页重复接收相同数据。

#### Q2：BroadcastChannel、localStorage 事件、SharedWorker、postMessage 怎么对比？⚠️

**参考回答要点：**
- **BroadcastChannel**：同源所有 tab/iframe/worker 广播，API 简洁（onmessage/postMessage），**不跨域、关掉的页面收不到、历史消息不留存（无消息积压）**；
- **localStorage + storage 事件**：兼容老浏览器（storage 事件其他页可监听），但只能传字符串、修改同值不触发、语义绕；
- **SharedWorker**：独立线程唯一持有连接，真正"连接只有一条"且不依赖某个 tab 存活；缺点是实现复杂（MessagePort 通信）、生命周期管理麻烦（所有关联页面关闭才销毁）、Safari 支持历史问题；
- **postMessage**：窗口间需要引用（window.open 的返回值/opener），适合父子窗口，不适合 N 个平级 tab。
- 我们的选型：BroadcastChannel + Leader 选举实现成本和维护难度最可控。

#### Q3：主标签页（Leader）怎么选举？怎么保证主页面关闭后有人接管？⚠️

**参考回答思路（按经典 Leader Elect 协议讲）：**
- **竞选**：页面加载时广播 `election`（带上自己的 id/随机优先级），一段时间内没人应答 `leaderAlive` 就自封 Leader 并开始广播心跳；
- **心跳**：Leader 每隔 T 秒广播心跳；从页超过 2~3 个周期没收到心跳就判定失联，发起重新选举；
- **接管清理**：新 Leader 产生前要**确认旧 Leader 的 SSE 连接已断**（旧 Leader 正常关闭时主动广播"我下线了"并 close 连接）；异常关闭靠心跳超时兜底；
- **互斥与脑裂**：两个页同时自封 Leader 的窗口期——用随机延迟竞选 + 收到对方心跳且对方 id 更小时主动退位，把双主概率压到最低。
诚实口径：如果实现里没做完整随机延迟/退位，可以说"通过心跳超时触发重选举，双主窗口期做了 XX 处理"，别过度包装。

#### Q4：如果让你从更高层面看，解决 SSE 连接数限制还有哪些路？（方案对比题）📌

**参考回答（分层框架）：**

从**网络协议层、客户端架构层、服务端治理层**三层看：

1. **网络协议层**：限制本质是 HTTP/1.1 同域 6 连接的硬约束。根治是**升级 HTTP/2**——多路复用，一条 TCP 连接并发上百个流，SSE 连接复用同一条 TCP；业务代码几乎零改动，但依赖服务端（Nginx/网关）和客户端支持，适合有升级条件的系统；
2. **客户端架构层**（协议短期升不了时）：
   - **SharedWorker**：独立 Worker 唯一持有连接，所有页面从 Worker 收推送；后台运行不阻塞主线程，但通信架构重构成本高、生命周期管理麻烦；
   - **BroadcastChannel + Leader 选举**：更轻量，有现成库，Leader 崩溃自动接管，实现/维护成本可控；仅限同源；
   - 我们选了后者，因为设备监控是同源场景且希望改动最小；
3. **服务端治理层**（配套兜底）：连接池复用 TCP、自适应心跳精准检测死连接、定期清理僵尸连接——不能突破浏览器限制，但提升单机承载。

**落地策略：优先 HTTP/2 源头解决；升不了就用 BroadcastChannel 方案；服务端配合治理。** 分层解耦、组合使用。

#### Q5：消息量太大会不会把前端打爆？怎么处理？📌

**参考回答：**

先说实际情况：我们场景是**不同服务器主机的状态推送**，前端接收后 ECharts 展示，消息频率和体量在正常范围内，没有出现消费不及时导致的阻塞。

但方案本身要考虑高频场景：主标签页转发 + 各从标签页都消费更新 UI，**高频消息下主线程和渲染性能可能成为瓶颈**。处理思路：
1. **按业务类型分级**：告警、连接状态等关键事件立即广播；统计数据做**批量聚合、节流**，或只保留最新状态，避免每条消息触发一次页面更新；减少高频日志类全量广播；
2. **消费端节流**：图表更新按帧/时间片合并（如 200ms 内多次数据只渲一次）；
3. **主从机制的连带风险**：主标签页因大量消息卡顿，可能心跳发不出被误判失联触发重选举——所以**主节点切换时的连接清理、选举互斥和状态确认**要完善，避免旧主恢复后重复建 SSE 连接（双连接）。

#### Q6：（八股追问）SSE 的 EventSource API 用法？和 fetch 流式读的区别？⚠️

**要点：** `new EventSource(url)`（仅 GET、自动重连、自动带 `Last-Event-ID`）；`onmessage`/`addEventListener('自定义事件名')`；`readyState`（0 连接中 1 开启 2 关闭）；`close()` 主动关闭。**局限**：不能自定义 headers（Token 注入麻烦——常改用 `?token=` 或 cookie）、只能 GET。所以带鉴权的流式接口常用 **fetch + ReadableStream**：`fetch` 后 `response.body.getReader()` 循环 `read()`，手动按 `\n\n` 分帧解析 SSE 文本——LLM 对话产品（OpenAI 风格 POST SSE）基本都走这条路。我们项目两种都有用到（按实际说）。

#### Q2：Docker + Nginx 部署到公司内网的完整流程？📌

**参考回答：**

目的是为招标快速交付可演示环境。流程五步：

1. **本地开发测试**：功能完成、本地验证，执行生产构建（`npm run build`）生成 dist 静态资源；
2. **编写 Dockerfile**：多阶段构建——builder 阶段用 node:22 镜像装依赖、构建；运行阶段把 dist 和 Nginx 配置拷进 nginx 镜像。这样**部署环境不需要 Node**，运行环境统一可复现；
3. **Nginx 配置**：静态资源托管（root 指向 dist、`try_files` 回退 index.html 支持 history 路由）+ 接口反向代理（`location /api` → `proxy_pass` 后端），前端不直连后端真实地址；
4. **构建镜像并部署**：`docker build` 打镜像（带版本号命名，如 `slow-sql-web:1.0.1`），内网服务器 `docker run -d -p 10801:10801` 启动；
5. **验证**：访问内网地址，检查页面、静态资源路径、接口联通。

**点题：Docker 解决环境一致性，Nginx 负责静态托管和请求转发。**

#### Q3：两个后端调试地址问题：ARG + Vite 环境变量方案，具体怎么做的？📌

**参考回答：**

**问题**：后端调试有两个地址（开发 `http://192.168.x.x:8000`、部署 `http://xxx:8000`），不能把地址硬编码进 React 代码。

**方案链路（一口气讲清）：**

```text
docker build --build-arg VITE_API_BASE_URL=后端地址
  → Dockerfile ARG（构建期参数）
  → ENV VITE_API_BASE_URL（转成环境变量）
  → npm run build 时 Vite 读取
  → import.meta.env.VITE_API_BASE_URL 编译进 dist 的 JS
  → Nginx 托管 dist
  → 浏览器加载 JS，Axios 拦截器用这个 baseURL 请求后端
```

Dockerfile 关键段：

```dockerfile
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
ARG VITE_API_BASE_URL
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
RUN npm run build
```

构建命令（注意 `.env` 文件被 dockerignore 了，所以构建时必须显式传）：

```bash
docker build -t slow-sql-web:1.0.1 --build-arg VITE_API_BASE_URL=http://172.20.20.128:10800 .
docker run -d -p 10801:10801 --name slow-sql-web-container slow-sql-web:1.0.1
```

前端取值（Axios 封装里）：

```ts
const baseURL = import.meta.env.VITE_API_BASE_URL;
```

**两个必被追问的点：**
- **为什么浏览器运行时还能用这个地址？** 因为它不是容器运行时动态读的，而是 `npm run build` 时被 Vite **静态编译进了 JS 产物**，Nginx 只是把含这个值的静态文件发给浏览器。
- **ARG 和 ENV 的区别**：ARG 是构建阶段参数（不留在最终镜像），ENV 是镜像环境变量（运行时存在）；这里 ARG→ENV 的桥接只影响构建期 Vite 的取值。
- **这个方案的缺点（主动说）**：换后端地址就要重新构建镜像。更灵活的替代：运行时配置——容器启动时用启动脚本按环境变量生成 `config.js`（window 全局变量）或 `/config.json`，前端运行时 fetch 读取；或者干脆走 Nginx 反向代理同源相对路径（改 Nginx 配置就行，前端完全不感知地址）。

#### Q4：（八股追问）Docker 基础：镜像和容器的区别？常用命令？⚠️

**要点：** 镜像是只读分层模板（Dockerfile 每条指令一层，层可缓存复用），容器是镜像的运行实例（可写层叠加）；`docker build / run / ps / logs / exec -it 容器 sh / images / stop / rm / rmi`；多阶段构建的意义：builder 阶段的 node_modules 不进最终镜像，产物小、攻击面小。

#### Q5：（八股追问）Nginx 配置：location 匹配规则？前端 history 路由 404 怎么解决？⚠️

**要点：**
- 匹配优先级：`=` 精确 > `^~` 前缀（不再查正则）> `~ / ~*` 正则 > 普通前缀；`/api` 和 `/` 的分工示例；
- **SPA 404 问题**：history 路由的 URL（如 `/detail/3`）刷新时 Nginx 找不到对应文件返回 404，要配 `try_files $uri $uri/ /index.html;` 回退到入口 HTML 由前端路由接管；
- 反向代理：`proxy_pass http://backend;` + 常用配套 `proxy_set_header`（Host、X-Real-IP）；gzip 压缩静态资源、`expires` 缓存头（带 hash 的静态资源长缓存、index.html 不缓存）。

#### Q6：（八股追问）Git Flow 了解吗？日常怎么协作？⚠️

**要点：** 长期分支 master/main（稳定）+ develop（集成）；功能分支 feature/* 从 develop 拉出、合回；release 分支做发布准备；hotfix 从 master 拉出修复后双向合。日常：领任务 → feature 分支开发 → 自测 → MR/PR + 代码评审 → CI → 合并。实习口径：公司用 XX 流程（按实际），我遵守分支规范、小步提交、commit message 规范（feat/fix 前缀）。

### 5.4 Vue3（项目二主栈）

| 问题 | 答题要点 | 项目关联 |
| --- | --- | --- |
| 响应式原理 | Proxy 代理对象读写（比 Vue2 defineProperty 强在：新增删除属性、数组索引、惰性深层代理）；依赖收集（track）→ 触发更新（trigger） | React vs Vue 对比（见下） |
| ref vs reactive | ref 任意类型（.value，模板自动解包）；reactive 仅对象（解构丢响应式——用 toRefs）；一般基础类型用 ref | 表单 model 设计 |
| computed vs watch | computed 缓存派生值；watch 侦听执行副作用（deep/immediate/flush）；watchEffect 自动收集依赖 | 动态校验规则（2.4-Q1） |
| 生命周期 | setup → onMounted/onUpdated/onUnmounted；对应 React 的 mount/update/unmount，但 Vue 更新是依赖精确触发 | 权限加载时序 |
| v-if vs v-show | vif 真卸载/编译；vshow display 切换；频繁切换用 vshow | 四/七层表单切换 |
| v-for 与 key | 同 React 的 key 复用逻辑；v-for 和 v-if 不同节点（Vue3 v-if 优先级更高） | 列表页 |
| Vue2 → Vue3 主要变化 | Composition API（逻辑复用替代 mixin）、Proxy 响应式、多根节点、Tree-shaking 更好、性能（静态提升/patchFlag） | 谈框架演进 |

**React vs Vue3 必背总结（两项目双栈，必被问）📌：**
> 两者本质区别是**响应式方式和更新触发机制**：Vue3 基于 Proxy 做依赖收集，数据变化**精确触发**依赖它的副作用，更新粒度细；React 是状态驱动重执行——state 变化后组件函数重新执行，经 Fiber 协调算出最小 DOM 变更，默认**组件级粗粒度**，需要 memo/useMemo/useCallback 手动优化。开发体验上 Vue"数据变视图自动变"，React"UI 是状态的函数"由开发者组合方案。结合项目：React 项目（智能体平台）我更关注状态设计和渲染隔离（卡片重绘治理）；Vue 项目（流量调度）我更多直接用响应式系统写复杂表单。**注意别绝对化——粒度差异还受组件设计和状态管理影响。**
