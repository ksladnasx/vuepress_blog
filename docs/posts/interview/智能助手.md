# 企业设备运维知识库与智能问答平台

## 一、项目设计

项目定位：面向企业 IT 运维、工业设备维护及售后技术支持的 RAG 智能问答应用

### 1. 项目背景

企业通常积累了大量设备说明书、维修手册、故障处理 SOP、产品技术文档和历史维修记录。传统方式主要依赖人工查阅文档，存在文档分散、专业术语复杂、设备型号相似导致检索不准确，以及回答缺少原始依据等问题。

因此，构建一个能够识别设备名称与型号、理解自然语言问题、检索对应技术文档并结合联网信息生成答案的智能助手。

举例来说，用户询问：

> 某型号工业控制器出现 E104 报错，设备重启后依然无法恢复，应该如何排查？

系统先识别设备名称及型号，在相关设备手册中检索故障码说明与处理 SOP，再根据检索结果组织排查步骤，并标明对应手册、章节和页码。只有在本地资料不足且问题适合联网查询时，才调用 MCP 联网工具补充信息。

### 2. 技术栈设计

| 模块       | 技术选型              | 主要职责                                   |
| ---------- | --------------------- | ------------------------------------------ |
| 前端       | React + TypeScript    | 文档管理、设备选择、流式问答、引用来源展示 |
| 后端       | Python + FastAPI      | REST API、鉴权、文件处理、业务接口         |
| 工作流编排 | LangChain + LangGraph | 文档入库流程、查询流程、条件路由与状态管理 |
| 向量检索   | Milvus + BGE-M3       | 稠密向量、稀疏向量及混合检索               |
| 检索增强   | HyDE + RRF + Reranker | 查询扩展、多路召回融合、候选文档重排序     |
| 外部工具   | MCP 联网检索服务      | 搜索外部技术资料及可访问的官方文档         |
| 会话存储   | MongoDB               | 会话、消息、引用记录、任务与文档元数据     |
| 文件存储   | MinIO                 | 原始文档、提取的图片、图片访问对象         |
| 流式交互   | SSE                   | 将大模型生成内容逐步传递到前端             |

其中，BGE-M3 支持多语言稠密检索、稀疏检索等能力；Milvus 支持多路向量检索及 RRF 等融合方式。MCP 则用于规范化地连接外部搜索工具，并不等同于联网搜索引擎本身。

#### A. 文档导入工作流

LangGraph 可以负责组织这些节点、维护运行状态，并按条件决定重试、跳过或进入失败分支。大文件处理应当通过后台任务执行，避免上传接口一直等待全部向量生成结束。

需要强调：MinIO 存文件，MongoDB 存业务元数据和会话，Milvus 存检索索引及其关联数据。它们不是同一个数据库，也不能假设三个系统之间天然具备统一事务。

#### B. 用户问答工作流

这里有两个关键设计。

第一，设备识别不仅是从问题里抽取一个名字，还要处理同名设备、系列型号和别名。如果出现多个候选设备，应该让用户选择，而不是直接把模型猜测的设备作为过滤条件。

第二，RAG 的召回、融合、重排和生成是不同环节。RRF 融合多个检索结果列表，Reranker 再评估问题与候选片段之间的相关性，最后才将高相关的真实资料传给生成模型。

## 二、项目面试高频问题：一问一答

以下答案按面试现场的表达方式来写，重点是讲清楚实现思路，而不是把所有技术名词重复一遍。你可以将它们作为这个项目的设计方案来学习，再根据实际代码调整回答。

### 第一组：整体架构与 LangGraph

#### Q1：这个项目主要解决什么问题？整体架构是怎样的？

面试回答：

这个项目主要解决企业设备手册分散、设备型号相似导致检索不准确，以及传统关键词搜索难以理解自然语言问题的问题。

整体采用 React + TypeScript 作为前端，FastAPI 提供后端 API，LangChain 负责模型调用、检索器及相关组件集成，LangGraph 编排文档导入和问答流程。底层使用 Milvus 存储向量索引，MongoDB 管理会话及业务元数据，MinIO 保存原始文档和图片。

在问答阶段，我会重点通过设备识别和元数据过滤缩小检索范围，再结合混合检索、RRF 和重排序来提升召回结果的相关性，最后生成附带来源的答案。

#### Q2：为什么使用 LangGraph？直接用 LangChain 的 Runnable Chain 不行吗？

面试回答：

如果只是简单的检索、拼接上下文和生成回答，使用 LangChain 的 Runnable Chain 就可以完成。

但这个项目有不少条件分支，比如设备不明确时需要用户确认，检索结果不足时需要调整查询或决定是否联网，文档处理失败时需要重试。这些场景有状态流转和条件路由需求。

所以我会使用 LangGraph 把每一个关键步骤拆成节点，通过 State 保存问题、设备信息、检索结果和处理状态，再通过条件边决定下一步执行什么。这样工作流会更清晰，也更方便调试和恢复执行。

#### Q3：LangChain 和 LangGraph 在项目中分别承担什么职责？

面试回答：

我会把 LangChain 理解为模型和检索组件的集成层，例如大模型调用、提示词模板、文档切片、Embedding 和 Retriever 等。

LangGraph 更侧重控制整个业务流程，例如先识别设备，再判断是否需要用户确认，然后执行检索、结果融合和回答生成。

简单来说，LangChain 负责组合具体能力，LangGraph 负责组织这些能力以什么顺序执行，以及在不同条件下如何流转。

#### Q4：LangGraph 的 State 应该如何设计？

面试回答：

我会把 State 设计成一个有明确字段结构的数据对象，主要包含 `question`、`device_candidates`、`selected_device`、`query_variants`、`retrieval_results`、`reranked_results`、`answer` 和 `source_documents` 等字段。

每个节点读取自己需要的数据，并返回本次需要更新的字段。例如设备识别节点负责更新候选设备，检索节点负责更新召回结果，生成节点负责更新答案和引用来源。

文档内容和大量向量不会直接全部塞进 State，而是保存标识、状态和必要的引用数据，具体内容由后端存储系统管理。

#### Q5：文档入库流程具体怎么编排？为什么不用一个普通 Python 函数串起来？

面试回答：

一个普通函数也能完成顺序处理。使用 LangGraph 的主要理由不是为了替代普通函数，而是为了管理更复杂的任务流程。

我会将流程划分为文件校验、文件存储、内容解析、切片、向量化、写入 Milvus 和更新任务状态等节点。中间可以根据处理结果进入成功、重试或失败分支。

比如，解析失败和向量服务暂时不可用需要不同的处理方式。通过任务状态、重试次数和节点边界，可以更容易定位问题。不过，生产环境中的后台任务调度、并发控制和资源隔离仍然需要单独考虑，不能只依靠 LangGraph。

### 第二组：RAG、BGE-M3 与检索优化

#### Q6：文档切片是怎么做的？为什么不直接把整篇文档交给大模型？

面试回答：

整篇文档可能超过模型的上下文限制，而且文档越长，越容易引入大量与当前问题无关的信息。

我会优先采用结构化切片，根据标题层级、段落和表格划分内容，同时保留设备型号、章节名称、页码、文档版本等元数据。对于较长的段落，可以再按 token 长度切分，并设置适当的重叠区域，避免关键内容在边界被截断。

具体的 Chunk 大小和重叠长度需要结合文档类型和检索效果测试，不应该只采用一个固定参数处理所有文档。

#### Q7：为什么选择 BGE-M3？混合检索解决了什么问题？

面试回答：

设备运维问题既包含语义描述，也包含型号、故障码、零件编号等精确术语。

稠密向量检索更适合处理语义相近但用词不同的问题；稀疏检索更有利于匹配具体关键词。BGE-M3 支持这两类检索表示，因此可以将稠密向量和稀疏向量存入 Milvus，分别检索后进行融合。

例如，用户询问“控制器 E104 无法启动”，系统既需要理解“无法启动”与相似故障描述的语义关系，也需要匹配准确的 `E104` 故障码。

#### Q8：稠密检索和稀疏检索的区别是什么？

面试回答：

稠密检索会把文本编码成连续向量，通过向量相似度寻找语义接近的内容。即使问题和文档的措辞不同，也可能匹配到相关内容。

稀疏检索通常会根据词项及其权重进行匹配，对于产品型号、故障码、专业术语等关键词比较有优势。

这两种方式不是相互替代，而是互补的。将它们结合起来，可以同时兼顾语义理解和精确匹配。

#### Q9：HyDE 是什么？在这个项目中怎么使用？

面试回答：

HyDE 的核心思路是先让大模型根据问题生成一段假设性的相关文档或回答，再将这段假设文本向量化，用于检索真实文档。

例如，用户的问题描述不够专业，直接检索可能无法找到手册中的标准术语。HyDE 可以先生成一段可能包含相关技术术语的假设文本，再用它检索实际资料。

需要注意，HyDE 生成的文本只是检索辅助内容，不能直接当成事实依据。最终回答仍然应该基于真实检索到的手册片段。

#### Q10：RRF 是什么？为什么不用直接比较不同检索器的分数？

面试回答：

不同检索方式产生的分数可能采用不同的计算机制和分布，直接将分数相加可能导致某一条检索路径占据过大的权重。

RRF，也就是 Reciprocal Rank Fusion，会根据文档在不同结果列表中的排名进行融合，常见形式是：

$$
\\{RRF}(d)= \sum_{i=1}^{m}\frac{1}{k+r_i(d)} 
$$
其中，\(r_i(d)\) 表示文档在第 \(i\) 个结果列表中的排名，\(k\) 是平滑参数。

在这个项目中，可以融合稠密检索、稀疏检索及 HyDE 检索等路径的候选结果。对于 MCP 获取的外部资料，也可以先形成带有来源标识的候选列表，再在应用层进行排名融合。

#### Q11：RRF 和 Reranker 有什么区别？为什么两者都需要？

面试回答：

RRF 主要解决的是多个检索结果列表如何合并的问题，它关注文档在各个列表中的排名。

Reranker 则会进一步判断用户问题与候选文档之间的相关程度。例如采用 Cross-Encoder 重排序模型，将问题和文档一起输入模型，得到相关性分数，再按照分数重新排序。

所以我的处理顺序会是先召回、再融合、再重排。RRF 能综合多个检索路径，Reranker 则对融合后的候选内容进行更细致的相关性判断。

#### Q12：为什么不直接提高向量检索的 Top-K，而要增加这么多检索步骤？

面试回答：

单纯增加 Top-K 确实可能提高召回机会，但也会引入更多无关文档，增加上下文长度、模型输入成本以及错误引用的可能性。

所以我会采用分阶段处理：多路召回阶段尽量覆盖相关内容，RRF 统一不同路径的候选顺序，Reranker 再筛选更相关的片段，最后只将有限的高相关上下文交给模型。

具体候选数量需要通过测试集调优，而不是越多越好。

### 第三组：设备识别与 MCP 联网检索

#### Q13：你提到设备名称识别与候选确认，具体是怎么实现的？

面试回答：

我会先结合设备别名表、型号信息和结构化大模型输出，从用户问题中识别设备名称、型号及故障码。

例如，用户可能只说“X 系列控制器”，而系统中存在多个具体型号。这种情况下，我不会直接选取一个型号作为过滤条件，而是先返回候选设备，让用户确认后再继续检索。

确认结果会作为后续查询的结构化参数，避免把不确定的设备识别结果直接传入检索环节。

#### Q14：确认设备以后，如何缩小检索范围？

面试回答：

设备确认后，我会将设备信息转换成检索过滤条件，而不仅仅是将设备名称追加到问题文本中。

例如，使用租户标识、设备型号、文档类型和版本等元数据，过滤出当前用户有权访问且与目标设备相关的文档，再执行向量检索。

这样能够先排除大量不相关资料，再进行语义召回。不过，租户隔离和访问权限不能只依赖大模型提取的字段，必须由后端根据已认证的用户身份强制执行。

#### Q15：为什么需要 MCP？直接调用搜索引擎 API 不行吗？

面试回答：

直接调用搜索引擎 API 当然可以。采用 MCP，主要是希望将外部工具的接入方式标准化，让应用能够通过统一协议发现和调用不同的工具。

在这个项目中，可以部署一个支持网页搜索和页面读取的 MCP Server，由后端或 Agent 调用相应工具，再将获取的标题、摘要、原文内容和 URL 转换成候选资料。

MCP 解决的是工具连接与调用问题，搜索能力本身仍然来自具体的搜索服务。



#### Q16：什么时候调用 MCP 联网检索？每次提问都联网吗？

面试回答：

我不会默认每次都联网，因为这会增加响应延迟，也会带来外部内容质量和安全方面的问题。

对于设备历史故障、内部维修 SOP 等问题，优先检索经过授权的内部知识库。对于需要最新公开公告、官方技术通告，或者本地知识库检索结果不足的问题，再根据业务规则决定是否调用 MCP。

如果联网检索失败，也应该保留已经找到的内部资料，并明确说明信息不足，而不是伪造一个完整的答案。

#### Q17：HyDE、MCP 和查询改写会不会做重复的事情？

面试回答：

三者的作用不一样。

查询改写是将用户的问题转换成更适合检索的表达方式；HyDE 是生成假设性的相关文本，利用它进行额外的检索；MCP 则是通过外部工具获取本地知识库之外的资料。

它们可以共同构成多路检索，但并不意味着每次都需要全部执行。我会根据问题类型和检索效果决定启用哪些路径，减少不必要的模型调用。

### 第四组：MongoDB、MinIO 与 SSE

#### Q18：为什么使用 MongoDB 存会话，而不是把所有东西都放到 Milvus？

面试回答：

Milvus 的主要职责是向量检索，不适合承担完整的业务会话管理。

MongoDB 更适合保存会话和消息记录，包括会话 ID、用户 ID、问题、回答、消息时间以及引用来源等信息。Milvus 保存切片文本、向量及检索所需的元数据，两者各自负责不同的数据访问场景。

我还会根据会话查询频率和数据增长情况设计索引，比如围绕用户 ID、会话 ID 和时间字段建立适当索引。

#### Q19：为什么图片和文档要放在 MinIO，而不直接存到 MongoDB？

面试回答：

原始文档和图片通常体积比较大，我会将它们以对象的形式存储在 MinIO，而在 MongoDB 中保存对象键、文件名、文档 ID、版本和处理状态等元数据。

这样可以避免把大量文件内容混入业务记录，也更方便进行文件下载、访问控制和生命周期管理。MinIO 提供 S3 兼容的对象存储接口，便于通过相应 SDK 进行操作。

对于图片，如果需要让它们参与问答，可以先提取 OCR 文本或图片描述并关联到文档切片；如果只需要原图展示，则保存图片与页码、章节或切片之间的关联即可。

#### Q20：前端如何实现大模型流式输出？

面试回答：

前端通过 SSE 连接后端问答接口，后端在模型生成内容时持续发送文本片段或结构化事件，前端接收到事件以后逐步更新对话内容。

我会区分增量文本、引用来源、任务完成和错误等事件，避免把所有事件都当成普通文本拼接。

同时需要处理连接中断、重复事件以及用户切换会话的情况。SSE 负责传输生成过程，不负责检索或推理本身。前后端也需要约定好事件格式和结束标记。

### 第五组：工程质量与故障排查

#### Q21：如果大模型生成的答案是错的，你会从哪些方向排查？

面试回答：

我会将问题拆成几个阶段排查。

首先确认设备识别是否正确，检索过滤有没有把正确的手册排除；其次检查召回结果是否包含正确内容，再检查 RRF 和 Reranker 有没有将正确片段排到后面。最后才检查生成阶段的上下文组织和提示词。

如果检索结果本身就不正确，单纯修改提示词通常不能彻底解决问题。因此我会保留每个阶段的输入、输出和来源标识，让整个检索链路可以被逐步验证。

#### Q22：如何处理文档重复导入、重复向量化的问题？

面试回答：

我会为文档设置稳定的 ID、版本号和内容哈希，判断这次导入是新文档、内容更新还是重复上传。

写入向量库时，使用文档 ID、版本号和切片序号等字段构建稳定的切片标识，确保重试时不会无限产生重复数据。

如果文档更新，则需要明确新旧版本的切换策略，避免旧版本和新版本同时被无差别检索。

#### Q23：如果文档已经存入 MinIO，但向量写入 Milvus 失败怎么办？

面试回答：

因为 MinIO、MongoDB 和 Milvus 之间没有天然的统一事务，我会使用显式的任务状态管理处理这类情况。

例如，文档先进入处理中状态，原文件上传成功后继续解析和向量化。如果向量写入失败，就记录具体阶段及错误信息，保留必要的任务信息并进行有限次数的重试。

只有确认该版本需要的索引全部写入成功后，才将文档标记为可检索。对于持续失败的任务，需要支持人工排查及补偿处理。

#### Q24：这个项目有哪些安全风险？如何处理？

面试回答：

我会重点关注三个方面。

首先是数据隔离，用户只能检索自己有权限访问的设备手册，租户和权限过滤需要由后端强制执行。其次是文件安全，需要校验文件类型、大小和内容，并限制存储文件的直接访问。最后是外部工具和提示注入风险，不能将网页中的指令直接当作系统命令执行。

MCP 工具应该有明确的调用范围、超时和权限控制，联网内容也不能覆盖系统原有的鉴权规则。

#### Q25：如何判断这个 RAG 项目做得好不好？

面试回答：

我不会只通过几条问答的主观感受评价效果，而是建立一组覆盖不同设备型号、故障码和问题表达方式的测试集。

检索层可以关注 Recall@K，观察相关片段是否出现在前 K 个结果里；重排序可以关注 MRR 或 NDCG；回答层则重点检查事实正确性、引用是否真正支持结论，以及资料不足时能否正确拒答。

性能方面，还可以记录检索耗时、模型生成耗时、整体响应时间及失败率。通过这些指标对比不同切片方案、检索参数和重排策略，才能判断改动是否真正有效。

#### Q26：如果项目开发时间有限，你会优先实现什么？

面试回答：

我会先实现一条完整的最小闭环：文档上传、解析切片、BGE-M3 向量化、Milvus 检索、模型生成，以及引用来源展示。

然后再加入设备识别与元数据过滤，确保检索范围正确。基础链路稳定之后，再逐步引入 HyDE、多路召回融合、Reranker 和 MCP 联网检索。

因为这些优化都依赖基础数据质量和检索流程。如果文档解析、设备元数据和基础召回不可靠，直接增加复杂的 Agent 流程只会增加排错难度。
