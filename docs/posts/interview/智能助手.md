# 企业设备运维知识库与智能问答平台

## 一、项目设计

项目定位：面向企业 IT 运维、工业设备维护及售后技术支持的 RAG 智能问答应用

### 1. 项目背景

企业通常积累了大量设备说明书、维修手册、故障处理 SOP、产品技术文档和历史维修记录。传统方式主要依赖人工查阅文档，存在文档分散、专业术语复杂、设备型号相似导致检索不准确，以及回答缺少原始依据等问题。

因此，构建一个能够识别设备名称与型号、理解自然语言问题、检索对应技术文档并结合联网信息生成答案的智能助手。

举例来说，用户询问：

> 某型号工业控制器出现 E104 报错，设备重启后依然无法恢复，应该如何排查？

系统先识别设备名称及型号，在相关设备手册中检索故障码说明与处理 SOP，再根据检索结果组织排查步骤，并标明对应手册、章节和页码。只有在本地资料不足且问题适合联网查询时，才调用 MCP 联网工具补充信息。

### 2. 技术栈设计

| 模块       | 技术选型              | 主要职责                                   |
| ---------- | --------------------- | ------------------------------------------ |
| 前端       | React + TypeScript    | 文档管理、设备选择、流式问答、引用来源展示 |
| 后端       | Python + FastAPI      | REST API、鉴权、文件处理、业务接口         |
| 工作流编排 | LangChain + LangGraph | 文档入库流程、查询流程、条件路由与状态管理 |
| 向量检索   | Milvus + BGE-M3       | 稠密向量、稀疏向量及混合检索               |
| 检索增强   | HyDE + RRF + Reranker | 查询扩展、多路召回融合、候选文档重排序     |
| 外部工具   | MCP 联网检索服务      | 搜索外部技术资料及可访问的官方文档         |
| 会话存储   | MongoDB               | 会话、消息、引用记录、任务与文档元数据     |
| 文件存储   | MinIO                 | 原始文档、提取的图片、图片访问对象         |
| 流式交互   | SSE                   | 将大模型生成内容逐步传递到前端             |

其中，BGE-M3 支持多语言稠密检索、稀疏检索等能力；Milvus 支持多路向量检索及 RRF 等融合方式。MCP 则用于规范化地连接外部搜索工具，并不等同于联网搜索引擎本身。

#### A. 文档导入工作流

LangGraph 可以负责组织这些节点、维护运行状态，并按条件决定重试、跳过或进入失败分支。大文件处理应当通过后台任务执行，避免上传接口一直等待全部向量生成结束。

需要强调：MinIO 存文件，MongoDB 存业务元数据和会话，Milvus 存检索索引及其关联数据。它们不是同一个数据库，也不能假设三个系统之间天然具备统一事务。

#### B. 用户问答工作流

这里有两个关键设计。

第一，设备识别不仅是从问题里抽取一个名字，还要处理同名设备、系列型号和别名。如果出现多个候选设备，应该让用户选择，而不是直接把模型猜测的设备作为过滤条件。

第二，RAG 的召回、融合、重排和生成是不同环节。RRF 融合多个检索结果列表，Reranker 再评估问题与候选片段之间的相关性，最后才将高相关的真实资料传给生成模型。

## 二、项目面试高频问题：一问一答

以下答案按面试现场的表达方式来写，重点是讲清楚实现思路，而不是把所有技术名词重复一遍。你可以将它们作为这个项目的设计方案来学习，再根据实际代码调整回答。

### 第一组：整体架构与 LangGraph

#### Q1：这个项目主要解决什么问题？整体架构是怎样的？

面试回答：

这个项目主要解决企业设备手册分散、设备型号相似导致检索不准确，以及传统关键词搜索难以理解自然语言问题的问题。

整体采用 React + TypeScript 作为前端，FastAPI 提供后端 API，LangChain 负责模型调用、检索器及相关组件集成，LangGraph 编排文档导入和问答流程。底层使用 Milvus 存储向量索引，MongoDB 管理会话及业务元数据，MinIO 保存原始文档和图片。

在问答阶段，我会重点通过设备识别和元数据过滤缩小检索范围，再结合混合检索、RRF 和重排序来提升召回结果的相关性，最后生成附带来源的答案。

#### Q2：为什么使用 LangGraph？直接用 LangChain 的 Runnable Chain 不行吗？

面试回答：

如果只是简单的检索、拼接上下文和生成回答，使用 LangChain 的 Runnable Chain 就可以完成。

但这个项目有不少条件分支，比如设备不明确时需要用户确认，检索结果不足时需要调整查询或决定是否联网，文档处理失败时需要重试。这些场景有状态流转和条件路由需求。

所以我会使用 LangGraph 把每一个关键步骤拆成节点，通过 State 保存问题、设备信息、检索结果和处理状态，再通过条件边决定下一步执行什么。这样工作流会更清晰，也更方便调试和恢复执行。

#### Q3：LangChain 和 LangGraph 在项目中分别承担什么职责？

面试回答：

我会把 LangChain 理解为模型和检索组件的集成层，例如大模型调用、提示词模板、文档切片、Embedding 和 Retriever 等。

LangGraph 更侧重控制整个业务流程，例如先识别设备，再判断是否需要用户确认，然后执行检索、结果融合和回答生成。

简单来说，LangChain 负责组合具体能力，LangGraph 负责组织这些能力以什么顺序执行，以及在不同条件下如何流转。

#### Q4：LangGraph 的 State 应该如何设计？

面试回答：

我会把 State 设计成一个有明确字段结构的数据对象，主要包含 `question`、`device_candidates`、`selected_device`、`query_variants`、`retrieval_results`、`reranked_results`、`answer` 和 `source_documents` 等字段。

每个节点读取自己需要的数据，并返回本次需要更新的字段。例如设备识别节点负责更新候选设备，检索节点负责更新召回结果，生成节点负责更新答案和引用来源。

文档内容和大量向量不会直接全部塞进 State，而是保存标识、状态和必要的引用数据，具体内容由后端存储系统管理。

#### Q5：文档入库流程具体怎么编排？为什么不用一个普通 Python 函数串起来？

面试回答：

一个普通函数也能完成顺序处理。使用 LangGraph 的主要理由不是为了替代普通函数，而是为了管理更复杂的任务流程。

我会将流程划分为文件校验、文件存储、内容解析、切片、向量化、写入 Milvus 和更新任务状态等节点。中间可以根据处理结果进入成功、重试或失败分支。

比如，解析失败和向量服务暂时不可用需要不同的处理方式。通过任务状态、重试次数和节点边界，可以更容易定位问题。不过，生产环境中的后台任务调度、并发控制和资源隔离仍然需要单独考虑，不能只依靠 LangGraph。

### 第二组：RAG、BGE-M3 与检索优化

#### Q6：文档切片是怎么做的？为什么不直接把整篇文档交给大模型？

面试回答：

整篇文档可能超过模型的上下文限制，而且文档越长，越容易引入大量与当前问题无关的信息。

我会优先采用结构化切片，根据标题层级、段落和表格划分内容，同时保留设备型号、章节名称、页码、文档版本等元数据。对于较长的段落，可以再按 token 长度切分，并设置适当的重叠区域，避免关键内容在边界被截断。

具体的 Chunk 大小和重叠长度需要结合文档类型和检索效果测试，不应该只采用一个固定参数处理所有文档。

#### Q7：为什么选择 BGE-M3？混合检索解决了什么问题？

面试回答：

设备运维问题既包含语义描述，也包含型号、故障码、零件编号等精确术语。

稠密向量检索更适合处理语义相近但用词不同的问题；稀疏检索更有利于匹配具体关键词。BGE-M3 支持这两类检索表示，因此可以将稠密向量和稀疏向量存入 Milvus，分别检索后进行融合。

例如，用户询问“控制器 E104 无法启动”，系统既需要理解“无法启动”与相似故障描述的语义关系，也需要匹配准确的 `E104` 故障码。

#### Q8：稠密检索和稀疏检索的区别是什么？

面试回答：

稠密检索会把文本编码成连续向量，通过向量相似度寻找语义接近的内容。即使问题和文档的措辞不同，也可能匹配到相关内容。

稀疏检索通常会根据词项及其权重进行匹配，对于产品型号、故障码、专业术语等关键词比较有优势。

这两种方式不是相互替代，而是互补的。将它们结合起来，可以同时兼顾语义理解和精确匹配。

#### Q9：HyDE 是什么？在这个项目中怎么使用？

面试回答：

HyDE 的核心思路是先让大模型根据问题生成一段假设性的相关文档或回答，再将这段假设文本向量化，用于检索真实文档。

例如，用户的问题描述不够专业，直接检索可能无法找到手册中的标准术语。HyDE 可以先生成一段可能包含相关技术术语的假设文本，再用它检索实际资料。

需要注意，HyDE 生成的文本只是检索辅助内容，不能直接当成事实依据。最终回答仍然应该基于真实检索到的手册片段。

#### Q10：RRF 是什么？为什么不用直接比较不同检索器的分数？

面试回答：

不同检索方式产生的分数可能采用不同的计算机制和分布，直接将分数相加可能导致某一条检索路径占据过大的权重。

RRF，也就是 Reciprocal Rank Fusion，会根据文档在不同结果列表中的排名进行融合，常见形式是：

$$
\\{RRF}(d)= \sum_{i=1}^{m}\frac{1}{k+r_i(d)} 
$$
其中，\(r_i(d)\) 表示文档在第 \(i\) 个结果列表中的排名，\(k\) 是平滑参数。

在这个项目中，可以融合稠密检索、稀疏检索及 HyDE 检索等路径的候选结果。对于 MCP 获取的外部资料，也可以先形成带有来源标识的候选列表，再在应用层进行排名融合。

#### Q11：RRF 和 Reranker 有什么区别？为什么两者都需要？

面试回答：

RRF 主要解决的是多个检索结果列表如何合并的问题，它关注文档在各个列表中的排名。

Reranker 则会进一步判断用户问题与候选文档之间的相关程度。例如采用 Cross-Encoder 重排序模型，将问题和文档一起输入模型，得到相关性分数，再按照分数重新排序。

所以我的处理顺序会是先召回、再融合、再重排。RRF 能综合多个检索路径，Reranker 则对融合后的候选内容进行更细致的相关性判断。

#### Q12：为什么不直接提高向量检索的 Top-K，而要增加这么多检索步骤？

面试回答：

单纯增加 Top-K 确实可能提高召回机会，但也会引入更多无关文档，增加上下文长度、模型输入成本以及错误引用的可能性。

所以我会采用分阶段处理：多路召回阶段尽量覆盖相关内容，RRF 统一不同路径的候选顺序，Reranker 再筛选更相关的片段，最后只将有限的高相关上下文交给模型。

具体候选数量需要通过测试集调优，而不是越多越好。

### 第三组：设备识别与 MCP 联网检索

#### Q13：你提到设备名称识别与候选确认，具体是怎么实现的？

面试回答：

我会先结合设备别名表、型号信息和结构化大模型输出，从用户问题中识别设备名称、型号及故障码。

例如，用户可能只说“X 系列控制器”，而系统中存在多个具体型号。这种情况下，我不会直接选取一个型号作为过滤条件，而是先返回候选设备，让用户确认后再继续检索。

确认结果会作为后续查询的结构化参数，避免把不确定的设备识别结果直接传入检索环节。

#### Q14：确认设备以后，如何缩小检索范围？

面试回答：

设备确认后，我会将设备信息转换成检索过滤条件，而不仅仅是将设备名称追加到问题文本中。

例如，使用租户标识、设备型号、文档类型和版本等元数据，过滤出当前用户有权访问且与目标设备相关的文档，再执行向量检索。

这样能够先排除大量不相关资料，再进行语义召回。不过，租户隔离和访问权限不能只依赖大模型提取的字段，必须由后端根据已认证的用户身份强制执行。

#### Q15：为什么需要 MCP？直接调用搜索引擎 API 不行吗？

面试回答：

直接调用搜索引擎 API 当然可以。采用 MCP，主要是希望将外部工具的接入方式标准化，让应用能够通过统一协议发现和调用不同的工具。

在这个项目中，可以部署一个支持网页搜索和页面读取的 MCP Server，由后端或 Agent 调用相应工具，再将获取的标题、摘要、原文内容和 URL 转换成候选资料。

MCP 解决的是工具连接与调用问题，搜索能力本身仍然来自具体的搜索服务。



#### Q16：什么时候调用 MCP 联网检索？每次提问都联网吗？

面试回答：

我不会默认每次都联网，因为这会增加响应延迟，也会带来外部内容质量和安全方面的问题。

对于设备历史故障、内部维修 SOP 等问题，优先检索经过授权的内部知识库。对于需要最新公开公告、官方技术通告，或者本地知识库检索结果不足的问题，再根据业务规则决定是否调用 MCP。

如果联网检索失败，也应该保留已经找到的内部资料，并明确说明信息不足，而不是伪造一个完整的答案。

#### Q17：HyDE、MCP 和查询改写会不会做重复的事情？

面试回答：

三者的作用不一样。

查询改写是将用户的问题转换成更适合检索的表达方式；HyDE 是生成假设性的相关文本，利用它进行额外的检索；MCP 则是通过外部工具获取本地知识库之外的资料。

它们可以共同构成多路检索，但并不意味着每次都需要全部执行。我会根据问题类型和检索效果决定启用哪些路径，减少不必要的模型调用。

### 第四组：MongoDB、MinIO 与 SSE

#### Q18：为什么使用 MongoDB 存会话，而不是把所有东西都放到 Milvus？

面试回答：

Milvus 的主要职责是向量检索，不适合承担完整的业务会话管理。

MongoDB 更适合保存会话和消息记录，包括会话 ID、用户 ID、问题、回答、消息时间以及引用来源等信息。Milvus 保存切片文本、向量及检索所需的元数据，两者各自负责不同的数据访问场景。

我还会根据会话查询频率和数据增长情况设计索引，比如围绕用户 ID、会话 ID 和时间字段建立适当索引。

#### Q19：为什么图片和文档要放在 MinIO，而不直接存到 MongoDB？

面试回答：

原始文档和图片通常体积比较大，我会将它们以对象的形式存储在 MinIO，而在 MongoDB 中保存对象键、文件名、文档 ID、版本和处理状态等元数据。

这样可以避免把大量文件内容混入业务记录，也更方便进行文件下载、访问控制和生命周期管理。MinIO 提供 S3 兼容的对象存储接口，便于通过相应 SDK 进行操作。

对于图片，如果需要让它们参与问答，可以先提取 OCR 文本或图片描述并关联到文档切片；如果只需要原图展示，则保存图片与页码、章节或切片之间的关联即可。

#### Q20：前端如何实现大模型流式输出？

面试回答：

前端通过 SSE 连接后端问答接口，后端在模型生成内容时持续发送文本片段或结构化事件，前端接收到事件以后逐步更新对话内容。

我会区分增量文本、引用来源、任务完成和错误等事件，避免把所有事件都当成普通文本拼接。

同时需要处理连接中断、重复事件以及用户切换会话的情况。SSE 负责传输生成过程，不负责检索或推理本身。前后端也需要约定好事件格式和结束标记。

### 第五组：工程质量与故障排查

#### Q21：如果大模型生成的答案是错的，你会从哪些方向排查？

面试回答：

我会将问题拆成几个阶段排查。

首先确认设备识别是否正确，检索过滤有没有把正确的手册排除；其次检查召回结果是否包含正确内容，再检查 RRF 和 Reranker 有没有将正确片段排到后面。最后才检查生成阶段的上下文组织和提示词。

如果检索结果本身就不正确，单纯修改提示词通常不能彻底解决问题。因此我会保留每个阶段的输入、输出和来源标识，让整个检索链路可以被逐步验证。

#### Q22：如何处理文档重复导入、重复向量化的问题？

面试回答：

我会为文档设置稳定的 ID、版本号和内容哈希，判断这次导入是新文档、内容更新还是重复上传。

写入向量库时，使用文档 ID、版本号和切片序号等字段构建稳定的切片标识，确保重试时不会无限产生重复数据。

如果文档更新，则需要明确新旧版本的切换策略，避免旧版本和新版本同时被无差别检索。

#### Q23：如果文档已经存入 MinIO，但向量写入 Milvus 失败怎么办？

面试回答：

因为 MinIO、MongoDB 和 Milvus 之间没有天然的统一事务，我会使用显式的任务状态管理处理这类情况。

例如，文档先进入处理中状态，原文件上传成功后继续解析和向量化。如果向量写入失败，就记录具体阶段及错误信息，保留必要的任务信息并进行有限次数的重试。

只有确认该版本需要的索引全部写入成功后，才将文档标记为可检索。对于持续失败的任务，需要支持人工排查及补偿处理。

#### Q24：这个项目有哪些安全风险？如何处理？

面试回答：

我会重点关注三个方面。

首先是数据隔离，用户只能检索自己有权限访问的设备手册，租户和权限过滤需要由后端强制执行。其次是文件安全，需要校验文件类型、大小和内容，并限制存储文件的直接访问。最后是外部工具和提示注入风险，不能将网页中的指令直接当作系统命令执行。

MCP 工具应该有明确的调用范围、超时和权限控制，联网内容也不能覆盖系统原有的鉴权规则。

#### Q25：如何判断这个 RAG 项目做得好不好？

面试回答：

我不会只通过几条问答的主观感受评价效果，而是建立一组覆盖不同设备型号、故障码和问题表达方式的测试集。

检索层可以关注 Recall@K，观察相关片段是否出现在前 K 个结果里；重排序可以关注 MRR 或 NDCG；回答层则重点检查事实正确性、引用是否真正支持结论，以及资料不足时能否正确拒答。

性能方面，还可以记录检索耗时、模型生成耗时、整体响应时间及失败率。通过这些指标对比不同切片方案、检索参数和重排策略，才能判断改动是否真正有效。

#### Q26：如果项目开发时间有限，你会优先实现什么？

面试回答：

我会先实现一条完整的最小闭环：文档上传、解析切片、BGE-M3 向量化、Milvus 检索、模型生成，以及引用来源展示。

然后再加入设备识别与元数据过滤，确保检索范围正确。基础链路稳定之后，再逐步引入 HyDE、多路召回融合、Reranker 和 MCP 联网检索。

因为这些优化都依赖基础数据质量和检索流程。如果文档解析、设备元数据和基础召回不可靠，直接增加复杂的 Agent 流程只会增加排错难度。

### 一、先准备一段项目介绍

面试官：介绍一下这个项目，你主要负责什么？

建议回答：

这个项目是一个企业设备运维知识库与智能问答平台，主要解决设备手册比较分散、运维人员查找故障处理方案效率比较低的问题。

整体前端使用 React 和 TypeScript，后端使用 Python 和 FastAPI，AI 应用部分主要通过 LangChain 集成模型和检索组件，再使用 LangGraph 编排文档导入和智能问答流程。

项目主要分成两条链路。一条是文档入库，负责文件上传、内容解析、切片、向量化以及写入向量数据库；另一条是问答链路，先识别用户询问的设备，再结合设备信息进行检索，通过混合检索、结果融合和重排序筛选相关内容，最后调用大模型生成带有参考来源的答案。

数据方面，Milvus 负责向量检索，MongoDB 负责会话和业务元数据，MinIO 存储原始文档及图片。我比较关注的是把整个 RAG 流程串起来，以及设备识别、检索过滤和后端业务状态管理这些部分。

这段回答的核心： 先讲业务目标，再讲两条业务链路，最后讲你关注的技术问题。不要一开始就连续报出十几个技术名词。

### 二、对应简历五条贡献

#### 一、先准备一段项目介绍

##### 面试官：你具体是怎么设计文档导入流程的？

建议回答：

文档入库我会拆成几个独立节点，分别负责文件校验、文件存储、文档解析、文本切片、向量化、写入 Milvus 和更新任务状态。

用户上传文件后，FastAPI 先进行文件大小、类型和权限校验，然后将原文件存到 MinIO，并创建对应的文档记录。接着由文档处理流程提取文本和页码等信息，按照标题、段落等结构进行切片，给每个切片补充设备型号、文档版本和来源页码等元数据。

之后调用 Embedding 模型生成向量，分批写入 Milvus。全部关键步骤成功后，将文档状态更新为可检索。

我使用 LangGraph 的设计思路，是将这些处理步骤拆成有明确输入输出的节点，并通过状态对象传递文档 ID、当前处理阶段、错误信息等数据。这样失败时可以知道具体卡在哪个阶段，而不是把所有处理逻辑放在一个大函数里面。

##### 面试官：为什么需要 LangGraph？普通 Python 函数不也能实现吗？

建议回答：

是的，普通 Python 函数完全可以完成简单的顺序流程。如果只有解析、切片、入库几个固定步骤，没有必要为了使用框架而使用 LangGraph。

但这个项目除了顺序处理，还有条件路由、失败重试以及用户确认等环节。比如设备无法确定时需要暂停查询，向量服务暂时不可用时可能需要重试，文件解析失败则应该进入失败分支。

LangGraph 可以把这些状态和分支显式地组织起来，让流程更容易维护和调试。不过，任务队列、并发限制和后台调度还需要配合其他后端机制实现。

##### 面试官：如果处理到一半失败了，你怎么恢复？

建议回答：

我会先区分错误类型。比如文件格式不支持属于业务错误，一般直接标记失败；向量化服务超时属于暂时性错误，可以进行有限次数的重试。

后端会记录文档的处理阶段、重试次数和错误信息，并给每个文档版本及切片设置稳定的 ID。这样重试时可以识别已经处理过的部分，尽量避免重复写入。

如果使用 LangGraph 的持久化检查点来恢复工作流，还要注意检查点和外部数据库写入之间不是一个原子事务，因此外部操作本身也需要具备幂等性。

##### 面试官：文档入库为什么需要异步处理？

建议回答：

因为解析大型 PDF、生成向量以及批量写入向量库可能需要较长时间。如果上传接口同步等待整条流程结束，请求耗时会很长，也更容易超时。

我会让上传接口先完成基本校验和文件存储，再创建处理任务并返回任务 ID。后台工作进程负责文档解析和向量化，前端通过轮询任务状态或者 SSE 获取处理进度。

这里需要区分异步接口和真正的后台任务：单纯将函数声明为 `async`，并不能自动实现任务持久化、失败重试和进程崩溃后的恢复。

#### 2. 设备名称识别、候选确认及检索过滤

这一条很值得重点准备，因为它把大模型能力和传统后端业务逻辑结合起来了。

##### 面试官：你所说的设备识别具体是怎么实现的？

建议回答：

我会将设备识别拆成名称提取、候选匹配和用户确认三个步骤。

首先从用户问题中提取设备名称、型号和故障码等信息，可以使用规则匹配结合大模型结构化输出。然后根据设备别名表和设备信息表查找候选项，结合型号、厂商等信息进行匹配。

如果只匹配到一个足够明确的设备，可以继续执行检索；如果有多个相似设备，就返回候选列表，让用户选择后再继续。

这里我不会完全依赖大模型判断设备，因为设备型号相似时容易出现误判。大模型负责理解自然语言，最终使用哪个设备，以及用户是否有权限访问相关资料，仍然要由后端业务逻辑决定。

##### 面试官：设备名称识别错了怎么办？

建议回答：

我会优先避免不确定的识别结果直接进入检索环节。

如果模型提取的设备型号不在设备库中，或者候选设备的匹配程度不足，就返回未匹配或待确认状态，而不是随便选择一个设备。

如果用户明确选择了候选设备，后端还会校验这个设备是否真实存在，以及当前用户有没有权限访问对应资料。这样能够减少错误设备导致的错误回答。

##### 面试官：为什么不能只把设备名称拼进 Prompt 里？

建议回答：

因为把设备名称写进 Prompt 只是告诉大模型应该关注什么，并不能保证检索系统只返回这个设备的资料。

我会把用户确认过的设备型号转换为结构化过滤条件，例如设备 ID、型号、文档版本和租户 ID。在向量检索阶段先过滤掉不符合条件的文档，再对剩余文档进行相关性搜索。

这样既能缩小搜索范围，也能减少相近设备之间的资料混淆。尤其是租户隔离和权限约束，必须由后端执行，而不能只依赖 Prompt。

##### 面试官：后端如何设计这部分的数据结构？

建议回答：

我会将设备信息和设备别名独立管理。设备表保存设备 ID、设备名称、型号、厂商等信息，设备别名表用于记录用户可能使用的简称或其他称呼。

文档记录里保存关联的设备 ID 和文档版本；切片的元数据中也保留设备 ID、文档 ID、页码等信息。

这样查询时可以通过设备 ID 关联到对应资料，而不是每次都依赖字符串模糊匹配。设备名称发生变化时，也可以维护别名，而不需要重新修改所有文档内容。

一个可用于解释业务关系的简化结构是：

设备表 `devices`

device_id · name · model · manufacturer

设备与文档通过 device_id 关联

文档表 `documents`

document_id · device_id · version · status · object_key

文档与切片通过 document_id 关联

切片索引 `chunks`

chunk_id · document_id · device_id · page · text · vector

这是逻辑关系示例。实际业务元数据可以存放在 MongoDB，向量和检索字段存放在 Milvus 中，不要求全部使用关系型表。

#### 3. BGE-M3 混合检索、HyDE、RRF 和 Reranker

##### 面试官：你这套检索流程具体是怎么跑的？

建议回答：

用户确认设备之后，后端先根据设备型号和权限生成过滤条件，再处理用户的问题。

检索时，我会使用 BGE-M3 的稠密向量和稀疏向量进行两路召回。稠密检索偏向语义相似度，稀疏检索更适合匹配具体的型号和故障码。

对于部分表达比较模糊的问题，还可以先通过 HyDE 生成一段假设性的相关文本，再利用它执行补充检索。多路检索结果经过 RRF 融合后，交给 Reranker 重新评估问题与候选片段的相关性。

最后选取排名靠前、内容适合回答问题的片段，连同来源信息一起传给大模型，生成带有手册引用的答案。

##### 面试官：你能具体解释一下这些技术之间的关系吗？

建议回答：

我把它们分成三个阶段理解。

第一阶段是召回，主要依靠 BGE-M3 的稠密和稀疏检索，必要时增加 HyDE 检索，尽量找到相关候选文档。

第二阶段是融合和排序。RRF 解决多路结果如何合并的问题，Reranker 则进一步对候选片段进行相关性打分和重排。

第三阶段才是生成。将筛选后的真实文档片段组织为上下文，传给大模型生成回答，同时保留文档 ID、章节和页码等来源信息。

我不会把 HyDE 生成的假设文本直接作为最终回答依据，因为它本身并不代表真实的设备资料。

##### 面试官：Milvus 中具体存了什么？怎么进行过滤？

建议回答：

每一个文档切片都会对应一个稳定的 ID、正文内容和相关的检索字段。

在向量化阶段，可以生成稠密向量和稀疏向量，再将它们及必要的元数据写入 Milvus。元数据包括设备 ID、文档 ID、版本、文档类型等字段。

查询时，后端先根据设备和用户权限构造过滤表达式，然后执行对应的检索。需要注意，不同租户和用户能够访问的文档范围应该由后端可靠地确定，不能直接信任用户传来的任意过滤字段。

实际索引、字段类型和混合检索 API 的选择，需要根据所使用的 Milvus 版本和模型输出格式确定。

##### 面试官：Reranker 已经做了重排序，为什么还需要大模型？

建议回答：

Reranker 的主要职责是评估候选文档与问题的相关性，它不会自动完成完整的业务回答。

例如，Reranker 可以将包含故障码处理步骤的手册片段排到前面，但它不会自动判断这些步骤应该怎样组织成可读的操作流程，也不会自动生成对用户友好的说明。

大模型是在筛选后的证据基础上组织答案。检索与重排负责找到更相关的依据，生成模型负责把依据转化为自然语言答案。

##### 面试官：如何避免大模型编造答案？

建议回答：

我会从检索质量和生成约束两方面处理。

一方面，尽量确保召回结果包含问题需要的真实资料；另一方面，提示模型优先根据提供的文档回答，对资料没有覆盖的部分明确说明不确定，而不是自行推断。

同时，答案中的引用不应该只是模型随意生成的字符串，而应当尽量关联到实际检索到的文档 ID、章节和页码，由后端生成或校验引用信息。

如果检索结果不足，还可以触发补充检索，或者明确告诉用户当前资料不足以得出可靠结论。

#### 4. MCP 联网检索及外部资料整合

##### 面试官：MCP 在你的项目中是怎样使用的？

建议回答：

我会把 MCP 作为连接外部搜索工具的标准化接口，而不是将它当成搜索引擎本身。

当内部知识库没有找到足够相关的内容，或者用户询问的是需要最新公开资料的问题时，后端可以根据预先设定的规则调用 MCP Server 提供的搜索工具，获取相关网页的标题、摘要和内容。

之后将外部资料转换为统一的候选文档格式，保留 URL、标题和获取时间，再与内部检索结果进行融合或分别组织上下文。生成答案时，也会区分内部手册和外部网页来源，避免用户混淆两种资料的可信程度。

##### 面试官：是不是 RAG 检索不到东西，就一定要联网？

建议回答：

不一定。内部知识库检索不到内容，可能是设备识别错误、过滤条件过严或者文档还没有完成入库。

所以我会先判断问题属于哪类情况。如果是设备信息不明确，就先让用户确认设备；如果是内部资料相关性不足，可以适当调整查询或补充召回；只有在符合业务规则并且外部信息确实有帮助时，才调用联网检索。

如果联网失败，系统仍然可以返回已有的内部检索结果，并明确说明资料不足。

##### 面试官：联网内容可能有提示词注入，怎么处理？

建议回答：

我会把外部网页当成不可信数据。网页内容只能作为待分析的参考资料，不能因为其中包含指令，就改变系统原本的行为或权限规则。

另外，MCP 工具只开放业务需要的搜索和读取能力，设置超时、调用范围和必要的权限限制，不让普通知识检索接口任意访问本地文件或内部服务。

对于需要登录、付款或执行外部操作的工具，也不会因为大模型自行判断就直接执行，必须经过明确的权限和业务校验。

#### 5. MongoDB、MinIO 与 SSE 流式交互

##### 面试官：MongoDB、MinIO 和 Milvus 分别存什么？

建议回答：

这三个组件的职责是分开的。

MinIO 保存原始 PDF、Word 文件以及抽取出的图片，MongoDB 保存文件的业务元数据、处理状态和用户会话记录，Milvus 保存用于语义检索的向量和相关检索字段。

例如，用户上传一本设备手册后，MinIO 保存文件本身，MongoDB 记录文档 ID、设备型号、版本、对象存储键和处理状态，Milvus 保存解析生成的切片和向量。

这样既方便管理原始文件，也能根据元数据查询文档状态，还可以单独优化向量检索。

##### 面试官：MongoDB 中的会话数据应该怎样设计？

建议回答：

我会把会话和消息分开管理。

会话记录保存会话 ID、所属用户、标题、创建时间和更新时间等信息；消息记录保存消息 ID、会话 ID、角色、内容、时间，以及回答引用的文档来源。

每次用户发起问题时，后端都会验证会话归属，再读取必要的历史消息作为上下文，避免把不同用户或者不同会话的数据混在一起。

会话比较长时，也不能无限制地把所有历史消息传给大模型，可以结合最近消息、摘要或上下文长度进行裁剪。

##### 面试官：为什么需要 SSE？直接等待 API 返回完整答案不行吗？

建议回答：

直接返回完整答案也能工作，但大模型生成通常需要一定时间，用户可能长时间看不到反馈。

通过 SSE，后端可以在生成过程中逐步发送文本片段，前端收到数据后不断更新当前消息，让用户提前看到结果。

在实现上，我会让后端使用流式模型接口，通过 FastAPI 的流式响应向前端发送事件，同时处理结束标记、异常和客户端断开等情况。SSE 负责传输，文档检索和大模型生成仍然由各自的业务节点完成。

##### 面试官：SSE 中途断开怎么办？已经生成的内容会丢失吗？

建议回答：

这里需要区分展示和持久化。

前端可以先展示已经收到的文本片段，但后端应该设计明确的消息状态，例如生成中、成功完成或失败。如果需要保留已生成的内容，就应当在生成过程中定期保存，或者在结束、取消和异常时按设计写入 MongoDB。

如果连接断开，也不能简单假设生成一定失败。后端需要管理生成任务的状态；前端重连时，可以先查询任务状态或读取已保存的消息内容，再决定是否继续接收。

如果要真正实现断点续传，还需要设计事件序号、持久化事件记录及重放机制。仅仅使用 SSE 并不会自动提供完整的断线恢复能力。

### 三、后端业务逻辑：最容易被继续深挖的部分

对于你希望呈现的“前端开发工程师，同时具备 Python 后端和 AI 应用开发能力”，这部分尤其重要。面试官未必要求你现场写出复杂的后端架构，但往往会检查你是否理解 API、数据库、业务状态和异常处理之间的关系。

#### 1. FastAPI 接口怎么设计？

##### 面试官：这个项目主要有哪些后端接口？

建议回答：

我会按照业务模块拆分 API，主要包括文档管理、文档处理任务、设备查询以及会话问答几个部分。

| 接口示例                               | 职责                               |
| -------------------------------------- | ---------------------------------- |
| `POST /api/documents`                  | 上传文件并创建文档记录             |
| `GET /api/documents`                   | 分页查询文档列表                   |
| `GET /api/documents/{id}`              | 查询文档详情与处理状态             |
| `POST /api/documents/{id}/reprocess`   | 重新处理失败的文档                 |
| `GET /api/devices`                     | 获取当前用户可访问的设备与候选设备 |
| `POST /api/conversations`              | 创建会话                           |
| `GET /api/conversations/{id}/messages` | 查询会话历史                       |
| `POST /api/chat/stream`                | 发起问题并流式返回答案             |

这些是建议的 REST API 设计，并不是固定的唯一方案。实际项目中会根据认证、分页、任务调度及流式返回方式进一步调整。

##### 面试官：你的 FastAPI 项目代码是怎么分层的？

建议回答：

我会把接口层、业务层和数据访问层拆开。

Router 负责接收请求、参数校验和组织响应；Service 负责具体业务逻辑，例如文档上传后创建处理任务，或者查询时组织设备识别和检索流程；DAO 或 Repository 负责与 MongoDB 等数据存储交互。

模型调用、文档解析和向量检索也可以封装成独立服务，避免直接把所有逻辑写在接口函数中。这样业务规则更容易测试和复用，后面要替换向量模型或者调整检索流程时，也不需要大规模修改 API 层。

这里不一定要求项目目录必须采用某一种固定结构，重点是职责清晰、依赖关系合理。

#### 2. 文档上传与状态管理

##### 面试官：一个文档从上传到可检索，中间有哪些状态？

建议回答：

我会设计一套明确的文档处理状态，例如待处理、处理中、处理成功和处理失败。如果需要更细粒度地排查，还可以额外记录当前阶段，比如解析、切片、向量化和入库。

上传接口成功，只代表文件已经接收并保存，不代表这个文档已经能够参与检索。

只有当解析、切片、向量化和必要的索引写入都成功之后，文档才标记为可检索。这样前端可以根据不同状态展示处理中、可用或者失败，并允许用户对失败任务重新发起处理。

##### 面试官：同一个文件上传两次怎么办？

建议回答：

可以先计算文件内容的哈希值，并结合用户、文档 ID 或业务范围判断是否重复。

如果完全相同的文件已经处理成功，可以直接返回已有记录，避免重复消耗向量化资源。如果文件内容发生变化，则创建新版本，或者按业务要求更新已有文档。

同时，向量切片需要使用稳定的标识，避免任务重试时产生大量重复记录。即使存在内容相同的文件，也要考虑不同用户是否有权共享文档，不能仅凭哈希相同就让不同用户访问同一个文件。

##### 面试官：文档更新时，怎么防止新旧版本混在一起？

建议回答：

我会给文档设置版本号，并在切片元数据中保留文档 ID 和版本号。

可以先将新版本写入索引，写入完成并校验成功后，再切换当前有效版本。检索时只查询当前有效版本或经过授权的指定版本。

旧版本可以在确认新版本正常之后再删除。如果更新过程中失败，应该保留可回滚的信息，避免原本可用的文档因为更新中断而无法查询。

#### 3. 会话与业务权限

##### 面试官：用户可以直接传一个 device_id 或 document_id 来查询资料吗？

建议回答：

不能直接信任客户端传来的 ID。

后端需要从已经验证的身份信息中获取用户或租户身份，再检查目标设备、文档或会话是否属于当前用户的可访问范围。如果用户传来的 ID 不存在或无权访问，就应该拒绝请求，而不是把这个 ID 直接交给向量数据库进行检索。

特别是多租户系统，即使用户知道另一个租户的文档 ID，也不应该通过接口访问到对方的资料。

##### 面试官：MongoDB 为什么还需要建立索引？

建议回答：

MongoDB 虽然不是关系型数据库，但如果会话和消息量比较大，查询仍然需要合适的索引。

例如，查询某个用户的会话列表，可以围绕用户 ID 和更新时间设计索引；查询某个会话的消息，则可以围绕会话 ID 和消息时间设计索引。

索引需要结合实际查询条件和排序方式设计。并不是字段越多索引越好，因为索引也会占用空间，并增加写入维护成本。

#### 4. 异常处理、幂等性与系统稳定性

##### 面试官：如果用户连续点击两次上传按钮，会出现什么问题？你怎么处理？

建议回答：

如果没有专门处理，可能出现重复的文档记录、重复的处理任务以及重复的向量写入。

前端可以在请求提交后暂时禁用按钮，但不能只依赖前端，因为用户也可能通过重复请求或网络重试提交同一个任务。

后端需要设计幂等机制。例如，为文档创建操作设置业务标识，对相同的处理任务进行去重；为向量切片生成稳定 ID，让重复写入能够被识别或覆盖。这样即使请求重复发送，也尽可能不会重复执行产生副作用的业务操作。

##### 面试官：调用大模型或 Embedding 服务超时怎么办？

建议回答：

我会区分超时、限流和参数错误等不同原因。

对于网络超时或临时限流，可以进行有限次数的重试，并设置合理的超时时间和退避策略；对于输入不合法、模型不支持等确定性错误，则不应该无限重试。

另外，批量向量化时不宜一次提交过多文本，可以按照批次处理，并记录失败批次和对应的切片 ID，方便后续补偿，而不是每次失败都从头处理整个文档。

##### 面试官：MinIO 上传成功，但 MongoDB 写入失败怎么办？

建议回答：

因为文件存储和 MongoDB 不属于同一个事务，不能假设两个操作会同时成功。

我会为文档处理设计显式的状态与补偿机制。例如，先创建带有唯一业务 ID 的待处理记录，再上传文件，成功后更新对象存储键和处理状态；如果后续步骤失败，则记录失败原因并支持补偿重试。

对于异常中断导致的孤立对象，还可以通过定期检查任务记录与对象存储之间的对应关系，清理确认不再需要的临时文件。具体的操作顺序需要结合业务对数据完整性的要求来确定。

##### 面试官：这个项目需要 Redis 或消息队列吗？

建议回答：

如果只是一个小型个人项目，可以先通过 FastAPI 的后台任务能力或者独立工作进程实现最简单的异步处理。

但如果涉及大文件、高并发上传、多个文档任务并行处理以及失败后可靠重试，我会考虑引入消息队列和独立 Worker，让 API 服务负责接收请求，Worker 负责执行文档处理任务。

Redis 可以用于缓存、任务协调或限流等场景，但不应该为了增加技术栈而强行使用。具体选型取决于任务规模、可靠性要求和运维成本。

##### 5. 最后一道综合题：这个项目中，你认为最有技术含量的部分是什么？

建议回答：

我认为比较有技术含量的部分是将设备业务逻辑和 RAG 检索链路结合起来，而不是简单地调用一个大模型接口。

如果不做设备识别和过滤，即使检索模型本身效果不错，也可能将相近型号的手册召回，最终生成看起来合理但实际上不适用的回答。

因此，我会先通过结构化信息识别设备并确认用户访问范围，再进行混合召回、结果融合和重排序，最后让大模型基于真实文档生成答案。

从后端的角度看，还需要保证文档从上传到可检索的状态一致性、任务失败后的重试，以及会话和资料的权限隔离。只有这些业务环节能够正确协作，RAG 才能真正作为一个可维护的应用运行起来。

#### 四、把后端业务逻辑串成一条完整的面试回答

如果面试官不问具体技术，而是问：

“你能不能从后端角度完整讲一下，用户提问之后，系统是怎么运行的？”

你可以用下面这段回答。这是最值得练熟的一段。

用户发起问题后，FastAPI 首先会验证用户身份和会话权限，然后读取必要的历史消息，并将当前问题交给 LangGraph 查询工作流处理。

工作流先识别问题中的设备名称、型号和故障码。如果设备不明确，就返回候选设备供用户确认；确认后，后端会结合用户权限、设备信息和文档版本生成检索过滤条件。

随后执行 BGE-M3 混合检索，必要时通过 HyDE 扩展查询，再使用 RRF 融合多路召回结果，并通过 Reranker 对候选片段重新排序。符合条件时，还可以通过 MCP 工具补充外部资料。

检索完成后，系统将相关文档片段及来源信息传给大模型，生成答案并通过 SSE 逐步返回前端。会话消息、处理状态以及引用来源会按照业务规则保存到 MongoDB，原始文档和图片保存在 MinIO，向量索引则维护在 Milvus 中。

整个过程中，我会重点处理设备过滤、接口权限、失败重试以及文档处理状态，避免检索到错误资料，或者出现上传成功但文档实际上不可检索的情况。

#### 五、面试前建议重点记忆的知识点

如果准备时间有限，优先掌握下面这些内容。

LangGraph

能解释 State、节点、条件边、失败分支与持久化检查点的作用，并说明为什么后台任务不能只靠工作流框架保证可靠执行。

RAG 检索链路

能说明切片为何保留元数据，稠密与稀疏检索的区别，HyDE、RRF、Reranker 各自解决什么问题，以及如何提供可验证的引用。

FastAPI 业务开发

能解释 Router、Service、Repository 的职责划分，接口参数校验、权限验证、异步任务、幂等处理、异常响应和重试策略。

数据与安全

能说明 MongoDB、MinIO、Milvus 的职责区别，文档状态流转、多租户数据隔离，以及如何处理跨系统写入失败。

最后提醒你一个很关键的面试原则： 对于 Python 后端，不需要把自己包装成资深后端工程师。你真正需要证明的是，你能理解业务需求，借助 AI 编程工具实现合理的接口和业务逻辑，并且能够自己理解、调试和解释代码。

尤其是项目中的 RRF、HyDE 和 MCP 等技术，如果只是看过概念，最好先用少量测试文档搭建一个真实可运行的流程。相比背出一套复杂的技术架构，能够现场讲清楚一条请求如何从 FastAPI 进入 LangGraph、怎样检索资料、如何处理异常并最终返回结果，会更有说服力。
