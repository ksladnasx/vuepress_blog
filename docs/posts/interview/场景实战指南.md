# 场景题实战指南

> 这份文档只训练一件事：**拿到一道陌生场景题时，按什么顺序想、按什么标准选、按什么方式说。**
>
> 全文只有一条思维主线，先放在这里，后面每一章都在展开它：
>
> **看到一个复杂场景 → 拆实体 → 找状态 → 看操作 → 选数据结构 → 设计状态流转 → 处理边界 → 分析复杂度 → 考虑规模化。**

---

## 一、什么是前端二面场景题

一面通常考语言基础、手写 API、算法题，答案对错分明。二面的"场景设计题"是另一种题型：面试官给你一段业务或游戏的描述——

- 设计一个双人贪吃蛇对战游戏；
- 设计一个聊天系统；
- 设计一个实时排行榜；
- 设计一个在线协作白板；
- 设计一个拖拽排序系统；
- 设计一个文件分片上传系统；
- 设计一个高频监控数据大屏。

然后让你现场讲清楚：数据怎么存、状态怎么变、流程怎么走、出问题了怎么办。

**这类题不是在考"你能不能把代码写出来"。** 面试官自己也知道 40 分钟写不完一个游戏。他真正在看的是六件事：

1. **拆解能力**：能不能把一团模糊的需求拆成几个清晰的模块和实体；
2. **结构选择**：能不能根据"这份数据会被怎么操作"来选数据结构，而不是背"链表比数组高级"这类结论；
3. **状态设计**：能不能设计出完整、自洽的状态变化流程——谁触发、改什么、影响谁；
4. **边界意识**：能不能主动想到同时发生、重复操作、非法输入、极端数据量这些犄角旮旯；
5. **复杂度意识**：说 O(n) 时知不知道 n 是谁、贵在哪一步、能不能优化；
6. **表达能力**：能不能把上面这些有条理地讲出来，让人听懂。

两个常见误区，先排掉：

- **误区一：上来就写代码。** 场景题的时间应该花在设计上，代码最多写到伪代码。你开始写代码的那一刻，就放弃了展示"怎么想"的机会。
- **误区二：堆术语。** "这里我们应该用 B+ 树"——然后说不出为什么。没有推理支撑的术语是减分项。面试官想听的是推理链："因为这份数据最高频的操作是 X，所以选 Y。"

还有一点值得知道：面试官心里往往有一张评估清单——有没有先问规则、有没有主动谈边界、有没有主动算复杂度……你每主动覆盖一项，把握就多一分。所以本文教的"套路"不是贬义，它是保证你在紧张状态下也不漏项的检查单。

## 二、拿到场景题后的通用思考框架

先给总流程，后面逐步展开：

```text
第一步：明确规则和输入输出
      ↓
第二步：找核心实体
      ↓
第三步：设计核心数据结构（看操作，不看名字）
      ↓
第四步：设计状态变化（事件 → 状态 → 影响）
      ↓
第五步：处理边界情况
      ↓
第六步：分析复杂度（说清楚 n 是谁）
      ↓
第七步：考虑规模扩大（10 → 100 → 10000）
```

### 第一步：明确规则和输入输出

场景题的题干是自然语言，第一件事是把它翻译成"程序能处理的规则"。这个过程会逼你发现题目里没说清的地方，而**该问就问**——问规则不是露怯，恰恰是在告诉面试官"我知道这里藏着边界情况"。

比如"每 10 秒刷新 100 个苹果"这句话，翻译过来是：

- 系统里存在一个 10 秒的周期定时器；
- 每次触发时批量生成 100 个苹果；
- 生成位置随机，且不能和现有物体重叠；
- "刷新"这个词本身有歧义：是补足到 100 个，还是无条件新加 100 个？——值得问一句。

其他常值得确认的：场地多大？一格能站几个东西？一方死亡后游戏立刻结束还是继续？苹果能生成在蛇身上吗？

### 第二步：找核心实体

最简单的办法：把题干读一遍，把名词圈出来。

"双人对战贪吃蛇"——玩家、蛇、苹果、场地（游戏本身）。圈出来之后做一次筛选：哪些是需要维护状态的实体，哪些只是描述性的词。留下来的每个实体，后面都要回答"它存什么、它被怎么操作"。

### 第三步：设计核心数据结构

对每个实体问三个问题：

1. 它需要保存哪些字段？
2. **它最高频的操作是什么？**（增？删？改？查存在性？查附近？按序遍历？）
3. 它的数据量级大概多大？

第 2 个问题是灵魂。**数据结构不是按名字选的，是按操作选的。** 这是第三章的全部内容。

### 第四步：设计状态变化

回答三件事：

- 什么事件会触发变化？（用户输入、定时器、网络消息、其他变化的连锁反应）
- 变化发生时，更新哪些状态？
- 更新之后要通知谁？（渲染、对方玩家、计分、胜负判定）

到这里，系统的骨架就有了：实体是名词，事件是动词，状态是结果。

### 第五步：处理边界情况

留一份固定清单，每次过一遍：

- **同时发生**：两个事件同一时刻触发，先算谁？
- **重复操作**：同一个按钮连点、同一条消息重复送达；
- **空数据**：列表为空、没有苹果、没有玩家；
- **非法数据**：越界的坐标、格式错的消息；
- **冲突**：两个人改同一个东西；
- **极端数据量**：蛇长到几万节、列表几十万条；
- **网络异常**：断线、乱序、迟到、重复；
- **高频更新**：每秒成百上千次变更打进来怎么办。

面试时建议真的留出两三分钟专门讲边界——大部分候选人讲完主干就停了，这部分是拉开差距的地方。

### 第六步：分析复杂度

规矩只有一条：**每说一个 O(n)，必须能回答三个问题——n 是谁？这个 n 在哪一步产生的？最坏情况长什么样？**

"碰撞检测是 O(n)"——这句话没有信息量。"如果遍历蛇身做碰撞，复杂度是 O(L)，L 是蛇的长度，开销产生在每次移动都从头扫到尾；如果我维护一个'坐标 → 占用者'的哈希索引，查询变 O(1)，代价是每次移动要顺手维护索引"——这才是面试官想听的。

### 第七步：考虑规模扩大

让数据在脑子里涨三个数量级：10 → 100 → 10000。每涨一级问一句：哪里先撑不住？

常见的瓶颈演化路径：

- 全量遍历撑不住 → 上**索引**（Map / Set）；
- 两两对比撑不住 → 上**空间划分**或分桶；
- 全量重渲染撑不住 → **局部更新**、虚拟列表；
- 单线程算不过来 → **Worker**、下沉服务端；
- 单条处理太频繁 → **缓冲、批处理、降频**。

### 这个框架为什么有效

最后正面回答"为什么值得记这个流程"：

1. **它把开放题变成了有限步骤。** 场景题最怕的不是难，是"不知道从哪说起"。有了固定流水线，紧张的时候也有路可走。
2. **步骤顺序就是依赖顺序。** 不弄清规则就拆不好实体，不知道操作就选不对结构，不知道结构就谈不了复杂度——顺着走，几乎不会说出没根据的话。
3. **它天然覆盖面试官的评估清单。** 拆解、结构、状态、边界、复杂度、扩展性——一步一项，讲完框架就讲完了考点。
4. **它可伸缩。** 时间充裕时每步展开聊十分钟；时间紧张时每步一句话，也能撑起一个完整的回答骨架。

## 三、数据结构选择方法：从操作出发，而不是从名字出发

传统数据结构课按"是什么"组织：先讲链表的定义，再讲应用。面试设计题要反过来：**先看这份数据会被怎么操作，再看哪种结构的这种操作最便宜。**

一张速查表先放在这里，后面逐个展开：

| 当题目反复出现这种需求 | 就该想到 | 代表场景 |
| --- | --- | --- |
| 顺序存、按下标取、整体遍历 | Array | 蛇身、消息列表、待渲染元素 |
| 频繁在头尾增删 | Deque / 双端队列 | 蛇身移动、滑动窗口、最近 N 条 |
| 已知位置、频繁在中间插删 | Linked List | LRU、编辑器内部序列 |
| 反复问"存不存在" | Set | 占用格、去重、已传分片 |
| 反复问"这个 key 对应的是谁" | Map | id→对象、坐标→占用者 |
| 先来先处理 | Queue | 任务队列、消息缓冲、BFS |
| 后进先出、要撤销 | Stack | 撤销重做、DFS、括号匹配 |
| 反复取最大/最小/前 K | Heap | Top K、定时任务、优先级调度 |
| 反复问"附近有什么" | Grid / 空间索引 | 大地图碰撞、范围查询 |

### Array（数组）

**什么信号：** 数据有顺序、要按下标访问、要整体遍历、量不大。

**为什么合适：** 下标访问 O(1)；内存连续、遍历时缓存友好；在 JS 里也是最顺手的序列工具。

**坑在哪：**

- 头部插删（`unshift` / `shift`）要把后面所有元素整体挪位，O(n)；
- 中间插删（`splice`）同样 O(n)；
- 无序数组的查找只能遍历，O(n)。

**面试里怎么说：** "蛇身如果只是按序遍历、量也不大，数组就是最优解——简单本身就是一种性能：代码路径短、引擎有优化、缓存友好。但每次移动都要头插的话，我会注意到 unshift 是 O(L) 的，规模大了就要换。"

### Linked List（链表）

**什么信号：** 已经拿到了某个节点，要在它前后频繁插删；或者序列头尾高频进出、又不想每次搬动整个数组。

**为什么合适：** 插删只改指针、不动其他元素；拿到节点引用后插删 O(1)。

**坑在哪：**

- JS 没有内置链表，要手写；
- 每个节点一个对象，内存开销和 GC 压力比连续数组大；
- 想访问第 i 个元素只能从头走，O(n)；
- 节点在内存里散落，遍历不如数组缓存友好。

**必须建立的认知：** 链表不是因为"它高级"才被使用，是因为某些操作模式只有它便宜。反例：一个序列如果从头到尾只做"顺序遍历"，链表反而更慢更费内存——这时候数组全方位更好。典型正例是 LRU 缓存：命中后要把节点摘下来插到头部，中间摘插是家常便饭，链表才出场。

**代表场景：** 贪吃蛇的身体（每步头插一格、尾删一格）、LRU、文本编辑器内部的大文本分段。

### Set

**什么信号：** 题目反复在问"某个东西在不在"——这一格有没有蛇身？这个分片传过没有？这个 ID 处理过没有？

**为什么合适：** 基于哈希，`has` / `add` / `delete` 平均 O(1)。把"存在性判断"从 O(n) 遍历降到 O(1)，是设计题里性价比最高的一类优化。

**坑在哪：** Set 只能回答"有没有"，回答不了"是谁的、是什么"。当你在判断存在之外还需要知道归属或详情，就该升级成 Map。

**代表场景：** 蛇身占用格、坐标去重、断点续传时"已上传分片"集合。

### Map

**什么信号：** 需要 key → value 的映射——userId 找用户、nodeId 找节点、id 找状态、坐标找占用对象。

**为什么合适：** 哈希查找平均 O(1)，而且 value 想装什么装什么。

**两个高频用法：**

1. **给 Set 升级**：`Set<坐标>` 告诉你这格有没有蛇，`Map<坐标, snakeId>` 还告诉你是谁的蛇。设计题里的"占用索引"几乎总是后者，因为撞上之后还要分"撞自己还是撞别人"。
2. **当稀疏容器用**：把坐标拼成 key（比如 `x * 10000 + y`），Map 就是一张只为"有东西的格子"分配存储的二维表——这在超大地图场景里是关键技巧（第十章展开）。

**坑在哪：** key 是对象时按引用比较，两个内容相同的对象是两个 key；做 key 尽量用字符串或数字。

### Queue / Deque（队列 / 双端队列）

**什么信号：** "先来的先处理"——任务、消息、BFS 的待访问层；或者"两端都要进出"——滑动窗口、最近 N 条、蛇身。

**为什么它经常出现在系统设计题里：** 大量系统本质是生产者-消费者：上游产生任务/消息的速度和下游消费的速度不一致，中间就需要一个队列做缓冲。队列同时是"削峰"的工具——高频流入先攒着，下游按自己的节奏批量取。

**Deque 的意义：** 普通队列只从一头进一头出；双端队列两头都能进出。蛇身就是标准 Deque：头进（新头）、尾出（旧尾）、吃苹果时只进不出。

**JS 现实：** 没有内置 Deque。小规模直接数组 `push` + `shift`；规模大了用"数组 + 头指针"的环形缓冲，头尾操作都 O(1)，几十行就能写完。

**代表场景：** 上传任务调度、消息缓冲区、BFS、最近 N 秒数据的滑动窗口。

### Stack（栈）

**什么信号：** "后进先出"——最后做的最先撤销；深度优先；配对匹配。

**为什么编辑器都爱它：** 撤销重做的天然模型就是两个栈——undo 栈和 redo 栈。做一个操作压 undo 栈；撤销时弹出来执行"逆向操作"并压入 redo 栈；一旦做了新操作，redo 栈清空。

**代表场景：** 撤销/重做、操作历史、DFS、括号匹配。

### Heap / Priority Queue（堆 / 优先队列）

**什么信号：** 反复要"最大 / 最小 / 前 K 个"，但不想每次都全量排序。

**为什么合适：** 插入 O(log n)、看堆顶 O(1)，堆顶永远是你当前最想要的元素。维护一个大小为 K 的小顶堆就能滚动求 Top K：新元素比堆顶大就替换进去，全程 O(n log K)。

**坑在哪：**

- JS 没有内置堆，面试可以说"手写一个也就几十行"，小规模直接 `sort` 也完全诚实；
- **堆回答不了"某个元素的排名是多少"**。排行榜要支持"查我排第几"时，堆不够用，得用真正有序的结构。

**代表场景：** Top K、定时任务（按到期时间组织的小顶堆，每次只看堆顶到没到时间）、优先级调度、实时排行榜。

### Grid / 空间索引（网格、空间哈希、四叉树）

**什么信号：** 地图大、对象多，问题里反复出现"附近""范围内""会不会碰到"。

**核心思想一句话：** 把"遍历所有对象两两比较"换成"只查我附近格子里的对象"。

**三个档位：**

- **网格**：把地图切成固定大小的格子，每个对象登记到所在格子。碰撞、邻近查询只看同格和相邻格。对象分布均匀时它最简单高效。
- **空间哈希**：地图巨大而稀疏时（比如 10000×10000 但只有几百个对象），不为每个格子分配存储，只对"有对象的格子"建哈希——本质就是上面说的"Map 当稀疏容器"。
- **四叉树**：对象密度极不均匀时，密的区域自动细分、空的区域粗放管理。面试里点到名字、说清"什么时候才需要它"就够，不要求手写。

**什么时候不需要：** 场地小、对象少的时候，暴力遍历最便宜，空间索引纯属自找复杂。

**一个具体感受：** 1000×1000 的场地、几十条蛇，暴力完全没问题；变成 10000×10000、100 条蛇、还要频繁问"我附近有什么"，两两比较就是每秒上百万次级别的比较，这时就该从"遍历全部对象"转向"只查询附近对象"了。

### 选结构的表达公式

面试里每确定一个数据结构，建议把这句话说完整：

> "这份数据最高频的操作是 ___，数据量级是 ___，所以选 ___；它的代价是 ___；如果 ___（量级或操作模式）变了，我会换成 ___。"

四个空能填出来，这个选择就立得住；填不出来，说明还没想清楚，别急着报结构名。

## 四、真题完整拆解：双人对战贪吃蛇

下面按真实面试的思维顺序，把这道题从头拆一遍。每一步都保留"为什么先想这个"。

### 4.1 先理解题目

题面大致是：

> 实现一个双人对战贪吃蛇：
> - 网格场地，两条蛇各自用键盘控制方向，蛇按固定节奏移动；
> - 场地上有苹果，吃到苹果蛇变长、加分；
> - 撞墙、撞到自己、撞到对方身体 → 判负；
> - 两个蛇头相撞 → 忽略，不判负；
> - 每 10 秒在场地内刷新 100 个苹果；
> - 需要实现 `onKeyboardEvent(key, player)` 和 `tick(deltaTime)`；
> - 追问：如果场地扩大到 10000×10000、有 100 条蛇同时移动，怎么办？

理解题目要做的不是马上下结论，而是三个动作：

**动作一：把规则翻译成程序概念。**

- "撞墙" → 新头坐标的越界判断；
- "蛇身" → 一串有序的格子 + 一份"哪些格子被占、被谁占"的索引；
- "苹果" → 一批带坐标的对象，核心操作是"这一格有没有苹果"；
- "每 10 秒" → 游戏内累计时间驱动的周期事件，而不是随口一个 `setInterval`；
- "两条蛇" → 立刻意识到这题有**多方同时变化**的问题——这是它区别于单机贪吃蛇的核心。

**动作二：把没说清的地方问出来。** 每一个问题都对应一个隐藏边界：

- 撞到对方的"头"算"蛇头相撞"还是"撞身体"？（决定碰撞怎么分类）
- 蛇死掉之后，蛇身是消失还是留在场上当障碍物？
- 苹果能生成在蛇身上吗？
- 两条蛇同一 tick 都死了，算平局还是比长度？
- 一方死亡后游戏立刻结束，还是另一条继续玩？

面试现场不一定有时间全问，但**主动问出两三个，就是在向面试官展示边界意识**。

**动作三：明确输入和输出。** 输入：键盘事件（谁按的、按了什么）、时间流逝（deltaTime）。输出：每一帧的画面、分数变化、胜负结果。所有设计都要服务这条"输入 → 状态 → 输出"的链路。

面试开场可以这么说：

> "我先确认几个规则……然后我会把系统拆成游戏、玩家、蛇和苹果几个实体，再看每个实体最高频的操作是什么——比如蛇身是频繁的头进尾出，占用关系是频繁的存在性查询，这两件事我会用两份数据结构分开管。"

### 4.2 核心实体拆分

圈出来的实体有四个：Game、Player、Snake、Apple。逐个过"存什么、被谁操作"：

**Game（游戏）**——全局状态的持有者：

- 游戏阶段（等待中 / 进行中 / 已结束）——一个显式的状态机字段；
- 场地尺寸（宽、高）；
- 蛇列表、苹果集合；
- 时间累计器、苹果刷新计时器；
- 胜负结果。

**Player（玩家）**——很薄的一层：

- 玩家 id、按键映射（哪个键代表哪个方向）。

Player 薄到可以和 Snake 合并。面试时可以主动说："这个场景里玩家和蛇是一对一的，我会把它们合并成一个对象；如果是大厅多房间，Player 就要独立出来管房间归属。"——这叫说明取舍，而不是为了拆而拆。

**Snake（蛇）**——本题主角，单独展开（见下）。

**Apple（苹果）**——几乎没有内部状态：

- 就是坐标（顶多再加个分值/类型留扩展余地）。

苹果的重点根本不在"字段"，而在**集合怎么组织**——一百个苹果用什么容器装、怎么查、怎么删，这是第六章的主题。

#### 蛇的数据结构：这题第一个真正的设计点

先别管用什么结构，**先列蛇身会被怎么操作**：

1. 每次移动：头部加一格、尾部减一格——高频，每步都发生；
2. 吃苹果：头部加一格、尾部不动——低频；
3. 碰撞检测：问"某个格子有没有被蛇占、被谁占"——极高频，每步每条蛇都要问；
4. 渲染：从头到尾按序遍历——每帧发生；
5. 访问第 i 节身体 / 在中间插删——基本不会发生。

操作清单一列，答案就清晰了：**需要一个"头尾操作便宜"的有序序列 + 一个"存在性查询便宜"的占用索引。** 这是两份数据，各管一件事，不要指望一个结构包打天下。

**方案 A：普通数组，头在 index 0。**

- 移动 = 头部插入新格 + 尾部弹出一格。`pop` 是 O(1)，但头部插入（`unshift`）要把整个数组往后挪，O(L)；
- 按序遍历渲染：没问题；
- 蛇长几十几百时，O(L) 的头插实际开销微不足道，**这是完全合理的起手方案**——先能跑，且好读好调。

**方案 B：双端队列 / 环形缓冲。**

- 逻辑上就是"队列"：新头从一端进，旧尾从另一端出，两端操作都是 O(1)；
- JS 没有内置，常用"数组 + 头指针"实现（写满就整体整理一次，摊销 O(1)）；
- 蛇可能长到几千几万节时（贪吃蛇大作战那种），它就明显比数组划算。

**方案 C：链表（头尾各存一个指针）。**

- 头插 O(1)，尾删 O(1)（需要双向链表 + 尾指针）；
- 按序遍历也没问题；
- 代价是每个节点一个对象、缓存不友好、JS 里还得手写；
- 结论：逻辑上完全成立，但在 JS 里相对方案 B 收益不大——除非场景里还出现"在蛇身中间摘除某节"这类操作。

**三方案对比着说，才是面试想要的答案。** 顺序是：先列操作 → 逐方案对操作算账 → 按规模给结论。结论本身反而是最不重要的一部分：

> 小规模用数组，简单可靠；长度可能巨大，用环形缓冲；它逻辑上就是一条队列。

**然后是本题最关键的一步：碰撞检测不靠遍历蛇身，靠占用索引。**

不管蛇身用什么序列实现，"这个格子有没有被占"都不应该去扫序列，而是单独维护一份：

```text
占用索引：Map<坐标, snakeId>
```

- 蛇头移入新格：`set(新头, snakeId)`；
- 尾巴移出一格：`delete(旧尾)`；
- 碰撞检测：`get(新头)` 一次哈希查询，O(1)。

为什么用 Map 而不是 Set？因为撞上之后还要回答"撞的是谁"——是自己（判负）、对方身体（判负）、还是对方的头（蛇头相撞，忽略）。Set 只能给"有没有"，Map 才能给"是谁"。**这一个选择，直接支撑了第七章所有碰撞分类。**

坐标当 key 的两个选择：字符串 `"x,y"` 直观好调试；数字 `x * 宽 + y` 更省内存更快。提一句即可，属于锦上添花。

**蛇头存哪？** 就是序列的第一格，不需要单独变量。真正需要单独存的反而是两样东西：**当前方向**和**待处理方向队列**——它们是行为状态，不是身体状态，下一章讲。

## 五、贪吃蛇的状态更新流程

### 5.1 玩家输入：onKeyboardEvent(key, player)

事件进来，只做四件事：

1. **翻译**：把按键映射成方向（WASD 对玩家一、方向键对玩家二之类），不是方向键的直接忽略；
2. **合法性**：是不是上下左右之一；
3. **防反向**：新方向不能和"当前生效方向"相反（蛇长 > 1 时；长度为 1 的蛇没有反向问题）；
4. **入队**：把方向放进这条蛇的**待处理方向队列**（长度限制 1~2），然后返回。**不要在这里直接改"当前方向"。**

为什么不直接改？因为一个移动周期里可能按了好几个键，直接改会造出经典 bug：

> 蛇正在向右移动，玩家在一帧内快速按了"上、左"。如果直接改方向，最终生效的是"左"——下个 tick 蛇头向左走，而左邻格正是它的第二节身体，蛇"撞死"在自己身上。

放进队列就没事：每个 tick 移动时从队列取**一个**方向，取出时再校验一次和"上一次实际移动方向"不反向，然后才生效。快速连按会变成连续两个 tick 的两次合法转向。这是贪吃蛇最著名的坑之一，主动讲出来非常加分。

### 5.2 游戏时间：tick(deltaTime)

`tick` 由 `requestAnimationFrame` 每帧调用，`deltaTime` 是距上一帧的真实毫秒数。

**为什么不能"tick 执行一次 = 蛇移动一次"？**

因为 rAF 的频率跟着屏幕刷新率走，而帧率是不可靠的：60Hz 和 120Hz 的显示器差一倍；掉帧时一秒少几次；标签页切后台浏览器还会节流。如果每帧移动一次，游戏速度就绑死在帧率上——同一台机器忽快忽慢，换个高刷屏游戏直接快一倍。

正确做法是把"游戏节奏"定义在游戏时间里，比如"每 100ms 移动一步"，然后让 tick 做时间累计：

```text
每帧：
    累计器 += deltaTime
    while 累计器 >= 步长(100ms):
        走一步()
        累计器 -= 步长
```

- 帧率正常时：大约每 6 帧（60Hz）走一步；
- 120Hz 屏幕：每 12 帧走一步——**游戏速度一样**；
- 掉帧时：这一帧累计够两步，就连续走两步——逻辑没有丢时间；
- 同时给循环加个上限（比如一次最多补 5 步），防止切后台回来后"追赶"卡死主线程。

"每 10 秒刷 100 个苹果"同理：另立一个苹果计时器累计时间，到 10 秒触发一次。不要用 `setInterval`——后台会节流、和游戏循环不同步、游戏暂停时它照跑。

这套"逻辑节奏用累计时间驱动、渲染跟随 rAF"的思路，是第十章"逻辑与渲染分离"的地基。

### 5.3 蛇移动：一步之内发生什么

一次移动的内部分六步，顺序本身就是答案：

1. **消费输入**：从待处理队列取一个方向，校验不反向后更新当前方向；
2. **计算新头**：当前头坐标 + 方向向量，得到新头坐标。注意：只是**算出来**，还没有动；
3. **碰撞检测**：拿新头坐标查边界和占用索引（第七章展开）；
4. **吃苹果判断**：查苹果集合里有没有这个格子；
5. **提交移动**：新头插入序列、占用索引登记；吃了苹果 → 尾巴不动（长度 +1）；没吃 → 尾巴弹出、索引注销；
6. **标记结果**：如果撞了，标记"这条蛇本步死亡"——注意是**标记**，不是立刻改游戏状态（第八章统一结算）。

**碰撞应该在移动前判断，还是移动过程中判断？**

应该在**提交移动之前**、基于"移动前的世界状态"判断。两个理由：

- **表现正确**：死了就不该真把头移进去。先 unshift 再检测，发现撞了还得回滚，蛇头还会在画面上"穿"进墙或身体一帧；
- **公平正确**：双人对战里两条蛇在同一步同时移动。判断必须基于同一个"移动前快照"，谁先谁后都不能影响结果——这直接引出第七章的"计算与结算分离"。

而"移动中判断"（先改状态再检查）会把这两点全部破坏：状态已经脏了，检测逻辑还得处处排除"刚被自己改过的部分"，又难写又容易错。

## 六、苹果系统设计

**苹果存什么？** 坐标，顶多加个分值。苹果几乎没有行为，所以设计重点在集合。

**用什么容器装？** `Map<坐标, apple>`（需要装分值/类型就用 Map，纯坐标用 Set 也行）。理由：

- 蛇头移动时的第一问就是"这一格有没有苹果"——存在性查询，Map/Set O(1)；
- 吃掉 → `delete(坐标)`，O(1)；
- 生成时防重叠 → 生成前 `has(坐标)` 一次查询，天然防苹果之间重叠，再查一下占用索引防和蛇重叠。

**为什么不用数组？** 数组回答"这一格有没有苹果"要遍历 O(A)。虽然 A = 100 时遍历也死不了人（下面会正面说这件事），但 Map 的写法和数组一样简单，还顺带把"防重叠、O(1) 删除"做对了——**当两种方案成本相同时，选语义更准的那个**。

**如何生成随机位置？**

```text
生成一个苹果：
    随机取 x, y
    最多重试 20 次：
        若坐标在界内、不在占用索引里、不在苹果集合里 → 放置并登记，结束
    重试用尽（场地太挤）→ 兜底：遍历收集所有空格，随机挑一个
```

随机重试在"空格还很多"时期望一两次就成功，O(1)；兜底扫描保证最坏情况也能终止。**先给期望路径，再给兜底路径**，这是面试里回答"随机生成"类问题的标准姿势。

批量刷 100 个就是循环调它——每放一个就立刻登记，天然保证这 100 个互不重叠。

**吃掉后如何删除、如何避免遍历？** 删除挂在蛇移动的第 4、5 步上：查苹果 Map → 有就 delete + 加分 + 蛇增长。全程没有一次"遍历所有苹果"。

**诚实讨论：100 个苹果，需要这么讲究吗？**

不需要。100 个苹果、每秒 10 步、2 条蛇，就算每步把苹果数组全遍历一遍，也只是每秒几千次比较——性能上毫无压力。选 Map 不是因为性能救急，而是因为：

1. 它让"存在性查询、防重叠、O(1) 删除"三件事用同一份结构顺带解决，逻辑最干净；
2. 它给规模化留了口子——苹果要是变成一万个、场地变成一万见方，不用换设计。

**数据结构应该和规模匹配，也要和"最可能的变化方向"匹配——但永远不要为了炫技上复杂结构。** 面试里主动承认"这个规模下数组其实也够，我选 Map 是为了语义和扩展"，比硬吹"我用哈希索引优化了性能"更加分。

## 七、碰撞检测设计

这是本题最重要的一章。碰撞一共四种情况，难度递增。

### 7.1 撞墙

新头坐标 `x < 0 || x >= 宽 || y < 0 || y >= 高` → 死。O(1)，没有悬念。

### 7.2 撞自己

查占用索引：`占用.get(新头) === 自己的 id` → 死。O(1)。

一个值得主动提的规则细节：**尾巴格**。如果这一步蛇没吃苹果，尾巴会同时移走——新头恰好落在旧尾的位置时，严格按"移动前快照"算，蛇死了；按"尾巴同时移走"算，蛇活。两种都是合理规则，题目没说清就**选一种、说清楚**（推荐简单版：按快照，尾格也算占用）。面试里能主动指出这个二义性，比选哪个答案本身更加分。

### 7.3 撞对方身体

`占用.get(新头)` 得到的 id 不是自己，且那一格不是对方的**头** → 死。O(1)。

### 7.4 两个蛇头相撞：为什么"忽略"，程序上怎么处理

题目规定蛇头相撞不判负。这个规定本身很讲道理：两头对撞是**对称事件**——判谁输都不公平，除非引入"谁速度快谁赢"这种题目没给的规则。所以"忽略"是唯一公平的默认。

程序上要做的是把"头对头"从"撞身体"里**分类出来**。头对头有两种形态：

1. **同格相撞**：A 的新头和 B 的新头落在同一个格子；
2. **互换穿越**：A、B 头挨着头，A 的新头 = B 的旧头位置，B 的新头 = A 的旧头位置——按快照判断，各自都"撞上了对方的头"。

处理方式：

- 先各自算出新头（都在提交前）→ 比较两个新头坐标：相同 → 双方标记"头对头"，跳过死亡；
- 再做互换检测：`A 新头 == B 旧头 && B 新头 == A 旧头` → 双方同样跳过；
- 兜底规则：查占用索引发现目标格是**对方的头** → 也按头对头处理，忽略。

结果：两条蛇都正常移动，可能短暂重叠一格，渲染上叠着画即可（或规定共占，说清楚就行）。一个随之而来的小细节：同格头对头时"一格两主"——占用索引要么允许一格记多个占用者，要么规定后到者不登记（两条蛇下一 tick 就各奔东西，只要规则定死、维护一致，两种都可以）。面试里点出这个细节并给出一种选择即可。

这里再次看到为什么占用索引必须是 `Map<坐标, snakeId>`——没有"是谁"的信息，根本做不了这个分类。

### 7.5 双方同时死亡：本题最重的边界条件

构造一个场景：A 的新头撞进 B 的身体，**同一个 tick**，B 的新头也撞进了 A 的身体。两条都该死。

**错误的做法**：

```text
处理 A：发现撞了 → A 死 → 游戏结束，B 获胜 → 结束循环
```

B 的碰撞根本没有被判断。如果换过来先处理 B，胜者就变成 A——**游戏结果取决于处理顺序**，这是设计里最糟的一类 bug：结果不确定。

**正确的做法：把"状态计算"和"状态结算"分开。**

- **计算阶段**：基于同一份移动前快照，把所有蛇的新头、碰撞分类、吃苹果情况**全部算出来**。这个阶段只读、只产出"结果单"，不改任何全局状态——两条蛇都会被标记死亡，谁也不影响谁；
- **结算阶段**：拿着结果单**一次性**应用：两条都死 → 平局（或按题目规则比长度）；一条死 → 对方胜；都没死 → 应用移动。

```text
一次 tick：
    ① 计算：对每条活蛇，算新头、判碰撞、记吃苹果 —— 只读快照，不改状态
    ② 结算：根据结果单统一处理死亡、胜负、移动、加分
```

为什么这样就能对：

1. **结果与处理顺序无关**。所有判断都基于同一份快照，M 条蛇谁先算都一样；
2. **计算是纯函数**。输入快照、输出结果单，可以单独构造用例测试（"两条蛇互撞"可以直接构造快照来测，不用真跑游戏）；
3. **天然扩展到 N 条蛇**。100 条蛇也只是"全员计算 → 全员结算"，规则不变。

这个思想不止用于游戏：数据库事务"先算校验、再统一提交"，协作编辑"先算冲突、再应用操作"，都是同一个模式。**面试里把它总结成一句通用结论说出来，是重要的加分动作**：

> "多个对象同时变化时，先全部计算，再统一提交，保证结果不依赖处理顺序。"

## 八、tick() 的核心逻辑（伪代码）

先把骨架写出来，再解释每一步为什么在那个位置。

```text
function tick(deltaTime):                    # 每帧被 rAF 调用
    累计器 += deltaTime                      # 时间累计：节奏用游戏时间，不用帧数
    苹果计时器 += deltaTime

    while 累计器 >= 步长:                     # 到点才走；掉帧一次可补多步（封顶）
        累计器 -= 步长
        走一步()

    if 苹果计时器 >= 10秒:                    # 苹果是独立的时间线
        苹果计时器 -= 10秒
        批量生成苹果(100)
```

```text
function 走一步():
    # ========== 阶段一：计算（只读快照，不改全局状态） ==========

    for snake in 存活蛇:
        方向 = 从待处理队列取一个并校验        # 消费输入：出队 + 防反向校验
        新头 = snake.头 + 方向                 # 只是计算坐标，先不动
        snake.计划 = { 新头, 结果: 待定, 吃: null }

        if 出界(新头):
            snake.计划.结果 = 撞墙
        else:
            owner = 占用索引.get(新头)          # O(1)：这格是谁的
            if owner == snake:            结果 = 撞自己
            else if owner 存在 且 是对方的头: 结果 = 头对头（忽略）
            else if owner 存在:           结果 = 撞对方
            else:                         结果 = 通过

    检查蛇头对撞(存活蛇)                       # 新头同格 / 新旧头互换 → 双方标"头对头"

    for snake in 结果为 通过 或 头对头 的蛇:
        snake.计划.吃 = 苹果集合.get(snake.计划.新头)   # 有则记下"要吃"

    # ========== 阶段二：结算（统一应用结果） ==========

    死亡名单 = 所有 结果为 撞墙/撞自己/撞对方 的蛇
    if 死亡名单 非空:
        按规则结算胜负（全死 → 平局；单死 → 对方胜）   # 只在此处修改游戏阶段

    for snake in 结果非死亡的蛇:
        占用索引.set(新头, snake)
        新头插入蛇身头部                       # 头进
        if snake.计划.吃 存在:
            苹果集合.delete(新头); snake.分数++  # 尾巴不动 = 长度+1
        else:
            旧尾 = 蛇身尾部弹出                # 尾出
            占用索引.delete(旧尾)
```

对照"处理输入 → 累计时间 → 判断是否需要移动 → 计算下一状态 → 碰撞检测 → 吃苹果 → 更新蛇 → 统一结算死亡 → 刷新苹果"这条流程链，每一步为什么在它所在的位置：

| 流程 | 为什么在这个位置 |
| --- | --- |
| 处理输入 | 输入分两半：事件进来时只校验 + 入队（5.1），真正生效在移动时出队——这样连按不会引发一步内的反向 |
| 累计时间 | 在一切逻辑之前：先确定"这一帧该不该走、走几步"，逻辑节奏才和帧率无关 |
| 判断是否需要移动 | `while 累计器 >= 步长`：掉帧补步、高刷不多走，速度恒定 |
| 计算下一状态 | 全部蛇共用同一份移动前快照，且只读——这是公平性的来源 |
| 碰撞检测 | 在提交移动之前、基于快照——死了不会产生"穿模"状态 |
| 吃苹果 | 属于"这一步会发生什么"的计算，和碰撞同阶段，同样只读 |
| 更新蛇 | 进入结算：改动蛇身和占用索引，从这一刻起世界才变化 |
| 统一结算死亡 | 死亡在**所有蛇都算完之后**一次性处理——双死判平局，与处理顺序无关 |
| 刷新苹果 | 独立时间线，不掺和移动逻辑；生成时查占用索引和苹果集合防重叠 |

核心就一句话：**一次 tick 里，所有"判断"读同一份快照，所有"修改"集中在结算——不因为先处理玩家一，就让玩家一的结果影响玩家二。**

## 九、算法复杂度分析

先把符号定义清楚——**说 O(n) 不说 n 是谁，等于没说**：

- `L`：单条蛇的长度（节数）；
- `M`：蛇的数量；
- `S`：全场蛇身总格数（约等于所有蛇的 L 之和）；
- `A`：苹果数量。

### 逐方案分析

| 方案 | 单蛇每步成本 | M 条蛇每 tick | 备注 |
| --- | --- | --- | --- |
| 数组 + 遍历蛇身判碰撞 | 头插 O(L) + 碰撞 O(S) | O(M·S) | 最直觉的起手式 |
| 数组 + 占用 Map | 头插 O(L) + 碰撞 O(1) | O(S) | 碰撞已优化，头插成了新瓶颈 |
| 环形缓冲/链表 + 占用 Map | O(1) + O(1) | O(M) | 理论最优，作为"终极答案" |

要点逐条说：

- **O(M·S) 是怎么来的**：每条蛇每步判碰撞要遍历蛇身（撞自己 O(L)，撞对方也要扫对方的身体），M 条蛇 × 总身长 S。M = 2、蛇长几百时它毫无问题；蛇长上万、蛇上百条时，每 tick 就是千万级操作，开始真实地疼。
- **占用 Map 把存在性查询降到 O(1)**，代价是每次移动多一次 `set` / `delete` 维护索引——用 O(1) 的维护成本换掉 O(S) 的查询，稳赚。
- **环形缓冲把头插降到 O(1)**，蛇身序列的操作从此和长度无关。
- **苹果**：查询、删除 O(1)；批量生成期望 O(A)（随机重试期望常数次），最坏 O(A + 空格数)（兜底扫描）。
- **空间**：占用索引 O(S)、苹果 O(A)、蛇身 O(S)。都是"有多少实体就占多少"，没有为空格子买单。
- **渲染是另一个独立的 n**：每帧 O(S) 全画。它不归 tick 管，归第十章管。

顺带一个重要的诚实说明：在题目原始规模（2 条蛇、百格场地）下，最差的 O(M·S) 方案也快得毫无感觉。**复杂度分析的价值不是"现在的方案会不会卡"，而是"规模涨一千倍后谁先倒下、我手里的优化梯子是什么"。** 把这个说出口，比报数字本身更加分。

## 十、性能与规模化：10000×10000 和 100 条蛇

题目最后一问把规模拉到：场地 10000×10000（一亿格）、100 条蛇同时移动。逐个方向分析。

### 10.1 先算内存账：大地图第一原则是"稀疏化"

一亿格，如果给每格分配存储——哪怕每格只存一个字节——就是 100MB 级的内存，而且 99.9% 是空格子。

所以第一反应是把"密集结构"换成"稀疏结构"：**不为每格分配存储，只为有东西的格子分配**——也就是 4.2 节那个 `Map<坐标, snakeId>` 占用索引。100 条蛇哪怕每条长 1000 节，全场也只有 10 万条记录，轻松承受。

一句话总结：**规模扩大后，第一刀永远砍向"为不存在的数据分配的存储"。**

### 10.2 碰撞检测：什么时候才真的成为瓶颈

用了占用索引后，每 tick 的碰撞成本是 O(M) = 100 次哈希查询——**完全不是瓶颈**。

碰撞检测成为瓶颈的条件是出现了"两两关系"：比如每个对象有体积、要和所有邻近对象做几何碰撞，那就是 O(M²) 量级（1 万对起步）并且每对都更贵。这时才轮到空间划分出场：把地图分成大格子，每个对象登记进所在格子，两两检测只在同格/邻格内做——比较对象从"全部对"降到"附近的对"。

**分界线要能说出来：对象间是"格点式"接触 → 占用索引就够；对象间是"几何式"接触且对象多 → 网格分桶；地图巨大且稀疏 → 空间哈希；密度极不均匀 → 四叉树。** 按需升级，不要一上来就四叉树。

### 10.3 苹果查询

"这一格有没有苹果"——`Map.get`，O(1)，规模扩大后不变，因为苹果总数没有随场地变大（题面还是 100 个）。场地越大，随机生成越不会撞，连兜底扫描都更少触发。

什么情况下苹果才需要新结构？需求变成"离这条蛇头最近的苹果在哪""半径 5 格内有哪些苹果"这种**邻近查询**时——把苹果也登记进空间哈希，查询只看附近桶。

### 10.4 渲染：逻辑层与渲染层分离

这一层是新问题，也是前端最该有共鸣的一层。原则：**逻辑层和渲染层彻底分开。**

- 逻辑层：纯状态 + tick 驱动，每秒 10 步，不知道渲染的存在；
- 渲染层：每帧（60fps）读状态画一画，不知道逻辑为什么这么走。

为什么必须分：

1. **帧率波动不能影响游戏速度**——渲染跟着 rAF 走，逻辑跟着累计时间走，两者解耦（5.2 的直接推论）；
2. **一亿格的地图不可能全画**——渲染层只取视口内的格子画（视口裁剪），渲染成本从 O(S) 降到 O(屏幕内格子数)；
3. **渲染技术可替换**——今天用 Canvas，明天上 WebGL，逻辑一行不改。

具体手段（点到为止）：几万+格子用 Canvas 而不是 DOM（DOM 节点过万必卡）；静态背景离屏缓存；只重绘变化区域（脏区）；两步逻辑之间做插值让画面平滑（逻辑 10fps、观感 60fps）。

### 10.5 高频更新的通用手段

每 tick 修改大量对象时的优化菜单（按性价比排序）：

- **批量**：本 tick 的所有变更收集齐、一次应用、一次重绘——正是"计算/结算分离"在渲染侧的映射；
- **增量**：只处理变化的部分（变化的格子、变化的设备、变化的行），别全量重算；
- **降频**：不是所有事都要每帧做——苹果 10 秒一次、分数面板每秒刷一次足够；
- **缓冲 + 批量消费**：高频流入先进队列，按帧批量消化（监控大屏那道例题的核心套路）；
- **rAF 对齐渲染**：所有 UI 更新挂在 rAF 节奏上，天然合并同帧多次变更；
- **Worker**：把模拟、寻路、聚合等重计算挪进 Web Worker，主线程只做渲染；结果用结构化克隆（或 SharedArrayBuffer）传回。

这些手段背后是同一句话：**主线程只干渲染，重活挪走，通信按批。**

### 10.6 顺手说一句天花板在哪

如果题目继续追问"做成真人多人在线呢？"——方向是逻辑下沉服务端（服务端权威，客户端只发输入、收状态），状态同步用快照或帧同步，客户端插值平滑。面试里点出方向和名词即可，表明你知道单机方案的天花板在哪。

## 十一、从这道题抽象出来：面试真正考什么

回到开头那条思维主线，把贪吃蛇升级成六个可迁移的能力。

### 能力一：实体建模

把自然语言的名词转换成数据结构：圈名词 → 筛"需要维护状态的" → 每个实体回答"存什么、被怎么操作、量多大"。贪吃蛇里是 Game / Snake / Apple，聊天系统里是会话 / 消息，上传系统里是文件 / 分片。**同一个动作，不同的名词。**

### 能力二：状态管理

找到"谁在变化"。贪吃蛇里在变的是：蛇的位置和方向、苹果集合、分数、游戏阶段。两个好习惯：

- 区分**真相**和**推导值**：蛇的长度可以从身体序列推出，就不要再存一份单独的长度——或者存了就要保证处处同步（有了占用索引后，"索引和序列一致"就是这个系统的第一真相约束）；
- 状态尽量集中（Game 对象统一持有），散落在多个对象里的可变状态是不确定性 bug 的温床。

### 能力三：事件驱动

找到"什么事件导致变化"。贪吃蛇的事件只有三类：键盘输入、时间流逝、碰撞结果。每个事件问：谁消费它？改哪些状态？触发什么连锁事件？前端日常开发（点击 → 更新 state → 视图更新）就是这个模型，面试时可以点破这层迁移关系。

### 能力四：状态机 / 生命周期

凡是"对象有一生"的地方，就把生命周期显式写出来：

```text
游戏：等待 → 进行中 → 结束
蛇：  存活 → 死亡
文件：等待上传 → 上传中 → 成功 / 失败
任务：等待 → 执行中 → 成功 / 失败
```

显式状态机的好处：**"现在能不能接受这个操作"从散落的 if 变成查状态。** 比如"游戏结束后按键不再入队""死亡蛇不再参与计算"，都是一行状态判断，而不是各处打补丁。什么时候该建状态机？一个对象的状态影响它后续行为时，就该建。

### 能力五：数据结构匹配操作

把第三章压缩成口诀，现场直接调用：

> 反复查存在性 → Set；要连归属一起查 → Map；频繁头尾进出 → Deque；反复取最值 / Top K → Heap；先来先办 → Queue；要撤销 → Stack；问附近 → Grid / 空间索引；按序渲染 → Array。

每一句的完整版都在第三章，这里只要记得：**选结构的理由永远从"操作"出发说，不要从"名字"出发说。**

### 能力六：并发与一致性

双蛇同时死亡给出的通用结论：**多个对象在同一时刻变化时，先全部计算，再统一提交——让结果不依赖处理顺序。**

它会换着马甲反复出现：协作白板两人同时拖一个元素、排行榜两人同分同刻更新、聊天消息乱序到达、批量任务部分失败。判断方法就一句：**问自己"这个结果是否依赖处理顺序？"——依赖，就必须找到排序规则，或者把计算与提交分离。**

## 十三、六道例题逐一拆解（统一模板）

每道题按同一个模板走：题目 → 考察点 → 第一反应 → 数据结构 → 核心流程 → 边界 → 复杂度 → 规模扩大 → 面试表达参考。**这个模板就是第二章的框架，多过几遍它会内化成直觉。**

### 例题一：多人实时排行榜

#### 题目

> 设计一个多人实时排行榜：1000 名玩家在对战中不断得分，页面要实时显示完整排名；玩家会上下线；分数相同的情况下先达到该分数的排前面；要支持查询任意玩家的当前排名和 Top 10；如果用户量扩大到一百万，方案要怎么调整？

#### 面试官考察点

- 能否意识到"高频更新 + 频繁查排名"不能靠每次全量排序硬扛；
- 同分规则怎么程序化（次级排序键）；
- Top K 怎么取；
- 关键加分项：知道排行榜在超大规模下是服务端问题，前端只做切片展示。

#### 第一反应：先拆哪些东西

实体两个：**玩家**（id、分数、达到该分数的时间戳）和**榜单**本身。然后列操作频率：分数更新（最高频，每秒可能成百上千次）、查某玩家排名、查 Top 10、上下线（低频，且注意——上线只是状态变化，人不该从榜上消失）。**更新远多于查询**，这个比例决定了不能选"每次更新都重排"的方案。

#### 核心数据结构

- `Map<userId, player>`：主索引，按 id 找人 O(1)；
- 有序数组（按"分数降序 + 时间戳升序"排）：排名视图。更新时"移除旧条目 + 二分查找插入新位置"，O(n) 但 n = 1000；
- Top 10：直接取有序数组前 10 个；
- 同分：比较器写成 `(score, timestamp)`，同分先到排前——把业务规则变成次级排序键，是最干净的实现。

#### 核心流程

分数变化事件 → 从 Map 取出玩家（O(1)）→ 在有序数组里删掉旧条目（二分定位）→ 更新分数和时间戳 → 二分插入新位置 → 给榜单组件发一次更新信号。上下线不改榜，只改玩家的在线状态供 UI 置灰。

#### 关键边界情况

- 同分同刻：时间戳撞了 → 再加一个自增序号兜底；
- 分数会不会回退（有的游戏扣分）？——方案不变，但问清规则；
- 更新风暴：一秒几千次更新 → 合并批量处理，一个 tick 结束后统一重排一次、渲染一次；
- 玩家离线还在榜上吗？——业务规则，问清楚，通常在但置灰。

#### 复杂度

n = 玩家数。单次更新 O(n)（数组删除 + 插入的搬移），查排名 O(log n)（二分），Top K O(K)。1000 规模下 O(n) 更新每秒做几千次也没压力——**先把这句"够用"说出口，再谈优化**。

#### 数据量扩大后的问题

一百万用户时，前端维护全量有序数组不再现实（内存、每次更新 O(n)、初始加载都要命）。正确分层：排行榜下沉服务端（Redis 的有序集合就是为这个场景生的），前端只拉两个切片——Top 100 + 我自己前后各 50 名的窗口；页面用虚拟列表渲染；更新走推送 + 节流。**"前端管展示窗口、服务端管全量排序"是这类题的终极答案。**

#### 面试表达参考

> "我会把它拆成玩家和榜单两层。玩家只需要 id、分数和上次更新时间，用 Map 装，按 id 找人必须 O(1)。榜单这层的关键是搞清楚最高频操作——分数更新远多于排名查询，所以不能每次更新都全量排序。一千人的规模，我会用一个按分数排好序的数组，更新时先删旧位置再二分插入，O(n) 但 n 只有 1000，实际开销可以忽略。同分按达到时间排，比较器里带个时间戳。查 Top 10 直接取数组头部。如果扩到百万用户，前端就不该维护全量榜了——那是服务端的事，前端只拉 Top 100 和我自己附近的排名窗口两个切片，渲染用虚拟列表。"

### 例题二：在线协作白板

#### 题目

> 设计一个多人在线协作白板：用户可以创建矩形/便签元素、拖动、缩放、删除；支持撤销/重做；多人同时操作时元素状态保持一致；要考虑两个人同时拖动同一个元素怎么办；操作历史如何管理、内存如何控制？

#### 面试官考察点

- 能不能把"操作"本身当成实体来建模（命令化）；
- 撤销重做的实现方式（命令 vs 快照的取舍）；
- 并发冲突有没有分层的策略意识（先简单方案，再进阶方案）；
- 同步机制的基本形态（序号、重放）。

#### 第一反应：先拆哪些东西

实体：**元素**（id、类型、位置/尺寸、内容、版本）、**用户**、**操作**（op 类型、目标 id、参数、序号、发起人）。这道题的特点是"操作"本身成了实体——因为要同步、要撤销、要重放。操作类型：创建 / 删除 / 移动 / 缩放 / 改内容。

#### 核心数据结构

- `Map<elementId, element>`：所有渲染和修改都按 id 定位，O(1)；
- 操作历史：undo / redo 双栈，**存命令不存快照**——命令对象小、可逆（每个命令带正向 apply 和逆向 invert）；快照方案只在元素极少时才划算；
- 操作日志 `ops[]`（带递增序号）：同步与重放的依据。

#### 核心流程

本地操作 → apply 到本地 Map → 压入 undo 栈、清空 redo 栈 → 附上序号发给服务端 → 服务端广播 → 其他人按序 apply。撤销 = 弹 undo 栈顶执行 invert 并压入 redo 栈；重做反向。规则要定义："只能撤销自己的操作"是协作场景最常见的简化（要问）。

#### 关键边界情况

- 两人同时拖同一元素 → 第一层方案：**拖动加锁**（开始拖时标记 lockedBy，结束解锁），简单可靠，很多产品就是这么做的；面试官追问再谈时间戳后写覆盖、OT / CRDT（点名思路即可，别硬装精通）；
- 元素被删时别人的拖动命令到达 → apply 前查目标存在性，不存在就丢弃（幂等）；
- 撤销"创建"等于删除该元素，undo 栈里对已删除元素的历史命令要能正确失效；
- 断线重连 → 按最后序号向服务端补拉缺失 ops 再重放。

#### 复杂度

按 id 定位 O(1)；apply 一条 op O(1)；撤销 O(1)（逆命令现成）；拖动的高频路径只更新被拖元素的位置 + 重绘它自己，别全画布重算。n = 元素数 / 历史命令数，分开说。

#### 数据量扩大后的问题

元素上万 → Canvas 渲染 + 视口裁剪（DOM 上万节点必卡）；历史无限涨 → 分段快照（每 N 条命令存一次全量快照，撤销跨段时先恢复快照再重放段内命令），历史内存从 O(总命令数) 变成 O(窗口大小)；人数多 → 服务端房间广播 + 权威仲裁。

#### 面试表达参考

> "白板的核心实体是元素和操作。元素用 Map 按 id 装；操作我会做成命令对象，每条命令既会正向执行也带一个逆向方法，撤销重做就是两个栈来回倒腾。多人同步上，我的第一版方案是：本地操作立即生效、带序号发给服务端广播，其他人按序重放。两个人同时拖同一个元素这种冲突，我先用最朴素的方案——拖动时给元素加锁，拖完解锁；如果需要更细的粒度，再讨论按时间戳后写覆盖或者 OT 这类方案，但我会先说明前者大概率够用。历史内存的问题可以用分段快照控制。"

### 例题三：文件分片上传

#### 题目

> 设计一个大文件（可能几 GB）分片上传系统：文件要切成小块并行上传；单个块失败要自动重试；支持暂停和继续；页面刷新后能从已传的部分继续；全部传完后服务端合并；要有实时进度条。

#### 面试官考察点

- 任务状态机设计（分片级 + 文件级两层）；
- 并发控制：知不知道"池化调度"和"一次性全发"的区别；
- 幂等与去重（重试、重复回调）；
- 断点续传的对账思路（谁是真相）。

#### 第一反应：先拆哪些东西

实体：**文件**（hash、总分片数、状态）、**分片**（index、状态、重试次数）。操作：调度下一个要传的分片、更新某个分片状态、统计进度。先画分片状态机：`待上传 → 上传中 → 成功 / 失败（可重试→回待上传，超限→放弃）`——文件级状态由分片汇总推导。

#### 核心数据结构

- `Map<index, chunkState>`：按 index 随机查改任意分片，O(1)；
- 调度未必需要真队列：index 有序，用一个游标顺序扫、挑"待上传"的即可（主动说明这层灵活性）；
- **并发池**：固定并发数（比如 3），完成一个补一个——而不是把所有分片一次性全发出去（浏览器并发连接有限，内存也不允许所有切片同时在途）。

#### 核心流程

选文件 → 算文件 hash（放 Web Worker 里算，别卡主线程）→ 拿 hash 问服务端"传过没有、传了哪些片"（秒传和续传的依据）→ 标记已传分片 → 填满并发池 → 分片成功：更新 Map、累加进度计数器；失败：退避后重试，次数超限 → 文件标记失败 → 全部成功 → 通知服务端合并（带 hash 和分片清单，服务端再对一次账）。

#### 关键边界情况

- 同一分片的成功回调来两次（网络重放）→ 状态机单向流转天然幂等：已成功就忽略；
- 暂停：停止补池，在途请求可 abort；继续：从游标继续填池；
- 页面刷新：本地只存文件 hash，恢复时以服务端的"已传分片列表"为准对账——**服务端是真相，本地记录只是缓存**；
- 上传中文件被修改：hash / 分片校验不过 → 判定文件已变更，重新校验或提示用户；
- 弱网：并发数应该可调（大并发在弱网反而更慢）。

#### 复杂度

n = 分片数。调度摊销 O(1)；单分片状态更新 O(1)；进度 O(1)——**维护"已成功字节数"计数器，而不是每次渲染时扫描 Map 数一遍**，这个对比很能体现意识。

#### 数据量扩大后的问题

10 万分片时 Map 本身毫无压力（十万条小记录），真正的坑在别处：内存（用 `File.slice` 惰性读片，绝不一次读全文件）、hash 计算（Worker + 增量/抽样 hash）、并发调优。**结论要会说：数据结构不是瓶颈，I/O 和主线程才是。**

#### 面试表达参考

> "我会把它建模成两层状态机：文件一层、分片一层。分片状态用 Map 按 index 装，因为要随时查任意一片的状态。调度上我不用真队列，用一个游标按 index 顺序取片，配一个固定大小的并发池——同时最多 3 个在传，完成一个补一个。重试带退避、次数封顶；同一片的成功回调可能来两次，所以状态机要幂等：只有待传→上传中→成功这条单向路。进度不每次扫描统计，维护一个已成功字节数的计数器。刷新后续传靠文件 hash 先问服务端要已传分片列表，本地记录只当缓存。"

### 例题四：聊天消息系统

#### 题目

> 设计一个即时通讯的前端：单聊和群聊；消息严格按顺序展示；发送失败可以重试；有已读/未读；支持撤回（两分钟内）；高频收发时页面不能卡。

#### 面试官考察点

- 有序性怎么保证（本地序 vs 服务端序）；
- 消息状态机（发送中/失败/已送达/已撤回）；
- 客户端 ID 与幂等去重；
- 能不能看出"按序"和"按 id"是两种相反的查找，从而设计双索引；
- 渲染性能意识。

#### 第一反应：先拆哪些东西

实体：**消息**（clientMsgId、serverSeq、内容、状态：发送中/已发送/失败/已撤回）、**会话**（消息列表、已读位点）。操作：尾部追加（高频）、按 id 改状态（回执/撤回）、按序渲染（高频）。**"按序"和"按 id"是两种相反的查找，这是选结构的线索。**

#### 核心数据结构

- 有序数组（按 seq 排）：管展示顺序；
- `Map<clientMsgId, message>`：管状态回执——重试、撤回、已读都是拿着 clientMsgId 来找消息的，O(1) 定位；
- **双索引是本题的核心结构设计：一个数组满足不了两种相反的操作**；
- 发送中的消息带本地生成的 clientMsgId，重试复用同一个 id（幂等：服务端据此去重，避免重试造成重复消息）。

#### 核心流程

发送：本地先上屏（乐观更新，标"发送中"）→ 发给服务端 → 成功回执带 serverSeq 回来 → 按 id 找到消息，更新状态和 seq；失败 → 标记失败 + 重试（复用同一 clientMsgId）。接收：消息按 seq 到达 → 追加到数组尾部；乱序到达（seq 跳跃）→ 二分插入正确位置，缺口触发"补拉"。

已读未读：**不给每条消息存布尔**，会话级维护"对方已读位点 lastReadSeq"，位点之后的全算未读——O(1) 更新，渲染时按位点画分界线。撤回：时间窗内发撤回请求 → 服务端改状态广播 → 客户端按 id 找到消息替换成"已撤回"占位（不删，保序号连续）。

#### 关键边界情况

- 收到重复 seq 的消息（推送和拉取撞车）→ 按 seq 去重；
- 乐观插入的位置后来发现不对（服务端序 ≠ 本地序）→ seq 回来后校准位置；
- 撤回的消息被回复/引用 → 引用内容保留快照；
- 断线重连 → 带最后 seq 补拉，回来和本地合并去重。

#### 复杂度

n = 当前会话已加载的消息数。尾部追加摊销 O(1)；回执定位 O(1)；乱序插入最坏 O(n) 但极少发生（聊天几乎总在尾部追加）——记得说明"最坏情况"和"实际分布"是两层意思。

#### 数据量扩大后的问题

历史几十万条 → 分页拉取 + 虚拟列表（只渲染视口内的消息）；本地 IndexedDB 按 seq 建索引；未读数用计数器，别遍历消息算。**渲染层永远只看见"视口里的几十条"。**

#### 面试表达参考

> "消息列表有两种相反的操作：按顺序渲染、按 id 改状态。一个数组只能优化其中一个，所以我会用双索引：有序数组管展示，Map 按 clientMsgId 管回执——失败重试、撤回这些操作都是拿 clientMsgId 定位的。发送走乐观更新：先上屏标'发送中'，服务端确认后校准。已读未读我不给每条消息存布尔，用会话级的'已读位点'，位点之后的都算未读，更新就是一个数字。顺序以服务端 seq 为准，乱序到达就二分插入并触发补拉。高频渲染靠虚拟列表兜底。"

### 例题五：前端实时监控大屏

#### 题目

> 设计一个前端实时监控大屏：100 台设备，每台每秒上报几十条指标数据；大屏要实时更新每台设备的折线图和当前值；数据频率很高，页面必须流畅；运维可能同时开好几个标签页看同一块大屏。

#### 面试官考察点

- 能不能先算一笔数据量账，抓住"数据频率 >> 渲染价值频率"这个核心矛盾；
- 生产者-消费者模型、缓冲与批量消费；
- 渲染节流与 rAF 的关系；
- 多标签页的连接共享（SharedWorker）。

#### 第一反应：先拆哪些东西

先算账：100 设备 × 每秒几十条 = 每秒几千条消息。核心矛盾一句话：**数据到达频率（千/秒）远高于人眼能感知的更新频率（每秒一两次）。** 所以整个设计就是一句话：高频流入 → 缓冲 → 批量消化 → 低频渲染。实体：设备（环形缓冲、最新值）、消息队列、图表层——生产者和消费者中间必须有个"蓄水池"。

#### 核心数据结构

- 每设备一个**定长环形缓冲**（如最近 300 个点）：新点写入、最旧点被覆盖，写入 O(1)、内存封顶——对比"数组无限 push"（内存涨）或"push + shift"（shift 是 O(n)）；
- 一个待处理消息队列：消息到达只做入队这一件轻事；
- `Map<deviceId, 最新值>`：瞬时数值面板用；
- 多标签：**SharedWorker** 持有唯一一条 WebSocket，解析、聚合后广播给各标签页（BroadcastChannel 是无 Worker 时的备选）——避免每个标签一条连接、一份解析。

#### 核心流程

消息到达 → 入队（轻）→ rAF 每帧：把本帧积压的消息**一次性**消化——写入各设备环形缓冲、聚合成图表需要的粒度（比如按秒取均值降采样）→ 触发一次图表更新 → 无变化的设备不重绘。切后台时 rAF 停了，缓冲靠定长自动丢最旧，切回来自然追上。

#### 关键边界情况

- 设备断流：折线要按时间戳留出空隙，不能把断流两侧的点连起来（所以每个点要带时间戳，不能只存"第 N 个点"）；
- 迟到 / 乱序数据：按时间戳插入，太旧的直接丢弃；
- 数据突发回灌（设备恢复后补发）→ 丢弃或降采样，别冲击渲染；
- 标签页不可见：暂停渲染，保留缓冲。

#### 复杂度

入队 O(1)；每帧消费 O(本帧消息数)；渲染 O(视口内点数)。n 各是谁说清楚——**每帧成本和"每秒总消息量"解耦了，这就是缓冲的意义**。

#### 数据量扩大后的问题

设备到 1 万 → 分组分页签，只订阅当前可视组的实时流，其他组降频拉聚合值；单帧消息量太大 → Worker 里先聚合，主线程只收结果。原则：**越靠近用户眼睛的地方，数据密度越要低。**

#### 面试表达参考

> "这道题的核心矛盾是数据频率远高于渲染的价值频率——一秒几千条数据，折线图每秒动 60 次也没有意义。所以我会做生产者-消费者：消息进来只做最轻的入队和写入环形缓冲——每台设备一个定长环形缓冲，存最近 N 个点，新点覆盖旧点，O(1) 且内存封顶。消费侧挂在 rAF 上，每帧把积压的消息一次性消化、聚合成图表需要的数据，只触发一次更新。多个标签页用 SharedWorker 建一条连接，聚合完广播给所有页面。还要处理设备断流——折线要按时间戳留空隙，不能把断流前后的点连起来。"

### 例题六：拖拽流程图编辑器

#### 题目

> 设计一个前端流程图编辑器：节点可以创建、删除、拖动；节点之间连有向边表示依赖；删除节点要连带删除相关边；加边时禁止形成循环依赖；支持撤销重做；选中一个节点要高亮它影响的所有下游节点；节点多了以后要保证流畅。

#### 面试官考察点

- 能不能识别出这是**有向图**问题并用邻接表建模；
- 环检测（BFS / DFS）放哪一步做；
- 级联删除怎么实现（为什么要反向邻接表）；
- 撤销重做的命令设计（复合命令的逆操作）。

#### 第一反应：先拆哪些东西

实体：**节点**（id、位置、数据）、**边**（from、to）。操作：按 id 找节点（最高频）、查某节点的出边/入边、加边前判环、删节点级联删边。一听到"依赖""不能成环"，就该意识到这是图的问题，第一反应应该是邻接表。

#### 核心数据结构

- `Map<nodeId, node>`；
- **两份邻接表**：出边 `Map<nodeId, Set<nodeId>>` + 入边 `Map<nodeId, Set<nodeId>>`——判环和高亮下游用出边 BFS；删节点级联、高亮上游要反查入边；用 Set 顺带去重（防重复连同一条边）；
- 为什么不用邻接矩阵：节点上千时矩阵是 O(V²) 空间，而图的边稀疏，邻接表按"实际有几条边"付钱。

#### 核心流程

加边 A→B：先判环——从 B 沿出边 BFS / DFS，能走到 A 就拒绝（前端拦一道，服务端再校验一道，双保险）；通过 → 两份邻接表各登记一条。删节点：删 Map 记录 + 从两份邻接表清除它的所有出边入边（入边表保证能找到"谁连着我"）。拖动：只更新该节点坐标 + 重画相连的线（局部渲染）。

撤销重做：命令模式双栈。删节点是**复合命令**——逆操作 = 恢复节点 + 恢复它当时带的所有边（所以命令对象里要存下这些信息）。

#### 关键边界情况

- 自环 A→A：直接拒绝；
- 重复加边：Set 已去重；
- 正在连线时源/目标节点被删：连线操作作废；
- 高亮"下游"和判环是同一个 BFS——复用同一个遍历，方向相反就是上游。

#### 复杂度

找节点 O(1)；判环 / 高亮 O(V+E)（V = 节点数，E = 边数）；删节点 O(该节点的边数)；拖动渲染 O(相连边数)。

#### 数据量扩大后的问题

几千节点后**逻辑不慌**（都是 O(1) 定位），瓶颈在渲染：Canvas + 视口裁剪 + 分层（边一层、节点一层）；判环每次 O(V+E) 开始有感 → 对"可达性"做缓存（增量维护，或合并短时间内的连续操作批量判一次）；自动布局离线跑，别在拖动的帧里算。

#### 面试表达参考

> "流程图本质是图。节点用 Map 装，边用邻接表——而且我会建两份：出边表和入边表，因为删节点要级联删边、高亮上游都要反查。加边之前必须查环：从目标节点沿出边 BFS，看能不能回到源节点，能回到就拒绝这条边，前端和服务端各校验一道。撤销重做用命令模式，每条命令带逆向操作；删节点是个复合命令，逆操作要把节点和相关边一起恢复。规模大了以后逻辑层其实不慌——都是按 id 的 O(1) 操作——瓶颈在渲染，用 Canvas 加视口裁剪。"

## 十四、万能答题套路与高频追问

### 14.1 答题九步（面试前扫一遍的检查单）

```text
1. 先确认规则       —— 复述题意；没说清的主动问 2~3 个
2. 找核心实体       —— 圈名词，留下需要维护状态的
3. 找每个实体的状态  —— 存什么字段？谁是真相，谁是推导值？
4. 根据操作选结构   —— 每个实体：最高频操作是什么 → 结构自然出来
5. 设计核心状态流转  —— 什么事件 → 改什么状态 → 通知谁
6. 处理边界情况     —— 同时发生/重复/空/非法/冲突/极端量/网络/高频
7. 分析复杂度       —— 每个O(n)说清 n 是谁、贵在哪、能否优化
8. 思考规模扩大     —— 10→100→10000，哪里先倒、换什么结构
9. 最后才谈性能优化  —— 批量/增量/降频/缓存/Worker/下沉服务端
```

时间分配参考：前四步用一半时间（打地基），五、六步用三成，七、八、九步用两成。**宁可主干快一点，也要把第六步边界留出来**——那是大多数候选人不去的地方。

### 14.2 高频追问与应对角度

追问本身是好消息——说明面试官对你的答案有兴趣，在往深处探。常见追问和应对角度：

**"为什么用数组，不用链表？"**
不要答"数组简单"。从操作模式答：这份数据的高频操作是什么，两种结构在这个操作上各自的成本是多少；再补一层现实（JS 里数组内存连续、缓存友好，链表每个节点一个对象，还有 GC 压力）；最后留口子："如果操作模式变成 X，我会换成链表。"——展示的是决策过程，不是站队。

**"为什么不用 Set？"**
看需不需要归属信息。Set 回答"有没有"，Map 回答"是谁的"。贪吃蛇就是标准例子：只用 Set 就分不出撞自己还是撞对方。

**"复杂度是多少？"**
说清三件事：n 是谁、开销产生在哪一步、最坏情况什么样。能主动补一句"规模到多少它会成为问题"更好。

**"数据量扩大十倍怎么办？"**
先找瓶颈（哪个 O(n) 变贵了），再给对应手段：遍历贵 → 索引；两两比贵 → 空间划分 / 分桶；渲染贵 → 虚拟列表 / 裁剪 / Canvas；算不动 → Worker / 下沉服务端。按"哪一级数量级触发哪个手段"来答。

**"如果两个事件同时发生怎么办？"**
先问自己：结果是否依赖处理顺序？依赖 → 计算与结算分离（贪吃蛇双死）、或定出排序规则（时间戳 / 序号）、或加锁串行化（白板拖拽）。

**"如果一个状态更新失败怎么办？"**
状态机里补 failed 态；可重试的带退避重试 + 次数上限；重试要幂等（同一 ID 去重）；不可恢复就明确终态并通知用户。千万不要"失败就假装没发生"。

**"如果数据特别多怎么办？"**
按层答：网络层分页；存储层只留窗口（环形缓冲）/ IndexedDB；渲染层虚拟列表 / Canvas；计算层 Worker / 增量。

**"如果更新频率特别高怎么办？"**
缓冲队列 + 批量消费 + 节流降频，渲染与逻辑解耦。核心句："数据的频率不应该决定渲染的频率，中间要有缓冲层。"

**"如果需要支持撤销怎么办？"**
操作做成命令（带正向 apply 和逆向 invert），undo / redo 双栈；数据量小可以直接存快照——说清取舍（命令省内存但要写逆操作；快照简单但贵）。

**"如果以后从单机变成多人协作怎么办？"**
逻辑下沉服务端（服务端权威），客户端只发意图、收状态；本地乐观更新 + 服务端确认校准；操作带序号和幂等 ID；冲突提前定规则（加锁 / 时间戳 / OT / CRDT 点名即可）。

### 14.3 收束

回到全文开头那条链，也是你在面试现场脑子里要过的全部东西：

> **看到一个复杂场景 → 拆实体 → 找状态 → 看操作 → 选数据结构 → 设计状态流转 → 处理边界 → 分析复杂度 → 考虑规模化。**

复习方法建议：上面六道例题，每道先遮住分析、口头讲 10 分钟，再对照参考找漏项；每天一道，一周覆盖全部方向。练到第七八道时，你会发现自己在读题的瞬间就开始自动圈实体、列操作——那这份文档的目的就达到了。
