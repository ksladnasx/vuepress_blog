# uniapp知识点

基于微信小程序面试真题梳理，覆盖**基础认知、生命周期、登录/支付/路由/发布流程、实现原理、性能优化**八大核心模块

## 一、微信小程序基础认知
### 1. 定义
2017年微信推出，是**无需下载安装即可使用的轻量应用**，实现“触手可及、用完即走”，用户通过扫码/搜索打开，无需安装卸载；除微信外，百度、支付宝、抖音也有各自的平台化小程序，均为平台自研的针对性应用程序。

### 2. 开发背景
微信原有JS-SDK无法满足开发者的体验需求，因此设计小程序体系，核心解决**快速加载、原生体验、强大能力、安全的微信数据开放、简单高效开发**五大问题。

### 3. 与H5的核心区别
| **维度** | **微信小程序** | **H5** |
| :--- | :--- | :--- |
| 运行环境 | 浏览器内核重构的内置解析器 | 手机浏览器 |
| 系统权限 | 可获取网络状态、数据缓存等更多权限 | 权限受浏览器限制 |
| 渲染机制 | 逻辑层与渲染层分离 | 渲染和脚本运行在同一线程 |
| 开发语法 | WXML+WXSS+JS | HTML+CSS+JavaScript |


### 4. 优缺点
#### 优点
+ 轻量便捷：随搜随用、用完即走，可替代轻量APP或作为APP功能补充；
+ 流量优势：依托平台生态，易获取自然流量；
+ 开发友好：开发门槛低、兼容性限制少；
+ 安全性高：受平台管控，数据和功能更规范。

#### 缺点
+ 留存率低：平均次日留存13%，双周留存仅1%；
+ 体积限制：微信小程序仅支持2M大小，无法开发大型应用；
+ 平台管控：功能、接口、内容均受微信限制，自由度低于原生APP。

## 二、微信小程序生命周期
小程序生命周期分为**应用、页面、组件**三类，是开发中页面渲染、数据请求、任务管理的核心依据，需掌握各阶段触发时机、作用及执行顺序。

### 1. 应用生命周期（app.js中通过App(Object)定义）
全局唯一，控制小程序整体的启动、显示、隐藏、错误处理，核心函数及说明：

| **生命周期** | **核心说明** |
| :--- | :--- |
| onLaunch | 小程序初始化完成，全局仅触发1次 |
| onShow | 小程序启动/从后台切前台，多次触发 |
| onHide | 小程序从前台切后台 |
| onError | 脚本错误/API调用报错时触发 |
| onPageNotFound | 打开不存在的页面时触发 |
| onUnhandledRejection | 有未处理的Promise拒绝时触发 |
| onThemeChange | 系统切换主题时触发 |


### 2. 页面生命周期（页面js中定义）
控制单个页面的加载、显示、渲染、隐藏、卸载，核心函数及**作用+触发时机**：

| **生命周期** | **说明** | **核心作用** |
| :--- | :--- | :--- |
| onLoad | 监听页面加载 | 发送请求获取初始化数据（仅触发1次） |
| onShow | 监听页面显示 | 重新请求数据（页面每次显示都触发） |
| onReady | 监听页面初次渲染完成 | 获取页面DOM元素（仅触发1次，少用） |
| onHide | 监听页面隐藏 | 终止定时器、暂停音乐等临时任务 |
| onUnload | 监听页面卸载 | 终止所有任务，释放资源 |


### 3. 组件生命周期（组件js中通过Component(Object)定义）
控制自定义组件的创建、挂载、渲染、移动、卸载，核心函数及注意事项：

| **生命周期** | **说明** | **关键注意事项** |
| :--- | :--- | :--- |
| created | 组件实例创建完成 | 可访问this.data，但**不能调用setData** |
| attached | 组件挂载到页面节点树 | 绝大多数初始化工作在此执行（核心） |
| ready | 组件初次渲染完成 | 可操作组件渲染后的节点 |
| moved | 组件在节点树中被移动 | 极少使用 |
| detached | 组件从节点树中卸载 | 清理组件资源，如定时器、事件监听 |
| error | 组件方法抛出错误时执行 | 捕获组件内部错误 |


#### 组件特殊生命周期：pageLifetimes
组件感知所在页面的显示/隐藏，需在Component中单独定义，核心函数：

```plain
Component({
  pageLifetimes: {
    show() { // 组件所在页面显示时执行 },
    hide() { // 组件所在页面隐藏时执行 }
  }
})
```

### 4. 生命周期执行顺序（核心面试点）
#### （1）应用+页面联合执行
+ 首次打开小程序：`App.onLaunch` → `App.onShow` → `Page.onLoad` → `Page.onShow` → `Page.onReady`
+ 进入下一个页面：`当前Page.onHide` → `新Page.onLoad` → `新Page.onShow` → `新Page.onReady`
+ 返回上一个页面：`当前Page.onUnload` → `上一个Page.onShow`
+ 离开小程序（切后台）：`App.onHide`
+ 再次进入（未销毁）：`App.onShow` → 后续按页面流程执行；若已销毁，重新执行`App.onLaunch`

#### （2）组件与页面联动
组件`attached`在页面`onReady`之后触发，`detached`在页面`onUnload`时触发（若组件未提前卸载）。

## 三、微信小程序登录流程
核心是通过微信官方能力获取**用户唯一标识openid**，并建立**自定义登录态**，实现小程序内的用户体系，全程保证`session_key`（微信会话密钥）的安全，避免前端传输。

### 1. 核心概念
+ `code`：小程序通过`wx.login()`获取的临时登录凭证，有效期短；
+ `openid`：用户在当前小程序的唯一标识，由微信服务器生成；
+ `session_key`：微信服务器生成的会话密钥，用于加密/解密用户数据，**禁止在网络传输**；
+ 自定义登录态（如3rd_session/token）：开发者服务器生成，关联`openid`和`session_key`，用于前端和服务端的登录校验。

### 2. 核心执行流程
#### 基础流程（小程序→开发者服务器→微信服务器）
1. 小程序调用`wx.login()`获取**临时code**；
2. 小程序通过`wx.request()`将`code`发送到**开发者服务器**；
3. 开发者服务器携带`code+appid+appsecret`（微信后台获取），调用微信**登录凭证校验接口**，换取`openid+session_key`；
4. 开发者服务器生成**自定义登录态**（如3rd_session），将`自定义登录态: {openid, session_key}`存入Redis/Memcached；
5. 开发者服务器将**自定义登录态**返回给小程序，小程序通过`wx.setStorageSync()`存入本地；
6. 后续小程序发起业务请求时，携带本地的**自定义登录态**，开发者服务器通过该标识查询`openid+session_key`，完成身份校验。

### 3. 登录态校验优化
为避免自定义登录态过期，结合微信原生API做双重校验，流程：

1. 小程序调用`wx.checkSession()`，校验微信原生`session_key`是否过期；
    1. 未过期：直接使用本地自定义登录态发起请求；
    2. 已过期：重新执行`wx.login()`获取code，走完整登录流程；
2. 若微信登录态有效，开发者服务器再校验**自定义登录态**的有效期，过期则重新生成。

### 4. 用户信息获取
由于小程序无法直接授权微信域名，需通过**开发者服务器中转**：

1. 小程序调用`wx.getSettings()`判断用户是否授权个人信息；
2. 授权后调用`wx.getUserInfo()`获取用户加密数据，发送到开发者服务器；
3. 开发者服务器通过`session_key`解密数据，获取用户昵称、头像等信息。

## 四、微信小程序路由跳转
小程序通过5种原生API实现页面跳转，核心区别在于**页面栈的操作**（入栈/出栈/清空）和**适用场景**，页面栈最大限制为10层，需根据业务选择合适的跳转方式。

### 1. 5种跳转方式核心对比
| **跳转API** | **页面栈操作** | **核心特点** | **适用场景** |
| :--- | :--- | :--- | :--- |
| wx.navigateTo | 新页面**入栈**，保留当前页 | 可通过wx.navigateBack返回 | 普通页面跳转（如列表→详情） |
| wx.redirectTo | 当前页**出栈**，新页面入栈 | 无法返回上一页，释放内存 | 无需返回的页面（如登录→首页） |
| wx.switchTab | 清空所有页面，新Tab页入栈 | 仅跳转到app.json中配置的tabBar页面，**路径不能带参数** | TabBar页面切换（如首页/我的/分类） |
| wx.navigateBack | 页面**出栈**（delta指定层数） | 返回上n页，delta默认1，超出则返首页 | 从详情页返回列表页等场景 |
| wx.reLaunch | 清空所有页面，新页面入栈 | 可跳转到任意页面，路径可带参数 | 重启小程序/从非Tab页跳转到Tab页 |


### 2. 关键注意事项
+ `wx.navigateTo`/`wx.redirectTo`**不能跳转到tabBar页面**，仅`wx.switchTab`/`wx.reLaunch`可实现；
+ 页面栈可通过`getCurrentPages()`获取，用于`wx.navigateBack`的delta计算，**禁止手动修改页面栈**；
+ `wx.navigateTo`支持**页面间通信**（events参数），基础库2.7.3及以上支持。

### 3. 页面栈核心规则
+ 入栈：新页面添加到页面栈顶部，栈长度+1；
+ 出栈：页面从栈顶部移除，栈长度-1；
+ 清空：所有页面从栈中移除，栈长度置0后添加新页面。

## 五、微信小程序发布流程
小程序开发完成后需通过**微信开发者工具+微信公众平台**完成发布，企业开发中会结合**代码管理+自动化构建**优化流程，核心分为**上传代码、提交审核、发布版本**三步。

### 1. 基础发布流程（个人/小团队）
#### 步骤1：上传代码
在微信开发者工具中，点击「上传」，填写**版本号**（如1.0.0）和**项目备注**，确认后完成代码包上传，上传的是编译/压缩后的代码包，非源代码。

#### 步骤2：提交审核
1. 登录**微信公众平台**→进入小程序后台→「开发管理」→「开发版本」；
2. 选择已上传的版本，点击「提交审核」，填写**审核信息**（功能页面、服务类目、标签），标签需与业务相关，提升搜索曝光；
3. 提交后等待微信官方审核，审核时间一般1-3个工作日，审核不通过会提示原因，修改后重新提交。

#### 步骤3：发布版本
审核通过后，在「审核版本」中选择对应版本，点击「发布」，发布后小程序正式上线，用户可搜索/扫码访问。

### 2. 企业级发布流程（中大型团队）
结合Git代码管理和自动化构建，流程更规范：

1. Git服务器新建开发分支，开发人员在分支上开发新需求；
2. 开发完成后测试，测试通过将分支**合并到master主分支**；
3. 拉取master最新代码，执行`build`命令生成可执行代码包；
4. 开发者工具上传代码→提交审核→发布；
5. 可选：通过Jenkins实现**自动化构建部署**，构建失败提醒开发者，成功后通知测试/运维。

## 六、微信小程序支付流程
微信小程序为电商类业务提供原生支付能力，核心基于`wx.requestPayment()`API，流程涉及**小程序、商户系统、微信支付后台**三方交互，无需配置支付目录/域名授权，比H5支付更简洁。

### 1. 核心适用场景
电商小程序的商品购买、充值、缴费等，用户通过**扫码/分享/搜索**进入小程序，完成选购后发起支付。

### 2. 完整执行流程
#### （1）前置条件
商户已完成微信支付商户号开通，小程序与商户号绑定，获取支付相关的`appid+商户号+API密钥`。

#### （2）具体步骤
1. 用户在小程序中选择商品，点击「下单支付」，小程序将**商品ID、数量、用户openid**发送到**商户系统**；
2. 商户系统生成**商户订单**，通过**微信支付统一下单API**（携带订单信息、商户信息、签名）向微信支付后台发起请求，换取**预付单ID（prepay_id）**；
3. 商户系统将`prepay_id`按微信规则**再次签名**，生成支付参数（timeStamp、nonceStr、package、signType、paySign），返回给小程序；
4. 小程序调用`wx.requestPayment()`，传入支付参数，**调起微信支付控件**，用户输入支付密码/指纹完成支付；
5. 微信支付后台完成鉴权，**同步返回支付结果给小程序**（前端展示支付成功/失败），**异步推送支付结果给商户系统**；
6. 商户系统根据微信推送的结果，**更新订单状态**（已支付/未支付），并处理后续发货/核销逻辑。

### 3. 核心API：wx.requestPayment()
参数为必传/可选结合，签名必须与商户后台一致，核心参数：

| **参数名** | **类型** | **必填** | **说明** |
| :--- | :--- | :--- | :--- |
| timeStamp | string | 是 | 时间戳，从1970-01-01 00:00:00至今的秒数 |
| nonceStr | string | 是 | 随机字符串，长度≤32位 |
| package | string | 是 | 统一下单返回的prepay_id，格式：`prepay_id=***` |
| signType | string | 否 | 签名算法，默认MD5，需与商户后台一致 |
| paySign | string | 是 | 支付签名，按微信支付文档规则生成 |
| success | function | 否 | 支付成功的回调函数 |
| fail | function | 否 | 支付失败/取消的回调函数 |


## 七、微信小程序实现原理
小程序的核心设计是**双线程架构**，将**逻辑层**和**渲染层**分离，解决了传统H5渲染和脚本互斥导致的页面卡顿问题，是理解小程序性能特性的核心。

### 1. 双线程架构核心组成
#### （1）渲染层（视图层）
+ 基于**WebView线程**实现，一个小程序有多个页面则对应多个WebView线程；
+ 负责页面渲染，执行WXML/WXSS相关逻辑，处理界面交互（如点击、滑动）；
+ 无DOM操作能力，无法直接修改页面数据，需通过逻辑层传参。

#### （2）逻辑层
+ 基于**JsCore线程**实现，整个小程序只有一个JsCore线程；
+ 负责执行业务逻辑（如数据请求、数据处理、事件回调），管理小程序生命周期；
+ 无法直接操作DOM，通过`setData`将数据传递给渲染层。

#### （3）通信桥梁
逻辑层和渲染层之间通过**微信客户端（Native）** 做通信中转，所有数据传递、事件分发都需经过Native，因此**数据通信是异步的**，存在一定延时。

### 2. 核心通信流程
#### （1）数据从逻辑层到渲染层（setData）
1. 逻辑层调用`this.setData({key: value})`，将数据传递给微信Native；
2. Native将新数据与渲染层原有数据对比，生成**新节点树**；
3. Native将新节点树传递给渲染层，渲染层替换原有节点树，完成页面更新。

#### （2）事件从渲染层到逻辑层（如按钮点击）
1. 渲染层捕获用户交互事件（如点击），将事件信息传递给微信Native；
2. Native将事件分发到逻辑层，触发对应的事件回调函数；
3. 逻辑层处理事件（如修改数据），再通过`setData`将新数据传回渲染层，完成页面响应。

### 3. 小程序运行机制
小程序启动分为**冷启动**和**热启动**，无“重启”概念，由微信客户端管控生命周期：

#### （1）冷启动
+ 触发场景：用户**首次打开**小程序，或小程序被微信**主动销毁**后再次打开；
+ 流程：微信下载小程序代码包→加载代码包→初始化逻辑层/渲染层→启动小程序；
+ 版本更新：冷启动时会检查小程序新版本，**异步下载新版本**，当前仍用本地旧版本启动，新版本需**下一次冷启动**生效，发布后24小时内会推送给所有用户。

#### （2）热启动
+ 触发场景：用户已打开过小程序，**短时间内再次打开**（微信后台未销毁）；
+ 流程：直接将小程序从微信后台切换到前台，无需重新加载代码包，启动速度极快。

#### （3）小程序销毁规则
1. 小程序进入后台后，微信客户端维持一段时间运行状态，超时后自动销毁；
2. 短时间内收到**系统两次以上内存警告**，微信会直接销毁小程序，导致页面奔溃；
3. 页面栈达到10层，未及时释放，也会触发内存溢出，导致小程序异常。

## 八、微信小程序性能优化（提高应用速度）
小程序性能优化核心围绕**启动加载**和**页面渲染**两大维度，目标是减少启动时间、提升首屏渲染速度、避免页面卡顿，是面试高频考点，也是实际开发的重点。

### 1. 启动加载优化：控制代码包大小，提升加载速度
小程序启动的核心耗时在**代码包下载/加载**，因此优化的关键是**减小代码包体积**，核心手段：

#### （1）基础体积压缩
+ 开发者工具勾选「上传代码时压缩代码」，自动压缩JS/CSS/WXML代码；
+ 及时清理**无用代码、无用图片/资源**，删除未使用的页面/组件；
+ 图片资源优化：除小icon外，所有图片放在**CDN**，不从代码包加载；对图片进行压缩（如WebP格式），减小文件大小。

#### （2）分包加载（核心手段）
将小程序代码包拆分为**主包+多个子包**，主包包含首页、tabBar页面等高频访问页面，子包包含低频访问页面（如个人中心详情、活动页），**按需加载**子包，减小首次下载的主包体积。

+ 分包预加载：开发者配置页面跳转的预加载规则，框架在进入某个页面后，**提前下载可能跳转的子包**，避免用户点击时的卡顿；
+ 注意：子包体积不宜过大，否则预加载会占用额外资源。

### 2. 页面渲染优化：减少卡顿，提升首屏体验
渲染优化的核心是**减少数据通信耗时、避免不必要的渲染、提升数据请求效率**，核心手段：

#### （1）提前请求数据，利用本地缓存
+ 数据请求在`onLoad`中执行，**无需等待onReady**，提前获取初始化数据；
+ 减少不必要的HTTPS请求：将高频使用的静态数据（如城市列表、商品分类）通过`wx.setStorageSync()`存入本地，下次使用通过`wx.getStorageSync()`读取，无需重复请求。

#### （2）首屏渲染优化
+ 前置页面传参：列表页跳转到详情页时，将列表中已有的数据（如商品名称、价格）通过路由传参带到详情页，完成**首屏快速渲染**，详情数据再异步请求；
+ 骨架屏占位：首屏数据未加载完成时，用**骨架屏**替代空白页面，提升用户体验，避免感知到的卡顿。

#### （3）优化setData（核心重点）
`setData`是逻辑层到渲染层的核心通信方式，**频繁调用/传递大量数据**会导致通信延时、页面卡顿，优化规则：

1. 合并多次setData：将多个独立的setData调用合并为一次，减少通信次数；
2. ✅ 推荐：`this.setData({a:1, b:2, c:3})`
3. ❌ 不推荐：`this.setData({a:1}); this.setData({b:2}); this.setData({c:3})`
4. 减少setData数据量：仅将**需要在页面渲染的数**据放入`data`，非渲染数据（如业务逻辑参数、临时变量）直接挂载到page对象上（如`this.info = {xxx}`），不放入`data`；
5. 避免在循环中调用setData：循环中调用会导致频繁通信，建议先将数据处理完成，再一次性setData。

#### （4）使用自定义组件
自定义组件有**独立的逻辑层和渲染层**，组件的`setData`仅更新自身节点，**不会影响页面上的其他元素**，因此将页面中的独立模块（如商品卡片、评论项）抽离为自定义组件，可减少页面整体的渲染开销。

### 3. 性能优化总结
| **优化维度** | **核心手段** |
| :--- | :--- |
| 启动加载 | 压缩代码包、清理无用资源、分包加载+预加载、图片放CDN |
| 首屏体验 | onLoad提前请求、本地缓存、前置传参、骨架屏占位 |
| 页面渲染 | 合并setData、减少setData数据量、自定义组件抽离 |

## 第一章：Node.js 基础与概念
### 1.1 Node.js 是什么？有什么特点？
**面试回答（直接背）：**

Node.js 是一个基于 **Chrome V8 引擎**的 **JavaScript 运行时环境**，让 JavaScript 可以在服务端运行。

Node.js 的核心特点有三个：

**第一，非阻塞 I/O**。Node.js 所有 I/O 操作（文件读写、网络请求、数据库查询）都是异步非阻塞的，不会等待 I/O 完成再执行后续代码，而是通过回调函数在完成后通知。这使 Node.js 能高效处理大量并发请求。

**第二，事件驱动**。Node.js 基于事件循环（Event Loop）处理异步操作。当异步操作完成时，触发对应的事件，执行回调。所有 I/O 操作都通过事件机制调度。

**第三，单线程**。Node.js 主线程是单线程的，但底层 I/O 操作由 libuv 线程池处理。单线程避免了多线程编程的复杂性和资源竞争，但 CPU 密集型任务会阻塞主线程。

Node.js 适合 **I/O 密集型** 应用（API 服务、实时通信），不适合 **CPU 密集型** 应用（图像处理、大量计算）。

**核心要点（快速回忆）：**

+ **本质**：V8 引擎的 JavaScript 运行时
+ **特点**：非阻塞 I/O + 事件驱动 + 单线程
+ **适用**：I/O 密集型（API、实时通信）
+ **不适用**：CPU 密集型（计算、图像处理）



### 1.2 Node.js 的事件循环和浏览器有什么区别？
**面试回答（直接背）：**

Node.js 和浏览器的事件循环有相同点也有不同点：

**相同点**：都是基于事件循环的异步模型，都有宏任务和微任务的概念。

**不同点**：

**阶段划分不同**。浏览器的事件循环相对简单（宏任务 → 微任务 → 渲染）。Node.js 的事件循环分为 **6 个阶段**：timers（定时器）→ pending callbacks（系统回调）→ idle/prepare（内部）→ poll（I/O 轮询）→ check（setImmediate）→ close（关闭回调）。

**微任务执行时机不同**。浏览器在每个宏任务执行完后清空所有微任务。Node.js 在**每个阶段切换时**清空微任务队列，且在微任务队列中 `process.nextTick` 优先于 `Promise.then`。

**宏任务队列不同**。浏览器宏任务主要是 `setTimeout`/`setInterval`。Node.js 有多个宏任务队列，对应不同阶段。

**核心要点（快速回忆）：**

|  | 浏览器 | Node.js |
| --- | --- | --- |
| 事件循环 | 宏任务→微任务→渲染 | 6个阶段循环 |
| 微任务执行 | 每个宏任务后 | 每个阶段切换时 |
| 特殊微任务 | - | `process.nextTick` 优先 |
| 宏任务队列 | 单一 | 多阶段多队列 |


**代码示例：**

```javascript
// Node.js 事件循环示例
console.log('1: 同步')

setTimeout(() => {
  console.log('2: setTimeout 宏任务（timers阶段）')
}, 0)

setImmediate(() => {
  console.log('3: setImmediate 宏任务（check阶段）')
})

Promise.resolve().then(() => {
  console.log('4: Promise.then 微任务')
})

process.nextTick(() => {
  console.log('5: process.nextTick 微任务（优先级最高）')
})

// 输出顺序：1 → 5 → 4 → 2/3（timers和check顺序不固定）
// 原因：nextTick 是最高优先级微任务

// 事件循环阶段顺序验证
const fs = require('fs')

fs.readFile(__filename, () => {
  console.log('6: I/O callback（poll阶段）')
  setTimeout(() => console.log('7: setTimeout（timers阶段）'), 0)
  setImmediate(() => console.log('8: setImmediate（check阶段）'))
})
// 在 poll 阶段中，先执行 check（setImmediate），再执行 timers（setTimeout）
```



### 1.3 `process.nextTick` 和 `setImmediate` 的区别是什么？
**面试回答（直接背）：**

两者都是 Node.js 的异步 API，但执行时机和优先级不同：

`process.nextTick`：在当前事件循环的**微任务队列中优先级最高**，在当前阶段结束后、下一阶段开始前立即执行。**会阻塞事件循环**，递归调用可能导致事件循环饥饿。

`setImmediate`：在**当前事件循环的 check 阶段**执行，位于 I/O 回调之后。**不会阻塞事件循环**，是设计用于执行低优先级任务。

执行顺序：`process.nextTick` 总是在 `setImmediate` 之前执行。

选择原则：**需要尽快执行且代码量小用 **`nextTick`**，需要延迟执行不阻塞事件循环用 **`setImmediate`。

**核心要点（快速回忆）：**

|  | `process.nextTick` | `setImmediate` |
| --- | --- | --- |
| 执行阶段 | 当前阶段结束，下一阶段前 | check 阶段 |
| 优先级 | 最高 | 较低 |
| 会阻塞 | ✅ 可能 | ❌ 不会 |
| 适用场景 | 紧急小任务 | 低优先级延迟任务 |


**代码示例：**

```javascript
// 执行顺序验证
setImmediate(() => {
  console.log('1: setImmediate')
})

process.nextTick(() => {
  console.log('2: process.nextTick')
})

// 输出：2 → 1

// nextTick 阻塞事件循环示例（危险）
function loop() {
  process.nextTick(loop)
}
// loop() // 会阻止事件循环进入下一阶段，导致 I/O 无法处理

// 正确用法：在事件循环中确保回调异步执行
function asyncOperation(callback) {
  // 确保回调异步执行，避免同步调用导致的调用栈问题
  process.nextTick(callback)
}

// 错误用法示例
let count = 0
setImmediate(() => {
  console.log('setImmediate 执行')
})

// 下面会导致 nextTick 永远执行不完，setImmediate 永远不执行
function recursiveNextTick() {
  process.nextTick(() => {
    count++
    if (count < 1000) recursiveNextTick()
  })
}
// recursiveNextTick()
```

### 2.2 `path` 模块的常用方法有哪些？
**面试回答（直接背）：**

`path` 模块用于处理文件和目录的路径，**自动处理跨平台路径分隔符**（Windows 用 `\`，Unix 用 `/`）。

**路径拼接**：

+ `path.join('a', 'b', 'c')` → `a/b/c`（自动处理分隔符）
+ `path.resolve('a', 'b')` → 绝对路径（从当前目录开始解析）

**路径信息提取**：

+ `path.basename('/a/b/file.js')` → `file.js`（文件名）
+ `path.dirname('/a/b/file.js')` → `/a/b`（目录名）
+ `path.extname('/a/b/file.js')` → `.js`（扩展名）

**路径解析**：

+ `path.parse('/a/b/file.js')` → 返回对象 `{ root, dir, base, name, ext }`
+ `path.format(obj)` → 从对象生成路径

**跨平台**：

+ `path.sep` → 路径分隔符（`/` 或 `\`）
+ `path.delimiter` → 环境变量分隔符（`:` 或 `;`）

**核心要点（快速回忆）：**

| 方法 | 作用 |
| --- | --- |
| `join` | 拼接路径（自动处理分隔符） |
| `resolve` | 解析为绝对路径 |
| `basename` | 获取文件名 |
| `dirname` | 获取目录名 |
| `extname` | 获取扩展名 |
| `parse` | 解析路径为对象 |


**代码示例：**

```javascript
const path = require('path')

console.log(path.join('/a', 'b', 'c')) // /a/b/c
console.log(path.join('a', 'b', '..', 'c')) // a/c

// 绝对路径解析
```

### 2.3 `Buffer` 是什么？有什么用途？
**面试回答（直接背）：**

`Buffer` 是 Node.js 中用于**处理二进制数据**的类，用于在 TCP 流、文件操作等场景中处理原始字节数据。Buffer 是**固定大小**的，创建后不能改变大小。

**创建 Buffer**：

+ `Buffer.alloc(size)`：分配指定大小的 Buffer（初始化填充 0，安全）
+ `Buffer.allocUnsafe(size)`：分配但**不初始化**（更快，可能包含旧数据）
+ `Buffer.from(data)`：从数组/字符串/Buffer 创建

**读写数据**：

+ `buf[index]`：读取/设置指定字节（0-255）
+ `buf.toString(encoding)`：转字符串（默认 utf8）
+ `buf.write(string, offset, length, encoding)`：写入字符串
+ `buf.slice(start, end)`：切片（共享内存，不是拷贝）

**编码支持**：`utf8`、`ascii`、`base64`、`hex`、`latin1` 等。

**核心要点（快速回忆）：**

+ **本质**：处理二进制数据的类
+ **创建**：`alloc`（安全）、`allocUnsafe`（快）、`from`
+ **固定大小**：创建后不可变
+ **用途**：文件操作、网络通信、加解密

**代码示例：**

```javascript
// 创建 Buffer
const buf1 = Buffer.alloc(10) // 分配10字节，全部填充0
console.log(buf1) // <Buffer 00 00 00 00 00 00 00 00 00 00>

const buf2 = Buffer.allocUnsafe(10) // 分配10字节，不初始化（快，可能有旧数据）

const buf3 = Buffer.from('hello') // 从字符串创建
console.log(buf3) // <Buffer 68 65 6c 6c 6f>

const buf4 = Buffer.from([0x68, 0x65, 0x6c, 0x6c, 0x6f]) // 从数组创建

// 读写
const buf = Buffer.from('hello world')
console.log(buf[0]) // 104 (ASCII 'h')
buf[0] = 72 // 改为 'H'
console.log(buf.toString()) // Hello world

// 编码转换
const utf8Buf = Buffer.from('你好', 'utf8')
console.log(utf8Buf) // <Buffer e4 bd a0 e5 a5 bd>
console.log(utf8Buf.toString('base64')) // 5L2g5aW9
console.log(utf8Buf.toString('hex')) // e4bda0e5a5bd

// 切片（共享内存）
const slice = buf.slice(0, 5)
console.log(slice.toString()) // Hello
slice[0] = 104 // 修改切片
console.log(buf.toString()) // hello world（原Buffer也被修改）

// 拼接 Buffer
const parts = [Buffer.from('hello'), Buffer.from('world')]
const combined = Buffer.concat(parts)
console.log(combined.toString()) // helloworld
```



### 2.4 `Stream` 是什么？有什么用途？
**面试回答（直接背）：**

Stream（流）是 Node.js 中处理**大量数据**的抽象接口，将数据分成**小块**逐步处理，不需要一次性加载到内存。

**四种类型**：

+ **可读流（Readable）**：读取数据，如 `fs.createReadStream`
+ **可写流（Writable）**：写入数据，如 `fs.createWriteStream`
+ **双工流（Duplex）**：既可读又可写，如 `net.Socket`
+ **转换流（Transform）**：在读写过程中转换数据，如 `zlib.createGzip`

**核心方法**：

+ `stream.pipe(dest)`：管道连接，将可读流数据自动写入可写流
+ `stream.on('data', callback)`：监听数据事件
+ `stream.on('end', callback)`：数据读取完成
+ `stream.on('error', callback)`：错误处理

**优势**：**内存效率高**（不需要加载整个文件），**时间效率高**（边读边处理）。

**核心要点（快速回忆）：**

+ **本质**：分块处理数据，不一次性加载到内存
+ **类型**：可读、可写、双工、转换
+ **核心方法**：`pipe()` 管道连接
+ **适用**：大文件处理、网络传输、数据压缩

**代码示例：**

```javascript
const fs = require('fs')
const zlib = require('zlib')
const { pipeline } = require('stream')

// 1. 基本流操作：复制文件
const readStream = fs.createReadStream('./large-file.txt')
const writeStream = fs.createWriteStream('./copy.txt')

readStream.pipe(writeStream)

readStream.on('end', () => {
  console.log('复制完成')
})

// 2. 错误处理（pipe 不自动处理错误）
readStream.on('error', (err) => console.error('读取错误:', err))
writeStream.on('error', (err) => console.error('写入错误:', err))

// 3. 流事件监听
const stream = fs.createReadStream('./data.txt', { encoding: 'utf8' })

stream.on('data', (chunk) => {
  console.log('收到数据块:', chunk.length)
})

stream.on('end', () => {
  console.log('读取完成')
})

stream.on('error', (err) => {
  console.error('错误:', err)
})

// 4. 转换流：压缩文件（gzip）
const source = fs.createReadStream('./file.txt')
const dest = fs.createWriteStream('./file.txt.gz')
const gzip = zlib.createGzip()

source.pipe(gzip).pipe(dest)
```

## 第三章：事件与进程
### 3.1 `EventEmitter` 是什么？如何实现一个？
**面试回答（直接背）：**

`EventEmitter` 是 Node.js 的**事件核心**，几乎所有模块都继承自它。它基于**观察者模式**，实现事件的发布和订阅。

**核心方法**：

+ `on(event, listener)`：注册事件监听
+ `emit(event, ...args)`：触发事件
+ `once(event, listener)`：注册一次性监听（触发后自动移除）
+ `off(event, listener)` / `removeListener`：移除监听
+ `removeAllListeners(event)`：移除所有监听

**实现原理**：内部维护 `events` 对象，键是事件名，值是回调函数数组。`on` 向数组添加函数，`emit` 遍历数组执行。

**核心要点（快速回忆）：**

+ **模式**：观察者模式（发布-订阅）
+ **核心方法**：`on`、`emit`、`once`、`off`
+ **存储结构**：`{ eventName: [listener1, listener2] }`

**代码示例：**

```javascript
// 使用 EventEmitter
const EventEmitter = require('events')

// 1. 直接使用
const emitter = new EventEmitter()

emitter.on('greet', (name) => {
  console.log(`你好, ${name}`)
})

emitter.once('onceEvent', () => {
  console.log('只执行一次')
})

emitter.emit('greet', '张三') // 你好, 张三
emitter.emit('onceEvent') // 只执行一次
emitter.emit('onceEvent') // 不执行

// 2. 自定义类继承 EventEmitter
class Logger extends EventEmitter {
  log(level, message) {
    this.emit('log', { level, message, timestamp: Date.now() })
  }
}

const logger = new Logger()
logger.on('log', (data) => {
  console.log(`[${data.level}] ${data.message}`)
})

logger.log('INFO', '系统启动')
logger.log('ERROR', '发生错误')

// 3. 监听器数量限制
emitter.setMaxListeners(20) // 设置最大监听数（默认10）
console.log(emitter.getMaxListeners()) // 20

// 4. 错误处理（必须监听 error 事件）
emitter.on('error', (err) => {
  console.error('错误:', err)
})
emitter.emit('error', new Error('出错了'))

// 5. 手写 EventEmitter（精简版）
class MyEventEmitter {
  constructor() {
    this.events = {}
  }

  on(event, listener) {
    if (!this.events[event]) {
      this.events[event] = []
    }
    this.events[event].push(listener)
    return this
  }

  once(event, listener) {
    const wrapper = (...args) => {
      listener(...args)
      this.off(event, wrapper)
    }
    this.on(event, wrapper)
    return this
  }

  emit(event, ...args) {
    if (this.events[event]) {
      this.events[event].forEach(listener => listener(...args))
    }
    return this
  }

  off(event, listener) {
    if (this.events[event]) {
      this.events[event] = this.events[event].filter(l => l !== listener)
    }
    return this
  }
}
```

### 3.3 子进程（child_process）是什么？
**面试回答（直接背）：**

`child_process` 模块用于**创建子进程**，执行外部命令或脚本，实现多进程处理。

**四种创建方式**：

+ `exec(command, callback)`：执行命令，缓冲输出，适合少量输出
+ `execFile(file, args, callback)`：执行可执行文件，比 exec 更安全
+ `spawn(command, args, options)`：执行命令，流式输出，适合大量输出
+ `fork(modulePath, args, options)`：创建 Node.js 子进程，支持 IPC 通信

**通信方式**：

+ 通过 `stdin/stdout/stderr` 流通信（spawn/exec）
+ 通过 `send()` 和 `message` 事件 IPC 通信（fork）

**使用场景**：执行系统命令、并行处理任务、隔离 CPU 密集型任务。

**核心要点（快速回忆）：**

| 方法 | 输出方式 | 适用场景 |
| --- | --- | --- |
| `exec` | 缓冲全部输出 | 少量输出，简单命令 |
| `execFile` | 缓冲全部输出 | 执行可执行文件 |
| `spawn` | 流式输出 | 大量输出，长期运行 |
| `fork` | 流式 + IPC | Node.js 子进程 |


**代码示例：**

```javascript
const { exec, execFile, spawn, fork } = require('child_process')
const path = require('path')

// 1. exec：执行命令，缓冲输出
exec('ls -la', (error, stdout, stderr) => {
  if (error) {
    console.error(`错误: ${error}`)
    return
  }
  console.log(stdout)
})

// 2. execFile：执行文件（更安全，不启动shell）
execFile('node', ['--version'], (error, stdout) => {
  console.log('Node版本:', stdout)
})

// 3. spawn：流式输出（适合大量数据）
const ls = spawn('ls', ['-la', '/usr'])
ls.stdout.on('data', (data) => {
  console.log(`输出: ${data}`)
})
ls.stderr.on('data', (data) => {
  console.error(`错误: ${data}`)
})
ls.on('close', (code) => {
  console.log(`子进程退出: ${code}`)
})

// 4. fork：Node.js 子进程（IPC通信）
// parent.js
const child = fork('./child.js')
child.on('message', (msg) => {
  console.log('收到子进程:', msg)
})
child.send({ type: 'start', data: 100 })

// child.js
process.on('message', (msg) => {
  console.log('收到父进程:', msg)
  // 处理任务
  const result = msg.data * 2
  process.send({ type: 'result', data: result })
})

// 5. 并行任务处理（使用 fork）
const os = require('os')
const cpuCount = os.cpus().length

function runParallel(tasks, workerPath) {
  const workers = []
  let completed = 0
  const results = []

  return new Promise((resolve, reject) => {
    tasks.forEach((task, index) => {
      const worker = fork(workerPath)
      worker.send(task)
      worker.on('message', (result) => {
        results[index] = result
        completed++
        worker.kill()
        if (completed === tasks.length) {
          resolve(results)
        }
      })
      worker.on('error', reject)
      workers.push(worker)
    })
  })
}
```



## 第四章：框架与工程化
### 4.1 Express 和 Koa 的区别是什么？
**面试回答（直接背）：**

Express 和 Koa 都是 Node.js 的 Web 框架，但设计理念不同：

**Koa 是 Express 的升级版**，由同一个团队开发。

**中间件模型**：Express 是**线性中间件**（回调/函数），Koa 是**洋葱圈模型**（`async/await`，中间件可以双向传递控制权）。

**异步处理**：Express 使用回调或 `next()`，异步需要手动处理。Koa 原生支持 `async/await`，异步代码更简洁。

**上下文**：Express 用 `req` 和 `res` 两个对象，Koa 用 `ctx`（Context）封装请求和响应。

**错误处理**：Express 需要手动 `next(err)` 或 `try-catch`。Koa 的 `try-catch` 可以在洋葱圈中捕获错误。

**Koa 更轻量**，核心只提供基础能力，功能通过中间件扩展。Express 更成熟，生态更丰富。

**核心要点（快速回忆）：**

|  | Express | Koa |
| --- | --- | --- |
| 中间件模型 | 线性 | 洋葱圈 |
| 异步方式 | 回调/next | `async/await` |
| 上下文 | `req`/`res` | `ctx` |
| 体积 | 较大 | 轻量 |
| 生态 | 丰富 | 相对较少 |


**代码示例：**

```javascript
// Express 写法
const express = require('express')
const app = express()

// 中间件（线性）
app.use((req, res, next) => {
  console.log('中间件1 开始')
  next()
  console.log('中间件1 结束')
})

app.use((req, res, next) => {
  console.log('中间件2')
  next()
})

app.get('/', (req, res) => {
  res.send('Hello Express')
})

// 错误处理（需要手动 next）
app.use((err, req, res, next) => {
  console.error(err)
  res.status(500).send('服务器错误')
})

app.listen(3000)

// Koa 写法
const Koa = require('koa')
const app = new Koa()

// 中间件（洋葱圈）
app.use(async (ctx, next) => {
  console.log('中间件1 开始')
  await next() // 交给下一个中间件
  console.log('中间件1 结束')
})

app.use(async (ctx, next) => {
  console.log('中间件2 开始')
  await next()
  console.log('中间件2 结束')
})

app.use(async (ctx) => {
  ctx.body = 'Hello Koa'
})

// 错误处理（try-catch）
app.use(async (ctx, next) => {
  try {
    await next()
  } catch (err) {
    ctx.status = 500
    ctx.body = { error: err.message }
  }
})

app.listen(3000)
// 输出顺序（洋葱圈）：
// 中间件1 开始 → 中间件2 开始 → 中间件2 结束 → 中间件1 结束
```

### 4.2 Koa 的洋葱圈模型是什么？
**面试回答（直接背）：**

洋葱圈模型是 Koa 中间件的执行机制：**请求从外到内穿过中间件，响应从内到外穿出**，形成类似洋葱的层次结构。

执行流程：

1. 请求到达，进入第一个中间件
2. 执行中间件中 `await next()` 前的代码
3. 进入下一个中间件
4. 重复直到最后一个中间件
5. 最后一个中间件执行完，返回到上一个中间件
6. 执行 `await next()` 后的代码（反向执行）

**特点**：

+ 中间件可以**双向控制**（请求和响应都能处理）
+ 天然支持**错误处理**（外层中间件可以捕获内层异常）
+ 执行顺序**可预测**（洋葱结构）

**核心要点（快速回忆）：**

+ **模型**：请求从外到内，响应从内到外
+ **关键**：`await next()` 控制流转
+ **优势**：双向控制、错误捕获、顺序可控

**代码示例：**

```javascript
const Koa = require('koa')
const app = new Koa()

// 中间件1（最外层）
app.use(async (ctx, next) => {
  console.log('1: 请求到达 - 开始处理')
  ctx.startTime = Date.now()

  await next() // 进入下一个中间件

  console.log('1: 响应返回 - 完成处理')
  console.log(`总耗时: ${Date.now() - ctx.startTime}ms`)
})

// 中间件2
app.use(async (ctx, next) => {
  console.log('2: 进入中间件2')
  ctx.user = { name: '张三' }

  await next()

  console.log('2: 离开中间件2')
})

// 中间件3（最内层）
app.use(async (ctx, next) => {
  console.log('3: 执行业务逻辑')
  ctx.body = `Hello, ${ctx.user.name}`

  // 最内层没有 next，开始返回
})

app.listen(3000)

// 执行顺序（洋葱圈）：
// 1: 请求到达 - 开始处理
// 2: 进入中间件2
// 3: 执行业务逻辑
// 2: 离开中间件2
// 1: 响应返回 - 完成处理

// 错误处理示例（外层捕获内层错误）
app.use(async (ctx, next) => {
  try {
    await next()
  } catch (err) {
    console.error('捕获到错误:', err.message)
    ctx.status = 500
    ctx.body = { error: err.message }
  }
})

app.use(async (ctx) => {
  throw new Error('业务逻辑错误')
})
```



### 4.3 中间件的实现原理是什么？
**面试回答（直接背）：**

中间件的核心原理是**函数组合（Compose）**，将多个中间件函数组合成一个执行链。

**核心机制**：

1. 每个中间件接收 `ctx` 和 `next` 参数
2. `next` 是下一个中间件的函数引用
3. 通过 `async/await` 或 `Promise` 控制执行流程

**简化实现**：

1. 将所有中间件存入数组
2. `compose` 函数将中间件组合成一个函数
3. 从最后一个中间件开始，依次将前一个中间件包装到 `next` 中
4. 最终返回第一个中间件的执行函数

**核心要点（快速回忆）：**

+ **本质**：函数组合（Compose）
+ **关键**：`ctx`（上下文）+ `next`（下一个函数）
+ **执行流程**：递归调用 `next`，形成洋葱圈

**代码示例：**

```javascript
// 中间件实现原理

// 1. 中间件函数
const middleware1 = async (ctx, next) => {
  console.log('中间件1 开始')
  await next()
  console.log('中间件1 结束')
}

const middleware2 = async (ctx, next) => {
  console.log('中间件2 开始')
  await next()
  console.log('中间件2 结束')
}

const middleware3 = async (ctx, next) => {
  console.log('中间件3（业务逻辑）')
  ctx.body = 'Hello'
}

// 2. compose 函数（核心）
function compose(middlewares) {
  return function(context) {
    let index = -1

    function dispatch(i) {
      if (i <= index) {
        return Promise.reject(new Error('next() called multiple times'))
      }
      index = i

      const middleware = middlewares[i]
      if (!middleware) {
        return Promise.resolve()
      }

      try {
        return Promise.resolve(
          middleware(context, () => dispatch(i + 1))
        )
      } catch (err) {
        return Promise.reject(err)
      }
    }

    return dispatch(0)
  }
}

// 3. 使用
const ctx = {}
const fn = compose([middleware1, middleware2, middleware3])

fn(ctx).then(() => {
  console.log('执行完成, body:', ctx.body)
})

// 输出：
// 中间件1 开始
// 中间件2 开始
// 中间件3（业务逻辑）
// 中间件2 结束
// 中间件1 结束
// 执行完成, body: Hello

// 4. 带错误处理的 compose（Koa 实际实现简化版）
function composeWithError(middlewares) {
  return function(context) {
    let index = -1

    function dispatch(i) {
      if (i <= index) {
        return Promise.reject(new Error('next() called multiple times'))
      }
      index = i

      let middleware = middlewares[i]
      if (!middleware) {
        return Promise.resolve()
      }

      try {
        return Promise.resolve(
          middleware(context, () => dispatch(i + 1))
        )
      } catch (err) {
        return Promise.reject(err)
      }
    }

    return dispatch(0)
  }
}
```



## 第五章：工程化与实践
### 4.4 JWT 鉴权的原理是什么？
**面试回答（直接背）：**

JWT（JSON Web Token）是一种**无状态**的身份认证方案，服务器不需要存储 Session，通过 Token 本身携带用户信息。

**JWT 结构**：由三部分组成，用 `.` 分隔：

+ **Header（头部）**：算法和类型，如 `{ alg: 'HS256', typ: 'JWT' }`
+ **Payload（载荷）**：用户信息（如 `userId`、`role`），**不存敏感信息**（Base64 可解码）
+ **Signature（签名）**：对 Header + Payload 用密钥签名，防篡改

**认证流程**：

1. 用户登录，服务器验证账号密码
2. 生成 JWT 返回给客户端
3. 客户端存储（localStorage/Cookie），后续请求在 Header 中携带 `Authorization: Bearer <token>`
4. 服务器验证签名，解析用户信息

**优缺点**：

+ **优点**：无状态（不需要存储 Session），跨域支持好，适合分布式系统
+ **缺点**：Token 无法主动失效（除非设置短有效期 + 刷新 Token），Payload 不加密（不要存敏感信息）

**核心要点（快速回忆）：**

+ **结构**：Header.Payload.Signature（三部分，`.` 分隔）
+ **流程**：登录生成 → 客户端存储 → 请求携带 → 服务端验证
+ **特点**：无状态、跨域友好、可解码（不存敏感信息）

**代码示例：**

```javascript
const jwt = require('jsonwebtoken')
const SECRET_KEY = 'your-secret-key'

// 1. 生成 JWT
function generateToken(user) {
  const payload = {
    userId: user.id,
    username: user.username,
    role: user.role
  }

  return jwt.sign(payload, SECRET_KEY, {
    expiresIn: '7d', // 7天过期
    algorithm: 'HS256'
  })
}

// 2. 验证 JWT（中间件）
function authMiddleware(req, res, next) {
  const authHeader = req.headers.authorization

  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ error: '未提供Token' })
  }

  const token = authHeader.substring(7) // 去掉 'Bearer '

  try {
    const decoded = jwt.verify(token, SECRET_KEY)
    req.user = decoded // 挂载用户信息
    next()
  } catch (err) {
    if (err.name === 'TokenExpiredError') {
      return res.status(401).json({ error: 'Token已过期' })
    }
    return res.status(401).json({ error: '无效的Token' })
  }
}

// 3. 刷新 Token
function refreshToken(oldToken) {
  try {
    const decoded = jwt.verify(oldToken, SECRET_KEY, {
      ignoreExpiration: true // 允许过期Token刷新
    })

    // 重新生成（更新过期时间）
    const { userId, username, role } = decoded
    return jwt.sign({ userId, username, role }, SECRET_KEY, {
      expiresIn: '7d'
    })
  } catch (err) {
    return null
  }
}

// 4. Express 中使用
const express = require('express')
```

### 4.5 文件上传怎么实现？
**面试回答（直接背）：**

文件上传在 Node.js 中通常使用 `multer`（Express）或 `koa-multer`（Koa）中间件。

**实现步骤**：

1. 前端使用 `multipart/form-data` 格式提交文件
2. 服务端使用 Multer 解析
3. 配置存储位置（磁盘或内存）
4. 处理上传后的文件（保存、重命名、压缩等）

**Multer 配置**：

+ `storage`：存储引擎（`diskStorage` 存磁盘，`memoryStorage` 存内存）
+ `limits`：文件大小限制
+ `fileFilter`：文件类型过滤

**核心要点（快速回忆）：**

+ **前端**：`enctype="multipart/form-data"` + `input[type="file"]`
+ **服务端**：Multer 中间件解析
+ **配置**：存储位置 + 大小限制 + 文件类型

**代码示例：**

```javascript
// Express + Multer 实现文件上传
const express = require('express')
const multer = require('multer')
const path = require('path')
const fs = require('fs')

const app = express()

// 1. 配置存储
const storage = multer.diskStorage({
  // 存储路径
  destination: (req, file, cb) => {
    const uploadDir = './uploads/'
    // 确保目录存在
    if (!fs.existsSync(uploadDir)) {
      fs.mkdirSync(uploadDir, { recursive: true })
    }
    cb(null, uploadDir)
  },
  // 文件名
  filename: (req, file, cb) => {
    const uniqueName = `${Date.now()}-${Math.round(Math.random() * 1E9)}`
    const ext = path.extname(file.originalname)
    cb(null, `${uniqueName}${ext}`)
  }
})

// 2. 文件过滤
const fileFilter = (req, file, cb) => {
  const allowedTypes = ['image/jpeg', 'image/png', 'image/gif', 'image/webp']
  if (allowedTypes.includes(file.mimetype)) {
    cb(null, true)
  } else {
    cb(new Error('只允许上传图片'), false)
  }
}

// 3. 创建 multer 实例
const upload = multer({
  storage,
  limits: {
    fileSize: 5 * 1024 * 1024 // 5MB
  },
  fileFilter
})

// 4. 单文件上传
app.post('/upload/single', upload.single('file'), (req, res) => {
  if (!req.file) {
    return res.status(400).json({ error: '未上传文件' })
  }
  res.json({
    message: '上传成功',
    file: {
      filename: req.file.filename,
      originalName: req.file.originalname,
      size: req.file.size,
      path: req.file.path
    }
  })
})

// 5. 多文件上传
app.post('/upload/multiple', upload.array('files', 5), (req, res) => {
  if (!req.files || req.files.length === 0) {
    return res.status(400).json({ error: '未上传文件' })
  }
  res.json({
    message: `上传成功 ${req.files.length} 个文件`,
    files: req.files.map(f => ({
      filename: f.filename,
      originalName: f.originalname,
      size: f.size
    }))
  })
})

// 6. 错误处理
app.use((err, req, res, next) => {
  if (err instanceof multer.MulterError) {
    if (err.code === 'FILE_TOO_LARGE') {
      return res.status(413).json({ error: '文件过大，最大5MB' })
    }
    return res.status(400).json({ error: err.message })
  }
  next(err)
})

// 7. 前端示例
/*
<form action="/upload/single" method="post" enctype="multipart/form-data">
  <input type="file" name="file">
  <button type="submit">上传</button>
</form>
*/
```
