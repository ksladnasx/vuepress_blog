# 原理说明文章

这只是一篇测试用的文章
还是挺好用的
图片不会立即传到github，只是暂时生成对应的路径，图片本体暂时存在浏览器 IndexedDB 的文章草稿，
只有点击顶部“发布修改”时，才会真正上传到 GitHub

实际的原理说明：
整体逻辑可以理解为：后台页面本身仍然是静态页面，但它在浏览器里直接调用 GitHub API，把“改文章、传图片、删文章、发布修改”这些操作转成对仓库文件的提交。

**GitHub API 更新文章**

登录后台时，你输入 GitHub Token。后台会先调用 GitHub API 验证 `/user` 和仓库权限，然后读取仓库里的文章文件列表与内容。

编辑文章时不会立刻推送到 GitHub，而是先在本地形成草稿。你点击顶部的“发布修改”后，系统会把当前未保存的编辑内容先保存为草稿，然后统一处理所有待发布草稿：

1. 新建文章：根据你选择的存放目录生成新的 md 文件路径，然后通过 GitHub Contents API 创建文件。
2. 修改文章：用原文章路径定位仓库文件，读取/保留对应文件的 `sha`，再通过 GitHub Contents API 更新同一路径文件。
3. 删除文章：把文章加入待删除队列，发布时通过 GitHub Contents API 删除对应文件。
4. 上传图片：图片会进入 `docs/.vuepress/public/uploads/...` 对应的公开资源目录，然后文章里插入 `/uploads/...` 路径。
5. 提交后 GitHub Actions 自动触发构建，把静态站点重新打包部署。

也就是说，并没有一个“专门修改博客文章”的 API，本质是用 GitHub 的“仓库文件增删改 API”去更新 md 文件。文章能被准确修改，靠的是文件路径和 GitHub 返回的 `sha` 来定位版本。

**文章修改监测与 IndexedDB 草稿**

后台维护了两层状态：

一层是远端文章，也就是从 GitHub 读取到的原始文章列表和内容。

另一层是本地草稿，存在浏览器 IndexedDB 里。草稿包括文章正文、日期、目录、分类、标签、额外 frontmatter、是否新建、是否待删除等信息。

编辑器打开文章后，会把当前表单内容和原始内容进行对比。一旦内容不同，就标记为“未保存”，顶部发布按钮右上角的数字也会把这条未保存修改算进去。

草稿保存触发点主要有这些：

1. 手动点击“保存草稿”。
2. 每隔 30 秒自动保存一次，但前提是当前文章有效，比如已经选择存放目录、标题符合要求。
3. 切换到其他文章、新建文章、手机端返回文章列表前，会先尝试保存当前修改。
4. 点击“发布修改”时，会先自动保存当前这篇未保存文章，再统一发布所有草稿。

保存后，草稿会写入 IndexedDB。即使刷新页面，只要还没退出后台或清掉本地数据，这些未发布修改仍然能恢复。发布成功后，对应草稿会从 IndexedDB 里删除，并重新读取远端文章列表，让后台状态和 GitHub 保持一致。

所以现在的工作流是：

在后台编辑文章 -> 本地 IndexedDB 暂存草稿 -> 顶部显示待发布数量 -> 点击发布修改 -> GitHub API 提交文件变化 -> GitHub Actions 自动构建部署。
